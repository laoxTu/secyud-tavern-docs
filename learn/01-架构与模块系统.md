# 01 · 架构与模块系统

这是整个项目的地基。看懂这一章，后面每个模块都只是同一套约定的重复。

---

## 1. 模块 = 目录 + manifest.json

`src/` 下的每个子目录（以及 `plugins/` 下的每个插件）都是一个**模块**，
其身份由一个放在目录根部的 `manifest.json` 声明。

```jsonc
// src/presets/manifest.json
{
  "client": "client", // 前端注册脚本名（相对模块根的路径，省略 .ts/.tsx）
  "id": "preset", // 模块唯一 id
  "server": "server", // 后端注册脚本名
}
```

字段来自 `src/plugins/index.ts`：

```ts
export interface Registerable {
  id: string;
  sequence?: number; // 同层级排序权重，越小越靠前
  requires?: string[]; // 依赖的模块 id，决定初始化顺序
}

export interface Manifest extends Registerable, DisableDto, VersionDto {
  server?: string; // 后端脚本
  client?: string; // 前端脚本
}
```

> ⚠️ 注意两个容易混淆的目录：
>
> - `src/plugins/` —— **框架本体**（Registry 实现），它自己没有 manifest。
> - `plugins/` —— **外部插件**（独立 Git 仓库，pnpm workspace 成员）。

实际在册的模块（由 `src/generated/client-registerer.ts` 可见）：

```
database, comfyui, files, global, lorebooks, memories,
models, presets, signal, stories, tools
外加插件：@plugins/secyud-tavern-importer
```

### 几个真实的 manifest（注意差异）

```jsonc
// src/database/manifest.json —— sequence 让数据库最先初始化
{ "client": "client", "id": "database", "sequence": -1 }

// src/interceptors/manifest.json —— 只有服务端，且脚本路径带子目录
{ "id": "interceptor", "sequence": -1000, "server": "server/register" }

// src/files/manifest.json —— ⚠️ id 是 "file"，与目录名 files 不一致
{ "client": "client", "id": "file" }

// src/models/manifest.json
{ "client": "client", "id": "model", "server": "server" }
```

三点值得注意：

- `server` / `client` 是**相对模块根的路径**（省略扩展名），
  可以是 `server/register` 这样的子路径，不一定是 `index`。
- `sequence` 为负值可让模块抢先初始化
  （`interceptor` 用 `-1000` 保证拦截器最先注册）。
- **`id` 不要求等于目录名** —— `src/files/` 的 id 是 `file`。
  依赖它时要用 `id`，不要用目录名。

## 2. Registry：一切可注册物件的容器

`src/plugins/index.ts` 里的 `Registry<T>` 是全项目复用最多的类。

```ts
export class Registry<T extends Registerable> {
  records: Record<string, T> = {};
  register(...list: T[]): void;
  unregister(id: string): boolean;
  async use(action: (t: T) => Promise<void>, endFlag?: () => boolean);
  first(): T | undefined;
  firstId(): string | undefined;
  record(name?: string): T | null;
  sorted(): T[]; // 带缓存
  protected sortByRequires(): T[]; // Kahn 拓扑排序
}
```

### 拓扑排序的语义

`sortByRequires()` 的行为值得单独说明：

1. 先按 `sequence` 升序排列所有记录（作为兜底次序）。
2. 构建邻接表：若 `A.requires` 含 `B`，则边 `B → A`，`A` 入度 +1。
3. 入度为 0 的节点入队，BFS 出队即得拓扑序。
4. **两种硬错误**：
   - 依赖了不存在的模块 → `Component "X" depends on non-existent component "Y".`
   - 存在环 → `Circular dependency detected involving: ...`

排序结果会被缓存（`sortedItems`），`register` / `unregister` 时失效。

### 全局注册表池

```ts
export function getRegistry<T>(name: string, init?): Registry<T> {
  const g = globalThis as { __registries?: Map<string, Registry<any>> };
  g.__registries ??= new Map();
  ...
}
```

挂在 `globalThis` 上，保证客户端/服务端在同一进程内共享同一份注册表，
也避免 HMR 或模块重复求值时产生多份实例。

### 项目里实际用到的注册表名

| 名称              | 定义位置                               | 用途                                  |
| ----------------- | -------------------------------------- | ------------------------------------- |
| `manifest`        | `scripts/operations/manifest.ts`       | prepare 阶段收集模块描述符            |
| `global-menu`     | `src/global/client/menu.tsx`           | 侧边栏主菜单项                        |
| `model-engine`    | `src/models/{client,server}/engine.ts` | 模型引擎（前后端各一个同名注册表）    |

## 3. 代码生成：把模块焊接成应用

`pnpm prepare` → `scripts/prepare.ts`，依次执行四件事：

```ts
await fileUtils.copy(favicon);
await migrate(root); // ① 数据库迁移
await generateEnvFile(root); // ② 生成 .env（密钥等）
await downloadModels(root); // ③ 下载推理模型到 public/models
await analyzeManifests(root); // ④ 扫描 manifest，生成注册表
const api = await import('./operations/api');
await api.default(root); // ⑤ 由 api.ts 生成真实路由
```

### ④ analyzeManifests 生成四个文件

`scripts/operations/manifest.ts`：

| 产物                                 | 内容                                                    |
| ------------------------------------ | ------------------------------------------------------- |
| `src/generated/resources.ts`         | 各模块 `localization/*.json` 的按语言聚合动态 import    |
| `scripts/generated/route.ts`         | 所有含 `server/api.ts` 的模块列表                       |
| `src/generated/server-registerer.ts` | `registerServerPlugin()`，按拓扑序 await 各模块 default |
| `src/generated/client-registerer.ts` | `registerClientPlugin()`，同上（前端）                  |

生成结果长这样（真实内容）：

```ts
// src/generated/client-registerer.ts
import r0 from '@/database/client'
import r1 from '@/comfyui/client'
...
export async function registerClientPlugin() {
    console.debug('@/database/client');
    await r0();
    ...
}
```

模块的 `client/index.tsx` 与 `server/index.ts` 都把**注册逻辑写在 default export** 里，
这正是注册表能直接 `await rN()` 的原因：

```ts
// src/models/client/index.ts（节选）
export default async function () {
  settings.tabs.register(models.setting);
  engines.registry.register(
    openais.engine,
    deepseeks.engine,
    anthropics.engine,
  );
}
```

### ⑤ API 路由生成

`scripts/operations/api.ts` 做三件事：

1. **递归展开**每个模块 `server/api.ts` 的 default 导出，凡是键名为
   `GET/POST/PUT/DELETE` 的，就记录一条 `{ method, module, path }`。
   嵌套层级直接拼成 URL 路径。
2. **重建** `src/app/api/` 整棵树（先 `rm -rf`，再按路径分组写 `route.ts`）。
3. **生成** `src/generated/api-path.ts`，导出 `GetPath`/`PostPath`/`PutPath`/`DelPath`
   四个字符串联合类型，供前端 `get/post/put/del` 获得类型提示。

生成的 route 本质是转发：

```ts
import api0 from '@/presets/server/api';

export const GET = api0['presets']['[id]']['GET'];
export const POST = api0['presets']['[id]']['POST'];
```

> 因此：**手改 `src/app/api/` 下的任何文件都是无效的**，下次 prepare 会全量覆盖。

## 4. 插件如何接入

插件放在 `plugins/<name>/`，是独立的 Git 仓库，主仓库通过 `.gitmodules` 引用，
pnpm workspace（`pnpm-workspace.yaml` 的 `packages: ['plugins/*']`）把它纳入依赖图。

> laotu：这里说的是示例插件，实际插件只需要是目录，有manifest.json即可。不要求是git仓库，也不要求是子模块

`getManifests()` 会同时扫描 `src/`（别名 `@`）和 `plugins/`（别名 `@plugins`），
因此插件的模块结构与内置模块**完全一致**，共享同一套注册机制。

以 `secyud-tavern-importer` 为例，它的全部工作就是注册一个菜单项：

```jsonc
// plugins/secyud-tavern-importer/manifest.json
{ "id": "secyud-tavern-importer", "version": "1.0.0", "client": "client" }
```

```tsx
// plugins/secyud-tavern-importer/client/index.tsx（节选）
const menu: GlobalMenuItem = {
  id: 'importer',
  label: () => <GlobalMenuLabel name={'importer'} icon={<ImportIcon />} />,
  content: Content,
};
export default function () {
  globals.menus.register(menu);
}
```

**编译期插件的代价**：新增、重命名或修改任何 `manifest.json` 后，
必须重新 `pnpm prepare` 并重启，无法热更新。

## 5. 命名与导出约定

来自 `CONTRIBUTING.md`，写代码时要遵守：

- 类型、工厂、hook **直接导出**；工具函数与常量集合**以对象形式导出**
  （如 `presets`、`strUtils`、`jsonUtils`、`fileUtils`）。
- 每个模块的 `index.ts` 通常导出一个小对象，聚合元信息与工具：

```ts
// src/presets/index.ts（节选）
export const presets = {
  toNameValue(model: Preset): NameValue { ... },
  name: 'preset',
  plural: 'presets',
  tags: ['theme', 'story', 'preset', 'agent', 'app', 'component', 'setting', 'tool'],
};
```

`name` / `plural` 这对字段是贯穿全项目的惯例：`name` 用于 entryType 与注册 id，
`plural` 用于归档时的目录名与 `model.entries[plural]` 键名。

- 格式化：Prettier，单引号、80 列，启用 import 排序与 JSON key 排序插件。
  `pnpm format` **只作用于 `src/`**。
- 多语言：`zh.json` 与 `en.json` 必须成对更新。

### 路径别名

| 别名       | 指向                     |
| ---------- | ------------------------ |
| `@`        | `src/`                   |
| `@/lib`    | `src/utils/lib`          |
| `@/hooks`  | `src/utils/client/hooks` |
| `@plugins` | `plugins/`               |

## 6. 依赖顺序实例

模块间的 `requires` 构成了一条隐含的启动链，例如宏处理链：

```ts
// src/presets/macros/client/realm.ts
export const processer: Processer = {
  id: main.name,
  requires: [regexMain.name], // 宏依赖正则：正则先跑，宏再求值
  init,
  prompt: apply,
};
```

```ts
// src/lorebooks/client/realm.ts
export const processer: Processer = {
  id: main.name,
  requires: [tools.name],       // 世界书依赖工具：knowledge 角色要用工具通道注入
  ...
};
```

所以实际执行序大致是：`regexes → macros → tools → lorebooks`。

## 7. 本章速查

- 想加一个新模块？建目录 → 写 `manifest.json` → 写 `client/index.tsx`（default 里注册）→
  `pnpm prepare` → 重启。
- 想加一个接口？写进模块的 `server/api.ts` → `pnpm prepare`（会重新生成路由）。
- 想改初始化顺序？调 `manifest.json` 里的 `requires` / `sequence`。
- 想知道某个 UI 元素从哪来？去对应注册表找 `register` 的调用点。
