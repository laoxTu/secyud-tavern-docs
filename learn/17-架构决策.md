# 17 · 架构决策与存疑之处

前 17 篇是「这个项目是什么」。这一篇是「我读完之后的所思所想」——
包括我认为它做得好的地方、让我困惑的地方、以及我自己在整理笔记时犯的错。

这一篇带主观判断，与前 17 篇的客观陈述性质不同，请分开看待。

---

## 一、这个项目最打动我的地方

### 1. 它把「可定制」做到了骨子里，而不是嘴上

大多数标榜「高度可定制」的项目，定制点是**枚举出来的**：
给你一堆开关、一堆模板槽位，你能改的都在文档里列着。

这个项目的做法不一样。它把**界面本身**也交给了用户：

> 没有任何预设时，是一片空白，无法直接互动。
> 你需要至少一个展示脚本才能看到交互页面。

第一次读到 `realm.md` 这句话时我愣了一下。这不是"功能缺失"的委婉说法，
而是一个**刻意的架构决定**——宿主连"聊天界面长什么样"都不预设，
只提供一个 iframe、一套 `postMessage` 协议、一个 `userInput` 接口。

结果是预设作者的能力边界不再是"配置"，而是"编程"。
`疯狂水世界`、`模拟经营` 这类模板能存在，正是因为这条路是通的。

**代价也真实存在**：新人第一次运行会面对空白页面不知所措。
这是个勇敢的取舍，我不确定换成我会不会敢做。

### 2. 「复用已有的通道」比「新建一套机制」更聪明

有两处设计让我停下来想了很久：

**第一处是知识注入。** 世界书和记忆都需要往上下文里塞文本。
最直觉的做法是设计一种新的消息类型，比如 `role: 'knowledge'` 直接插进 messages。
但作者的做法是——**伪造一次 `get_knowledge` 工具调用**：

```ts
caller('', null, [
  {
    name: models.engines.knowledge.info.name, // 'get_knowledge'
    arguments: models.engines.knowledge.args({ type: 'lorebook' }),
    result: content,
  },
]);
```

于是世界书、记忆、未来的任何"知识"都复用同一条工具通道，
不需要在引擎层为"知识"这个概念写任何代码。
那句 `description: 'return empty if current knowledge is injected'`
甚至是在用自然语言引导模型不要重复调用——很巧。

**第二处是变量系统。** 每条消息挂一个 JSON Patch 数组而非完整快照。
省存储只是顺带的好处，真正的收益是：**切换到任意历史输出，
回放补丁就能得到那一刻的变量状态**。"输出翻页会改变上下文"这个交互，
在数据模型层面就已经成立了，不需要额外写状态管理代码。

这种"让数据结构自己承载语义"的思路，我觉得是这个项目里最值得学的东西。

### 3. 代码注释保留了「为什么」

很多项目的注释在解释"这段代码在做什么"——而这从代码本身就能看出来。
这个项目的注释更多在记录**决策与陷阱**：

```ts
/**
 * 复选的规则很复杂，
 * 1，相同的code，不同的key共享一个禁用
 * 2，不同的code，相同的key是正常情况
 * 3，相同的code，相同的key，会追加且共享
 * 这是为多preset设计的，可以继承，共享
 */
```

```tsx
{
  /* key不要删除。发布后，如果没有这个key，会导致引用有问题，原因不明，开发环境无此问题。 */
}
```

第二句尤其珍贵——**作者明确承认"原因不明"**。
比编一个听起来合理的解释要诚实得多，也更有用：
后来者知道这里不能乱动，且知道作者也没搞懂。

## 二、让我困惑或存疑的地方

下面这些不是"bug 清单"（那在 [12-开发手册](./15-开发手册.md) 里），
而是我在阅读时**停下来想过"为什么"但没能完全说服自己**的地方。

### 1. `Promise<{ id: string }>` 形式的 params

`src/app/[id]/page.tsx` 的 props 是 `params: Promise<{ id: string }>`，
所有 API handler 都要写 `const { id } = await params`。

这是 Next.js 15+ 的破坏性变更（params 改为异步）。
项目用了 Next 16，所以必须跟进——但整个代码库里这个 `await` 无处不在，
读起来有种"到处在等同一个东西"的噪音感。这不是项目的问题，
但我确实花了几分钟才确认这不是某种自定义约定。

### 2. 为什么模块注册要写成 `default export async function`

```ts
export default async function () {
  globals.menus.register(menu);
}
```

匿名 default 导出的函数，在调用栈里显示不出名字，调试时不够友好。
代码生成器生成的 `console.debug('@/presets/client')` 一定程度上补偿了这点，
但如果写成具名函数（`export default async function registerPresets()`），
profiler 里的可读性会好很多。这可能只是个小疏忽。

### 3. `disabled` 字段的两套语义

预设里的条目禁用状态存在**两处**：

- 数据库 `preset_entry.disabled` 列（条目自身）
- `realm.properties` 里的 `checkItems` / `selections` / `items`（运行时开关）

宏和工具用 getter/setter 把两者缝在一起：

```ts
get disabled() {
  return (macro ? checkItems[tool.name] : items[tool.name]) ?? disabled;
}
```

这个设计是合理的（条目默认值 + 本次游玩覆盖），
但 `??` 的语义意味着**运行时一旦显式设过就永远覆盖条目配置**，
且没法"恢复默认"。我在笔记里如实描述了，但没找到"重置为默认"的入口。

### 4. `builder: 'layered'` 的归属

`model.builder` 字段定义在**模型**上，但消费点在**世界书注入器**里。
我一开始在 `src/models/**` 里找了很久都没找到用法，差点当成死字段。

跨模块通过一个字符串字段解耦，好处是模型侧无需知道世界书的存在；
代价是这个字段的语义漂在两个模块之间，只看一边完全看不懂。
我在 [08-模型接入](./07-模型接入.md) 和 [05-世界书](./12-世界书.md) 里
各写了一半，读者需要跨篇拼起来。

## 三、我自己犯的错（值得记下来）

### 我把 Zod 写进了技术栈

这个错误值得单独拿出来说，因为它的成因很典型。

我在最初浏览项目时用 glob 扫了一遍文件树，`node_modules/.pnpm/` 里出现了
`zod-to-json-schema@3.25.2_zod@3.25.76`。后来整理技术栈表时，
我把 Zod 写了进去——**尽管我早就读过 `package.json`**。

问题出在哪？我把"这个目录存在于 node_modules" 当成了
"这是项目的依赖"。而它其实只是某个包（可能是 `shadcn` CLI 或 drizzle-kit）
的传递依赖，跟你删没删毫无关系。

**教训**：`node_modules` 只能说明"某个东西被安装过"，
判断直接依赖的唯一依据是 `package.json`。我跳过了这一步，
而且是在**已经读过正确信息的情况下**跳过的——这比"没查"更糟，
因为它说明我当时是在凭印象填表，而不是在核对。

顺手复查又发现同表的第二处错误：我写了 "Radix / Base UI"，
实际是 32 处 `@base-ui/react`、0 处 `@radix-ui`，底层是 Base UI。
更尴尬的是我在 `06-前端架构.md` 里写对了（"底层不是 Radix"），
两篇自相矛盾——说明我写总览时是在**总结印象**，而不是**回查事实**。

### 我依赖了四个 subagent 的报告

这一轮我派了 4 个 subagent 并行调研，它们返回了很详实的报告。
这提高了效率，但引入了一个风险：**我把它们的部分结论直接写进了笔记，
而没有逐条回到源码验证**。

比如 ComfyUI 的 `execSync` 命令注入、`checker.validateCode` 的正则只匹配单字符
——这两条我后来抽查确认是真的。但"抽查确认了两条"不等于"其余都确认了"。

我现在的判断是：subagent 报告适合用来**发现问题**，
不适合直接作为**结论**。我在笔记开头写了"结论均来自源码阅读"，
更准确的说法应该是"主干逻辑来自我亲自阅读，部分细节来自辅助调研"。

### 关于「疑似 bug」的分寸

我标注了大约 10 处疑似 bug。回头看，我的分寸大致是：

- **高置信**（读了完整调用链，能说清为什么错）：
  如正则 `target` 过滤与挂载点不一致、`remaining.join(', ')` 对对象数组调用。
- **中置信**（两处代码对不上，但可能是我漏看了中间环节）：
  如 vector 匹配器索引写 `name`、检索比对 `id`。
- **低置信**（只是"看起来不对"）：
  如非流式分支传 `stream: true`——也可能是我误解了参数语义。

我尽量都标了"疑似"并写了不确定的原因。但现在想，
**更好的做法是把置信度写得更显式**，而不是让读者从我措辞的软硬去猜。

## 四、读完之后的几个判断

### 这个项目的复杂度是"必要复杂度"

`src/` 下 364 个文件、10 个模块、一套代码生成流水线——
乍看很重。但读完之后我认为大部分复杂度是被**产品目标逼出来的**：

要让"预设能自己画界面"，就必须有 iframe + 消息协议；
要让"多个预设能叠加继承"，就必须有条目合并与去重规则；
要让"用户能翻看历史并回滚变量"，就必须有 Patch 回放。

真正的"额外复杂度"其实不多。唯一让我觉得可以更简单的是注册表系统——
但换成别的方案，大概也省不下多少，还未必有 `requires` 拓扑排序这么清晰。

### 测试是最大的欠账

4 个测试文件，覆盖 ComfyUI 的两个点、宏的 Eta 调用、hasher 往返。
而数据库、插件系统、拦截器、生成管线、故事、世界书——**全是零覆盖**。

我读代码时多次遇到"这行为对不对？"却无法通过测试确认
（比如 vector 匹配器那个疑似 bug，一个测试就能定性）。
`CONTRIBUTING.md` 说"纯逻辑部分非常欢迎补测试"，这个邀请是真诚的，
因为`Registry.sortByRequires`、`jsonUtils.merge`、`json-patch`
这些东西**测试成本极低、价值极高**。

### 「自部署个人应用」这个定位解释了几乎所有取舍

一开始我对"允许预设执行任意 JS"感到不安。读完 `CONTRIBUTING.md`
的那一节后才理解：**部署者即管理员，不存在多租户边界**。
在这个前提下，允许执行用户自己写的脚本不是漏洞，是功能——
就像本地 IDE 允许你运行自己的代码一样。

这让我意识到：**评价一个安全设计，必须先确定威胁模型**。
脱离"谁在用、谁能被攻击"谈"这段代码危不危险"，是没有意义的。
（当然，`execSync` 拼 curl 那条仍然值得修——
它的输入虽然来自本地库，但库内容来自外部 API，链条更长。）

## 五、如果我要继续参与

按我心里的优先级：

1. **补测试**——尤其是 `Registry` 的拓扑排序、
   `json-patch` 的 `patch`/`extract`、`buildUrl`/`handleResponse`。
   这是唯一能"低风险高收益"改变项目质量的事。
2. **给疑似 bug 写复现用例**——把"疑似"变成"确定是/不是"。
   vector 匹配器那条尤其值得，因为它影响功能正确性而非仅代码整洁。
3. **修明确的低级错误**——`checker.validateCode` 的正则、
   `response.download` 的 Content-Type、循环依赖报错里的 `[object Object]`。
   这些改动小、风险低、不会有争议。
4. **谨慎碰的东西**：正则 `target` 的语义、
   `Registry` 的报错行为——这些可能有人依赖了当前行为，
   按 `CONTRIBUTING.md` 的建议，**先开 Issue 讨论再动手**。

## 六、最后

这个项目给我最深的印象不是某个具体技术点，而是一种**态度**：
作者在注释里承认"原因不明"，在文档里承认"目前不能复刻脚本，需要自行调整"，
在贡献指南里明确说"不要提移除能力的加固 PR"。

这种坦诚让代码变得可读——**因为我知道哪里是精心设计的，哪里是妥协的产物**。
读一个把取舍摊开来讲的代码库，比读一个假装一切都很完美的代码库，
收获要大得多。

也正因为如此，我把自己犯的错（Zod、Radix）也写进了这一篇。
如果只留下"我读懂了"的部分而藏起"我搞错了"的部分，
那这份笔记本身就成了另一种"假装完美"。

## 七、二次核对（基线 `1.3.3.0`）：七处误报、两处确认、一批过期项

> 本节内容来自 2026-09-21 的一次代码评审讨论。我按前 17 篇的方法又读了一遍
> 若干核心文件（`plugins/`、`utils/json`、`utils/archive`、`files/`、
> `presets/server/api`、`models/client/processer`）并提交了一份缺陷报告，
> **9 条里被作者驳回 7 条**，驳回理由统一的都是「这是刻意的设计」。
> 把结论固化在这里，避免后来者重复误判。
> 本节基线是 `70fe081`（`1.3.3.0` 之后的提交），与前文的 `1.3.2.8` 不同。

### 1. 七处被我误判为缺陷的刻意设计

| 我报的「缺陷」                                       | 实际的设计意图                                                                                                                                                       |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `jsonUtils.merge` 原地改入参、跳过 `null`            | 左值是累加器（**可引用，也可初始化**），右值永不被改 / 不被别名 / 不擦除字段；结果身份要么是左值、要么是新克隆。「跳过 `null`」就是「合并不擦除」，与「保留左值」是同一件事。 |
| `Registry.sortByRequires` 里 `sequence` 会被依赖覆盖 | `sequence` 是**粗排**（直觉顺序），`requires` 是**严格约束**，两者不同源、依赖优先。见 [03 篇](./03-模块系统.md)补充。                                            |
| `files` 用一个字段同时存 uuid 与外链 URL             | **复用字段**，运行时按值分流：URL → 显示外链，GUID → 内部文件。                                                                                                      |
| `jsonUtils.minify` 把非法 JSON 变成空串              | **边界消毒**。上游 UI 已校验；非法内容只可能来自导入的预设包，清空是刻意的（省 token、防误导格式）。见 [12 篇](./12-世界书.md)补充。                                   |
| `getRegistry` 第二次调用静默忽略 `init`              | 初始化设计：注册表**单所有者**，`init` 只在创建那一刻执行。                                                                                                           |
| `deserializeMimeType` 的 `args` 往返不一致           | `args` 不参与语义，这个字段只存取前段 `type`，「后面的不重要」。                                                                                                       |
| `parse` / `zipToArchive` / `create` 的静默降级       | 导出/导入的**容错策略**：没有内容的文件不该出现在包里（省空间，也避免空白文件干扰外部检阅）；导入侧保持宽容、不做拦截报错，责任在预设包的制作者。                       |

**共性**：这七条的正确性都依赖一个**写在代码之外的前提**
（「左值是调用方自己的对象」、「上游已校验」、「空文件不必导出」……），
而代码里没有任何地方记录它。我读到的只是它们**在缺少前提时看起来的样子**。

这也正好解释了 issue **#35**（iframe sandbox）与 **#38**（default 模式无 token 预算）：
`CONTRIBUTING.md` 里那节「关于安全性的取舍」把前提写下来了，
所以 AI 复核提这两条时，作者可以直接引用它说明「这是刻意的」。
**前提被写下来的地方，误报就停止了。** 本节存在的意义就是给剩下那些地方补上前提。

### 2. 两处真实问题（其中一处作者已确认）

- **`retry.max = 0`**：`while (retry > 0)` 把唯一的 `engine.generate` 调用包在里面，
  `0` 会让这次生成**一个请求都不发**，而外层 `iteration` 循环照跑，产出 20 条空输出。
  设置界面的 `min={0}` 恰好允许这个值。**作者确认为 bug，`min` 应为 1。**
- **`NaN` 通道**：`forms.int` 是裸 `parseInt`，清空数字输入框即得 `NaN`；
  `Math.max(2, model.iterations ?? 20)` 与 `while (iteration > 0)` 都接不住
  （`??` 只挡 `null` / `undefined`，挡不住 `NaN`）。详见
  [08 篇「已知问题」第 5 条](./08-生成管线.md)。

### 4. 一条方法上的结论

标注「疑似」是对的，但**只标注置信度不够**。如果一个「看起来不对」的写法，
其正确性依赖代码外的前提，那么**从代码本身永远无法判定**它是否成立 ——
提高置信度也解决不了这个问题。

遇到这类条目，更有用的动作是问一句「这里有没有我读不到的前提」，
而不是回去把代码再读一遍。我那七条误报全部属于这一类。
这也是我上一节说自己「应该把置信度写得更显式」的进一步修正：
**该显式的不是置信度，而是「这条依赖什么前提」。**

## 八、三次核对（基线 `1.3.5.0`）：还上的债、新挖的坑、以及一条验证方法的边界

> 本节来自 `1.3.5.0`（`73e66eb`）的一次全文复核。
> 我把 02–19 篇逐句对照当前源码，把失效的结论改掉、把新增的机制补上，
> 并新增了 [17-任务与调度](./10-任务与调度.md)。
> 下面只写**「核对之后我改变了看法」的部分**，逐条清单在各篇的「已知问题」里。

### 1. 我上一节的方法论有个缺口：我把「没测试」当成了「无法验证」

§七 结尾我写了一句：「正确性依赖代码外前提的写法，读代码判不出来」。
这话在**语义前提**上是对的，但我把它用过头了 ——
当时的隐含推论是「既然没有测试，那也只能靠读和猜」。
**这个推论是错的**，因为「跑不了测试套件」不等于「跑不了代码」。

这一轮复核里，我对 `signals.proxy.subscription` 那个缺陷就是这么处理的：

1. 静态阅读指向「`{id}` 没被替换」，但我不确定 `buildUrl` 在
   `params` 缺失时到底怎么走；
2. **把 `buildUrl` 原样抠出来，写成一段独立脚本，喂四种入参直接跑**；
3. 实测输出确认：`"sse/{id}/subscription" + { action, type }` →
   `sse/{id}/subscription?action=set&type=task_progress`，**占位符原样留着**。

成本大约两分钟，得到的是**确定结论**而不是「疑似」。
（方法细节见 [04 篇](./04-接口层.md) §9。）

> **教训**：读代码判不出来的，往往是**运行时行为**；
> 而运行时行为里有一大类（纯函数）**根本不需要测试框架**。
> 我上一节把「前提缺失」与「缺少运行环境」混成了一件难事，
> 实际上它们是两种不同的问题，解法也不同。

### 2. 边界的另一面：真跑不了的那部分，要老实标注

`pnpm test` 在当前沙箱里确实起不来（Vite 加载配置时要 `spawn`，被拒 `EPERM`）。
这次我没有像上轮那样「派 subagent 调研然后直接采信」，
而是定了一条更保守的规矩：

| 证据类型 | 我怎么标注 |
| --- | --- |
| 我独立读码且链路完整 | 🔬 |
| 来自 `tests/TODO.md`（有行号/实测记录） | 📄 |
| 纯读码推断、未实测 | 🔍 |

这样一来，读者不必从我措辞的软硬去猜置信度 ——
这正是 §三 里我批评过自己的那点（「更好的做法是把置信度写得更显式」）。
**这一轮总算做到了，但用的是符号而不是散文。**

### 3. 我要收回两处上轮的判断

**第一处：测试欠账的严重程度。**
§四 我写「测试是最大的欠账」。这句话在当时成立，
但到 `1.3.5.0` 已经完全反过来了 ——
**160 个测试文件、1785 个用例**，而且配了
`tests/GUIDELINES.md`（怎么写）与 `tests/TODO.md`（哪里有坑）。
我在 [18 篇](./18-项目评价.md) §6.1 单独称赞了后者。

我上轮把「测试」当成这个项目最需要外部推动的地方，现在它变成了
**这个项目最值得学的工程实践之一**。判断错了就要说错在哪：
我当时只在看「有没有」，没有能力评估「补起来有多快」。

**第二处：「零测试覆盖」被我写进了风险清单。**
[19 篇](./19-项目潜力.md) §三 原来的三个瓶颈里有一条是它。
现在只剩「单点依赖」与「生态冷启动」。
**一个风险项在 33 天内被消掉，说明我的风险评估颗粒度太粗**
—— 我把「当前状态」写成了「结构性缺陷」。

### 4. 这一轮新确认的东西（比修 bug 更有价值的两条）

**其一：这个项目的「好设计」在持续产出。**
`ask_user`（[09 篇](./09-工具与记忆.md) §4）用**一个永不 resolve 的 Promise**
实现了「AI 停下来问用户」，没有给生成管线加任何暂停/恢复概念。
这与我 §一 里最欣赏的那两处（伪工具注入、JSON Patch）是同一种品味：
**不新增机制，用已有原语表达新语义**。

**其二：`TaskRunner` 被第二次用到，而且用得很干净。**
一个为「后台长任务」写的并发池，被 `tools/client/task.ts` 直接继承去做
「工具并行调用」。两个子类的差异只落在「结果去哪」与「谁来等」，
队列/锁/状态机/重试/并发上限全部复用
（对照表见 [10 篇](./10-任务与调度.md) §6）。

我上轮说「注册表系统是唯一让我觉得可以更简单的地方」。
现在看，**真正的抽象能力体现在「第二个用户来得有多快、改得有多少」**——
`TaskRunner` 交出了满分答卷。

### 5. 关于「疑似 bug」的新分寸

上轮我定的分寸是「读完整调用链 → 高置信」。
这轮我加了两条更硬的判据，因为它们分歧更小：

1. **能实测的必须实测**（纯函数、字符串处理、条件分支）；
2. **不能实测的，看它是否被测试固化**。
   如果一条可疑行为**已被 `it(...)` 断言锁定**，
   那它就不是「漏掉的边界」，而是**已知的取舍**
   （例：`tasks` 的 `restart` 只允许 `running` 状态，有专门用例）。

第 2 条让我避免了两处误报 —— 我一开始把
「restart 非 running 报错」和「达到上限时任务留在队列」都当成缺陷，
读了测试才发现作者明确知道并接受它们。
**「有测试」不只是安全网，它也是一种意图声明。**

### 6. 我要收回第三处判断：把「命名规律」写成了「读代码陷阱」

> 📌 本节标题说的「两处」，到这里变成了三处 ——
> 第三处是我写完之后经读者指出才想通的，没有回去改标题，
> 以免掩盖它「后补」的痕迹。

（这一条是写完上面五节之后、经读者指出才补的，值得单独留档。）

我在 [03 篇](./03-模块系统.md) §2 原来写的是：

> 其中 `model-engine`、`tool-provider`、`comfyui-model-importer` 这三对
> **同名不同接口**，是读代码最容易读串的地方。

这句话把**结论当成了口诀**。它教人"记住这三个名字要小心"，
却没有回答**为什么它们同名** —— 于是读者只能靠背，遇到第四个同类还是会慌。

正确的理解是：

> **一个模块 = 一个业务域。域在浏览器与 Node 两侧各有一套实现，
> 它们服务同一个概念，所以注册表名必然相同。**

名字标识的是**域**，不是实现。两侧的差别不在名字里，而在
「同一个域的两个运行时半边各承担什么职责」——
客户端做**界面与交互**（`configComponent` / `configureObject` / `create`），
服务端做**执行与数据**（`generate` / `download` / 归档）。

我回头实测了三对接口，分工完全一致：

| 注册表 | 客户端半边 | 服务端半边 |
| --- | --- | --- |
| `model-engine` | `configComponent` · `configureObject` · `prompt` · `result` | `generate()` |
| `comfyui-model-importer` | `configComponent` · `configureObject` | `download()` |
| `tool-provider` | `configComponent` · `configureObject` · `create` | `loadArchive` · `saveArchive` ⚠️ |

**规律一旦立起来，判据就是反的**：看到两侧同名 → 立刻想到
「这是同一个域的两面」，然后去找两面各做什么，而不是担心混用。

**而且这条规律立刻产出了一个结论**：`tool-provider` 的三对里，
服务端半边**只有归档钩子**，没有"提供工具"的语义 ——
它和客户端那半边**合不成一个域**。按上面的判据，
这正是**命名缺口**的信号（更贴切的可能是 `tool-archive`），
而不是"又一个要背的名字"。

**教训**：我上一轮把「同名」当成了需要防御的复杂度，
实际上它是**架构一致性留下的线索**。两者的区别在于
前者只能背、后者可以用来推导。

> 顺带修正一个相邻的误判：`model-processer` 与 `realm-processer`
> 我原来隐约当成"前后端同名的一对"，其实**两个都在客户端**。
> 它们不同名、也不同侧，是真的两件事
> （名字里的 `model`/`realm` 指**处理对象**，不是运行时侧，见 [08 篇](./08-生成管线.md) §1）。
>
> 这事说明我当时是**按"名字像"归类的，而不是按"域"归类的** ——
> 这与我 §三 里反省的 Zod 错误是同一个毛病：
> 凭印象建立关联，而不是回到事实核对。

### 7. 最后：这一轮我最想留在笔记里的一句话

复核 10 篇、改动上百处之后，如果只留一句给后来者：

> **这个项目的注释和测试，都在替作者说「我知道这里是这样的」。
> 读它们，优先于读我的笔记。**

我这份笔记的价值在于**跨模块的地图**（谁依赖谁、数据怎么流、
哪些名字相同但接口不同）；一旦落到具体行为，
源码注释与 `tests/TODO.md` 永远比我准。
上轮我在「关于本笔记的可靠性」里写了类似的话，
但那时测试只有 4 个文件，说这话底气不足。现在可以了。

## 附：几条通用的阅读心得

- **先找注册点，再看实现**。这个项目里"什么东西从哪来"永远比"它怎么工作"更难找。
- **`manifest.json` 是理解模块边界的钥匙**，比任何文档都准。
- **两侧同名 = 一个域的两个运行时半边，不是陷阱。**
  看到 `model-engine` 在 `client/` 与 `server/` 各有一个，
  应该立刻想到「这是同一个域的两面」，去找这两面各做什么；
  客户端管**界面与交互**、服务端管**执行与数据**。
  （这条我在 `1.3.5.0` 复核时才想通，之前写成了"最容易读串的地方"——见 §八 第 6 条。）
- **真正该警惕的是「不同名却同形」**：`model-processer` vs `realm-processer`
  （都在客户端，属不同模块）、`TaskRunner.execute` vs `TaskProvider.execute`
  （同名不同签名）、`src/plugins/` vs `plugins/`（这才是同名不同物）。
- **`requires` 就是调用顺序**。看不懂执行顺序时，先查 `requires`。
- **文档与代码冲突时信代码**。我至少遇到两处
  （`Script.defaultEntry.type`、正则 target 的行为）。
- **警惕"看起来有据"的推断**。我的 Zod 错误就是这么来的。
- **"正确性依赖代码外前提"的写法，读代码判不出来**——先问前提，别急着下结论。
  （这条是补的，见 §七。）
- **能跑的就跑**：纯函数不需要测试框架，抠出来单跑两分钟就有确定答案。
  （这条是补的，见 §八 第 1 条。）
- **可疑行为先查有没有测试**：被 `it(...)` 锁住的可疑写法多半是**已知取舍**，
  不是漏掉的边界。（这条是补的，见 §八 第 5 条。）
- **`tests/TODO.md` 比大多数文档更值得读**：它逐条标了行号，
  还区分了「已实测」与「纯推断」。按它索骥，别当结论用。
