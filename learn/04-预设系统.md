# 04 · 预设系统

**预设（Preset）是这个项目的玩法包**。它自己不直接产生行为，
而是通过一组「条目」参与生成流程与渲染流程。

> 官方文档的说法：没有任何预设时是一片空白，无法直接互动，
> 你至少需要一个展示脚本才能看到交互页面。**所有交互内容都是可定制的。**

> 📌 本篇已按 `1.3.5.0` 复核。主要变化：正则 `target` 作用域**已修复**、
> `Script.defaultEntry.type` **已改为 `application/javascript`**、
> `presets.toNameValue` 现在拼上了版本号、新增「条目重复机制」小节。

## 1. Preset 数据模型

```ts
// src/presets/index.ts
export interface Preset extends Entity, Properties, Entries {
  name: string; // 显示名
  version: string; // 版本，用户自填
  cover?: string; // 封面（文件 id）
  opening?: string; // 开场白
  variables?: string; // 初始变量（JSON 字符串）
  description?: string;
  tags: string[]; // 分类标签
  requires: NameValue[]; // 依赖的其他预设（注意：是预设级依赖，非模块级）
}

// 数据库直存格式
export interface PresetEntry<T = any> extends Entry, DisableDto {
  data: T;
}

// 导入导出格式（Storage 负责转换）
export type PresetItem<T = any> = DisableDto & T & EntryItem;
```

`requires` 在预设层是**预设之间的依赖**（会随本预设一起加载），
不要与 `manifest.json` 里模块级的 `requires` 混淆。
解析发生在 `presets.repository.traversal()`：BFS 展开依赖闭包后**反转**，
所以 `realm.presets` 里**依赖排在前面、使用者在后面**
（详见 [02-数据层](./02-数据层.md) §5）。

### 标签体系

```ts
tags: [
  'theme',
  'story',
  'preset',
  'agent',
  'app',
  'component',
  'setting',
  'tool',
];
```

> ⚠️ 注意 `presets.tags` 里写的是 `'setting'`（单数），
> 而 `docs/templates/root/默认设置/meta.json` 里用的是 `'settings'`（复数）。
> 标签目前**只用于 `LIKE '%tag%'` 模糊匹配**，不做枚举校验，
> 所以这种不一致不会有报错，只会让筛选结果对不上。

### 六个条目类型

| 条目            | entryType  | 作用域             | 说明                          |
| --------------- | ---------- | ------------------ | ----------------------------- |
| 宏 macro        | `macro`    | 输入+输出          | Eta 模板动态求值              |
| 正则 regex      | `regex`    | 输入 / 输出 / 两者 | 查找替换                      |
| 脚本 script     | `script`   | 渲染               | 注入 iframe 的 JS / importmap |
| 样式 style      | `style`    | 渲染               | 注入 iframe 的 CSS            |
| 世界书 lorebook | `lorebook` | 输入               | 条件匹配的知识注入            |
| 工具 tool       | `tool`     | 输入+输出          | 暴露给 LLM 的函数调用         |

注册位置：`src/presets/<type>/client/index.tsx` 的 default 导出里
向 `presets.tabs.register(...)` 注册各自的编辑 Tab。

> 准确地说，`src/presets/client/index.tsx` 只注册了 `styles` / `scripts` /
> `regexes` / `macros` 四个 Tab；`lorebook` 的 Tab 由 `src/lorebooks/client/index.tsx` 注册，
> `tool` 的 Tab 由 `src/tools/client/index.tsx` 注册 ——
> **因为它们实际住在 `lorebooks/` 与 `tools/` 模块里**，不在 `presets/` 下。

### ⭐ 六种条目的重复（去重）机制各不相同

这是多预设叠加时最容易踩的地方，作者在 04 篇末尾专门批注过，这里整理成表：

| 条目 | 去重键 | 叠加行为 |
| --- | --- | --- |
| 世界书 lorebook | **预设 id + code** | 跨预设不同预设不会互相覆盖；同一预设内 code 相同即同一条 |
| 正则 regex | **不去重** | 全部按 `sorter`（= `name`）顺序依次 `replace` |
| 脚本 script | **code** | `code` 相同则只注入一次（用 `sct-${code}` 做 DOM id 去重） |
| 样式 style | **code** | 同脚本（样式也走 script 注入通道） |
| 宏 macro | **code × key** | 最复杂：相同 `code` + 不同 `key` 共享禁用状态；不同 `code` + 相同 `key` 是正常情况；相同 `code` + 相同 `key` 会追加并共享 |
| 工具 tool | **工具名（`ToolItem.name`）** | 后注册的同名工具**覆盖**前一个（`cache.tools[name] = ...`） |

> 所以在多预设叠加时：**正则会重复执行、工具会被覆盖、脚本按 code 去重、
> 世界书按 `预设id-code` 区分、宏按 `code`+`key` 组合判定**。
> 调试「为什么这条没生效 / 为什么执行了两遍」时，先回这张表。

## 2. 宏（Macro）—— 动态模板求值

```ts
// src/presets/macros/index.ts
export interface Macro {
  code: string; // 去重用标识
  key: string; // 变量名（同类 key 共享一个"单选组"）
  value?: string;
  json: boolean; // value 是否按 JSON 解析
  multiple: boolean; // 是否复选（可多选）
  hidden: boolean;
}
```

### 求值引擎：Eta

宏的底层是 **Eta** 模板引擎（`eta/core`）：

```ts
// src/presets/macros/client/realm.ts
const eta = new Eta({ autoTrim: false, rmWhitespace: false });
```

所以宏值里可以写 `<%= 表达式 %>`，能访问的上下文是：

```ts
const obj = {
  ...variables, // 所有宏 key → 值
  ...(properties?.args ?? {}), // 本次调用的参数
  variables: realms.variables(history, false), // 故事当前变量
};
const generate = async (str: string) => eta.renderStringAsync(str, obj);
converts.push(generate); // ← 注册成一个"转化器"
```

### 合并规则的三种情况

这是宏系统里最需要理解的逻辑：

```ts
let json: any = null;
const texts: string[] = [];
for (const item of entries) {
  if (item.json) json = jsonUtils.merge(json, item.content);
  else texts.push(item.content);
}
const text = arrUtils.join(texts, '');
variables[key] = json
  ? {
      ...json,
      toString() {
        return text;
      },
    } // ← 技巧：对象也能当字符串插值
  : text;
```

三条规则：

1. **有 JSON 宏** → 合并所有 JSON，并把纯文本拼到 `toString()` 上。
   这样 `<%= key.某字段 %>` 能取字段，`<%= key %>` 能取文本。
2. **全是字符串** → 直接拼接作为值。
3. 单选（`multiple: false`）时，`singles[select]` 会被 `unshift` 到最前。

### 复选与单选的复杂规则

源码注释（`src/presets/macros/client/realm.ts:114-123`）写得很清楚：

```
复选的规则很复杂，
1，相同的code，不同的key共享一个禁用
2，不同的code，相同的key是正常情况
3，相同的code，相同的key，会追加且共享
这是为多preset设计的，可以继承，共享
```

单选则简单：`key` 下只会选中一个 `code`，后面的覆盖前面的。

选择状态存在 `realm.properties` 里（`selections` / `checkItems`），
由 `macros.property(realm)` 取得。

### 注册为双向处理器

```ts
export const processer: Processer = {
  id: main.name,
  requires: [regexMain.name], // ⭐ 依赖正则：正则先跑，宏再求值
  init,
  prompt: apply, // 输入方向
};

export const renderer: Renderer = {
  id: main.name,
  requires: [regexMain.name],
  init,
  output: apply, // 输出方向
  stream: apply,
};
```

同一个 `apply` 同时挂在 processer（发送给模型前）和 renderer（渲染到页面前），
**所以宏对输入和输出都生效**。

## 3. 正则（Regex）—— 静态查找替换

```ts
// src/presets/regexes/index.ts
export interface Regex {
  pattern: string;
  replacement: string;
  target: string; // 'input' | 'output' | 'both'
}
```

实现非常直接：

```ts
// src/presets/regexes/client/realm.ts
const generate: ConvertContent = async (text, { role }) => {
  if (role === 'tool') return text; // 工具调用内容不转化
  if (!text || text == '') return '';
  for (const { pattern, replacement } of cache.regexes) {
    text = text.replace(pattern, replacement);
  }
  return text;
};
converts.push(generate);
```

### 正则的 target 作用域（已修复）

`processer` 与 `renderer` **各自调用一次 `init`，但传入的作用域不同**：

```ts
// src/presets/regexes/client/realm.ts
async function init({ realm }: { realm: Realm }, t: string) {
  const cache: RegexCache = { regexes: [] };
  await utils.forEachItemsList<PresetItem<Regex>, Preset>(
    realm.presets, regexes.plural,
    async (entry) => {
      const { disabled, target } = entry;
      if (disabled) return;
      if (target == 'both' || target == t) {   // ← 与传入的作用域比较
        cache.regexes.push(entry);
      }
    },
  );
  return cache;
}

export const processer: Processer = {
  id: regexes.name,
  init: (ctx) => init(ctx, 'input'),   // ⭐ 输入方向只收 input / both
  prompt: apply,
};

export const renderer: Renderer = {
  id: regexes.name,
  init: (ctx) => init(ctx, 'output'),  // ⭐ 输出方向只收 output / both
  output: apply,
  stream: apply,
};
```

> ✅ **旧笔记的「疑似 bug」已结案。**
> `1.3.2.8` 时 `init` 只挑 `input` / `both`，但同一份 cache 被 processer 与
> renderer 共用，于是标 `input` 的正则也会作用于**输出渲染**。
> 作者当年批注「这是个 bug，输入输出的作用域不同，所以初始化时需要加参数」，
> 现在正是这么修的：**`init` 多了第二个参数 `t`，两个方向各建一份 cache**。

### 正则的另外两个特性（仍然成立）

1. 用的是 `String.prototype.replace(pattern, replacement)` 的**字符串形式**，
   没有 `new RegExp()`，也没有解析 `/.../g` 标志的逻辑 ——
   所以要写 `"a"`、`"a"` 这样的字面量模式，**不要写成 `/a/g`**。
2. `criteria` 里的 `sorter` 是 `${match}${code}${name}`（世界书）或 `name`（正则），
   **正则的应用顺序由条目名称字符串决定**，不是列表里的视觉顺序。

### ConvertContent 链

这是全项目的文本变换机制 —— **一个函数数组，依次串联**：

```ts
export type ConvertContent = (
  text: string,
  ctx: ConvertContext,
) => Promise<string>;

async function convert(
  converts: ConvertContent[],
  text: string,
  ctx: ConvertContext,
) {
  let res = text;
  for (const convert of converts) res = await convert(res, ctx);
  return res.trim();
}
```

正则、宏都只是往这个链上 `push` 一个函数。**顺序由 `requires` 决定**：
`regexes` 先注册（无依赖），`macros` 依赖 `regexes` 故排在其后。

### 宏 vs 正则（官方 Q&A）

> 宏可以进行动态的计算和替换，同时替换输出和输入，但只能按表达式进行匹配。
> 正则的匹配能力更强，可以单独替换输出或输入，但只能替换为相对固定的内容。

## 4. 脚本与样式 —— 注入 iframe

```ts
// src/presets/scripts/index.ts
export interface Script {
  code: string;
  content?: string;
  priority: number; // 默认 100，越小越先
  type: string;     // 'application/javascript' | 'link' | 'importmap' | ...
}

// src/presets/styles/index.ts —— 结构逐字相同，只有默认 type 不同
export interface Style {
  code: string;
  content?: string;
  priority: number;
  type: string;     // 默认 'text/css'
}
```

两者的默认值：

| 条目 | `defaultEntry` |
| --- | --- |
| `Script` | `{ code: '', content: '', priority: 100, type: 'application/javascript' }` |
| `Style` | `{ code: '', content: '', priority: 100, type: 'text/css' }` |

> ✅ **旧笔记的「疑似复制粘贴遗留」已结案。**
> `1.3.2.8` 时 `Script.defaultEntry.type` 是 `'text/css'`（与文档不符），
> 现在已改为 `application/javascript`。
> 两个接口的字段依然**逐字相同**，差别只在默认 `type`。

⚠️ **但它们其实是两条独立的注入通道**（旧笔记说「样式作为 script 的一种 type」是错的）：

| | 脚本 `scripts` | 样式 `styles` |
| --- | --- | --- |
| 文件 | `src/presets/scripts/client/realm.ts` | `src/presets/styles/client/realm.ts` |
| DOM 前缀 | `sct-${code}` | `stl-${code}` |
| 一次性标志 | `window.__injectedScriptInitialized` | `window.__injectedStyleInitialized` |
| 元素 | `<script>`（`type` 为 `link` 时用 `src`） | `<style>`（`type` 为 `link` 时用 `<link rel=stylesheet>`） |
| 挂载点 | `document.body` | `document.head` |
| 特殊处理 | `importmap` 单独先插、合并成一张映射表 | 无 |

两者都做 **`code` 去重 + `priority` 升序**，但它们各自持有自己的 `Set` 与标志位，
所以**同一个 `code` 在脚本与样式里互不影响**。

### 脚本注入的实现

`src/presets/scripts/client/realm.ts` 是一个 `Renderer`：

```ts
const prefix = 'sct';

export const renderer: Renderer = {
  id: scripts.name,
  init: async ({ realm }) => {
    // 收集所有预设的脚本条目，type='importmap' 的合并成一张 importMap
    // 其余按 priority 升序排列
    cache.entries.sort((a, b) => a.priority - b.priority);
    cache.importMap = JSON.stringify(map);
    return cache;
  },
  output: async ({}, cache) => {
    const { contentWindow, contentDocument: document } = realms.iframe;
    const window = contentWindow as any;
    if (!window.__injectedScriptInitialized && document) {
      // ← 只注入一次
      window.__injectedScriptInitialized = true;
      // 1. 先插 importmap（若存在）
      // 2. 再按顺序插入各脚本
    }
  },
};
```

注入细节：

- **importmap** 必须**先于**任何 module script 插入，否则模块解析不到裸导入。
- `type === 'link'` 时用 `<script src>` 并 `await onload`，
  以此保证「按 priority 顺序依次加载」；内联脚本则同步执行（`async = false`）。
- 用 `set` 去重（`id = sct-<code>`），并从 iframe 的 `window`
  上用 `__injectedScriptInitialized` 标记防止重复注入。
- 内容用 `document.createElement('script')` + `textContent` 写入，
  **不是** `eval`，但效果等价于在 iframe 内执行任意 JS。

### iframe 与主应用的通信

iframe 是渲染沙箱，主应用通过 `postMessage` 单向推送数据：

```ts
// src/stories/client/realms/index.ts
function postMessage(type: string, data: any) {
  const window = realms.iframe?.contentWindow;
  const g = window as { __messageData?: Record<string, any> };
  g.__messageData ??= new Map<string, any>();
  g.__messageData[type] = data; // ← 同时挂到 window 上供脚本同步读取
  window.postMessage({ type }, '*');
}
```

推送三类数据：

| type               | 内容                                                  |
| ------------------ | ----------------------------------------------------- |
| `variables`        | 当前变量快照                                          |
| `content`          | `{ inputs, output, thought }` 三段已转化的文本        |
| （由脚本自行监听） | 脚本可 `window.addEventListener('message', ...)` 接收 |

### 脚本可以反向影响输入

这是很巧妙的一处设计：主应用在 iframe 的 window 上暴露 `userInput` 接口，
预设脚本可以注册 `inputBuilders` 来改写用户输入：

```ts
// src/stories/client/realms/page.tsx（UserInput 组件）
window.userInput = {
  text: {
    element: () => inputRef.current,
    get: () => content,
    set: (v) => setContent(v),
  },
  summary: { get: () => summary, set: (v) => setSummary(v) },
  inputBuilders: [], // { id, sequence?, build: (text: string) => string }
};
```

生成时按 `sequence` 排序后依次应用：

```ts
// src/stories/client/realms/index.ts（generate 中）
window?.userInput?.inputBuilders
  ?.sort((a, b) => (a.sequence ?? 0) - (b.sequence ?? 0))
  .forEach((builder) => {
    input = builder.build(input);
  });
```

所以预设脚本可以拦截/预处理玩家输入（例如自动补全指令、解析自定义语法）。

## 6. 导入导出

预设的导入导出是 **ZIP 归档**，由 `archive` 工具统一处理。

### 归档抽象

```ts
// src/utils/archive.ts
export interface ArchiveFile {
  type: 'file';
  name: string;
  content: () => Promise<Buffer | undefined>;
}
export interface ArchiveFolder {
  type: 'folder';
  name: string;
  nodes: Record<string, ArchiveNode>;
}
export type ArchiveNode = ArchiveFile | ArchiveFolder;
export interface Archive {
  name: string;
  nodes: Record<string, ArchiveNode>;
}
```

`archive.set.{buffer,text,json}` 写入，`archive.get.{buffer,text,fuzzy,json}` 读出，
`archiveToZip` / `zipToArchive` 在 JSZip 与树结构间转换（DEFLATE level 6；
`level === 0` 用 STORE；只收 `root/` 前缀的条目）。

三个实现细节（都在 `src/utils/archive.ts`）：

- **空内容不写进 zip**：`appendNode` 里有 `if (content?.length)`，
  而 `set.text` / `set.json` 对空字符串会传 `undefined`。
  所以「空白文件不会出现在包里」是刻意的（省空间，也避免干扰外部检阅）。
- `zipToArchive` 是**惰性读**：`content()` 首次调用才 `entry.async('nodebuffer')`，
  并用闭包变量缓存 Promise（`buffer ??= ...`）。
- `get.fuzzy` 是 `Object.keys(nodes).find(u => u.startsWith(prefix))` ——
  **返回第一个命中的**，不是全部。前缀有歧义时会静默取错文件。

### 每个条目类型自定义归档格式

`src/presets/server/factory.ts` 的 `storages.create` 接收两个归档钩子。
以世界书为例：

```ts
// src/lorebooks/server/storage.ts
export const storage = storages.create<Lorebook>(
  lorebooks,
  ({ name, data: { code, match } }) => ({
    sorter: `${match}${code}${name}`,
    filter: `${match}${code}${name}`,
  }),
  // loadArchive：写进 zip
  async (nodes, item, s) => {
    const name = `${item.code}-${s}`;
    const ext = lorebooks.typeToExt(item.type); // json/plaintext/markdown/yaml/xml → 扩展名
    archive.set.json(nodes, `${name}.meta.json`, {
      ...item,
      content: undefined,
    });
    archive.set.text(nodes, `${name}.content.${ext}`, item.content);
  },
  // saveArchive：从 zip 读回
  async (nodes, name) => {
    const item = await archive.get.json<PresetItem<Lorebook>>(
      nodes,
      `${name}.meta.json`,
    );
    if (item) item.content = await archive.get.fuzzy(nodes, `${name}.content.`);
    return item;
  },
);
```

要点：

- **元数据与内容分文件**：`<code>-<seq>.meta.json` + `<code>-<seq>.content.<ext>`。
  好处是文本内容以真实扩展名保存，便于外部编辑与阅读。
- 文件名里的 `sequence` 就是数组下标（**不是**数据库 `entryId`），
  源码注释特别提醒「请保证左右文件名前缀一致」。
- 读回时用 `archive.get.fuzzy(nodes, '前缀')` 做前缀匹配，
  这样不用关心内容文件的具体扩展名。
- `lorebooks.compare` / `sequence()` 决定排序，使导出顺序稳定。

### 预设级导出

`src/presets/server/api.ts` 提供 `presets/[id]/export` 与 `presets/import`，
配合 `apps` 层的 `open(...)` 触发浏览器下载。

导出时会**沿依赖闭包一起打包**（`repository.traversal(ctx, [id], { entities: true })`，
`ctx.action` 里逐个 `storage.load()`），所以一个预设包可能含多个预设目录。
下载文件名是 `preset_${source.at(-1)?.name}.zip` —— `at(-1)` 正是
「依赖在前、使用者在后」的那个**最上层预设**。

### 归档目录长这样（真实模板）

`docs/templates/root/` 是一个解开的存档示例，可以当格式参考：

```
root/
├── <预设名>/
│   ├── meta.json                Preset 本体（entries / variables / opening 已被剔除）
│   ├── variables.json           初始变量
│   ├── opening.txt              开场白
│   ├── cover.png                封面（level 0，不压缩）
│   ├── lorebooks/               <code>-<下标>.meta.json + .content.<ext>
│   ├── macros/                  <code>-<下标>.meta.json + .value.txt
│   ├── regexes/  scripts/  styles/  tools/    同构
│   └── ...
├── model/                       模型配置（存档也带模型）
└── comfyui/                     工作流 + 模型登记
```

所以**一个存档 = 多个预设 + 工作区（模型 / ComfyUI）**，
`example.zip` 就是整个 `root/` 的压缩包。

### SillyTavern 兼容

由**外部插件** `secyud-tavern-importer` 提供，走
`plugins/secyud-tavern-importer/server/silly-tavern.ts`，
接口挂在 `/api/silly-tavern/import`。目前只能导入文字描述类内容，
**不能复刻脚本**，需要自行调整。

## 7. 条目如何进入生成流程

所有条目类型都通过 `forEachItemsList` 跨预设扁平遍历：

```ts
await utils.forEachItemsList<PresetItem<Macro>, Preset>(
  realm.presets,          // ← 一个 Realm 可挂多个 Preset
  macros.plural,          // 'macros'，即 model.entries['macros']
  async (entry, model) => { ... },
);
```

然后各自注册到流程里：

| 条目   | 注册方式                                                             |
| ------ | -------------------------------------------------------------------- |
| 正则   | `processer.prompt` + `renderer.{output,stream}` → 向 `converts` push |
| 宏     | 同上 → 向 `converts` push                                            |
| 世界书 | `processer.prompt` → 向 `ctx.injects` push 一个注入器                |
| 工具   | `processer.init` → 建缓存；`processer.output` → 执行工具调用         |
| 脚本   | `renderer.output` → 注入 iframe                                      |
| 样式   | 同脚本（作为 script 的一种 type）                                    |

## 8. 本章速查

- 想改 AI 看到的内容？写**正则**（静态）或**宏**（动态表达式）。
- 想改玩家看到的界面？写**样式** + **脚本**，数据通过 `postMessage` 到达。
- 想让 AI 按条件知道设定？写**世界书**（见第 05 章）。
- 想让 AI 能做事？写**工具**（见第 09 章）。
- 想预置初始变量？写预设的 `variables` 字段（多个预设会**深度合并**）。
- 调试提示：预设条目都是跨预设扁平遍历的，多预设叠加时注意 `code` 冲突与优先级
  —— **每种条目的重复机制不一样，回看 §1 的那张表**。

> laotu：这里有必要提一嘴，每种entry的重复机制不一样，如世界书是预设id+code去重
> 正则不去重，脚本，样式按code去重，最复杂的就是宏，code和key结合判定
