# 01 · 学习地图

这一篇不描述项目，只回答一个问题：**这里有哪些做法可以搬走用**。

每条给三样东西：好在哪、代价是什么、什么时候不该用。
源码位置都标了，方便回去核对。

与相邻篇目的分工：本篇是**工具**，
[17 架构决策](./17-架构决策.md) 是读码感想，[18 项目评价](./18-项目评价.md) 是评价。

---

## 一、契约与顺序

### 1. 契约压到三个字段

`Manifest` 只要 `{ id, client, server }`（`src/plugins/registry.ts`），
其余全靠约定：`client/index.tsx` 的 **default 导出就是注册函数**。

大多数插件系统是配置驱动的 —— 中心文件里声明、填元数据、实现一长串接口。
字段越少，出错越少，新增模块的成本也越低。

**代价**：约定没有类型约束，写错只能运行时才发现。所以需要配套下一条。

### 2. 顺序靠声明推导

`Registry.sortByRequires()` 用 Kahn 算法拓扑排序，`sequence` 做同级粗排：

```ts
const processer: Processer = {
  id: main.name,
  requires: [regexMain.name],   // 顺序自动推导
};
```

依赖不存在或成环**直接抛错**，不静默跳过。
比「在文档里写清谁先谁后」可靠得多 —— 顺序错导致的 bug 极难排查。

**可以直接抄的小技巧**：想表达「最后执行」，不必把别人往后排，给个极大值就行：

```jsonc
// src/tasks/manifest.json
{ "id": "task", "sequence": 99999 }
```

同理 `interceptors` 用 `-1000` 抢在最先。

**边界**：拓扑排序只解决偏序。同级规则一旦复杂到需要按优先级插队，
FIFO 队列就不够了，得换优先队列。

### 3. 代码生成让路径变成类型

`scripts/operations/api.ts` 读各模块 `server/api.ts`，找出方法键，生成真实路由，
以及**前端可用的路径字符串联合类型**：

```ts
const get = ['models', 'models/{id}', 'presets', ...] as const;
export type GetPath = typeof get[number];
```

于是 `get('presets/{id}')` 路径拼错**编译不过**。
手写 REST 路径几乎必然拼错，且只能运行时发现。

**顺手记一个细节**：写的时候用 `[id]`（Next 动态段），生成给前端时
`replaceAll('[', '{')`。两种括号各服务一个消费者，一行转换就接上。

**代价**：改 manifest 或 api 结构后必须重跑 `pnpm prepare`，无法热更新。
换来的是完整的原生 Next.js 调试体验。

## 二、抽象与复用

### 4. 等第二个用户出现再抽

`TaskRunner`（`src/tasks/index.ts`）最初为后台长任务写：
并发上限、队列、状态机、取消、重试。

后来 `src/tools/client/task.ts` **直接继承它**做工具并发调用。
两个子类的差异只有两处：结果去哪（两张表 / 写回 `toolcall.result`）、
谁来等（不需要 / 自己实现 `wait()`）。队列、锁、状态机、重试全部复用。

**可迁移的判断**：不要一开始就设计通用框架，那通常为了通用而牺牲具体。
等第二个真实用户出现，你才知道哪些是共性。

### 5. 同名的是「同一个域的两面」

`model-engine`、`tool-provider`、`comfyui-model-importer`
在 `client/` 与 `server/` 各有一个注册表，名字相同。

这不是重名，是一个业务域在两侧的实现：客户端管**界面与交互**
（`configComponent` / `configureObject`），服务端管**执行与数据**
（`generate` / `download`）。名字标识**域**，不是实现。

**可迁移的判断**：发现某东西前后端各有一半，先问「是不是同一个域」。
是就让它同名；不是，**那是名字起错了**。
本项目里服务端 `ToolProvider` 只有归档钩子，就属于合不成一个域的情况。

### 6. 单表多态换灵活性

预设六种条目共用一张表（`src/database/server/factory.ts`）：

```ts
schemas.entry(name, ref, extraColumns)
//   复合主键 (masterId, entryType, entryId) + data JSON 列
```

加条目类型不用改表结构，通用 CRUD 完全复用，归档逻辑也统一。

**代价**：失去列级约束与类型检查。之所以成立，是因为条目字段本就是
用户可编辑的自由内容，本来也不需要数据库约束。

**边界**：字段需要被查询、聚合、或有强一致性要求时，它就会变成负担。
适用范围是「内容型数据」。

### 7. 冗余列替代 JSON 索引

每行 entry 有两个冗余列，由各模块的 `criteria()` 自己算：

```ts
criteria: ({ name, data: { type } }) => ({
  sorter: `${type}${name}`,
  filter: `${type}${name}`,
})
```

内容在 JSON 列里，但用户要按名称搜索、按类型排序。
把检索要用的键预先拼成字符串列，普通 `LIKE` 与 `ORDER BY` 就够了，
不必引入 JSON 函数或迁移。

**可迁移**：写时多算一点，读时省很多。任何用 JSON 列存内容的系统都能用。

**代价**：派生数据，业务逻辑改了要记得同步；算错不报错，只会静默排序不对。
只适合**稳定**的检索维度。

## 三、数据与状态

### 8. 用增量 + 回放替代快照 + 回滚

每条消息挂补丁数组而非完整快照（`src/stories/realms.ts`）：

```ts
export interface RealmMessage {
  content: string;
  variables: Operation[];   // 补丁序列
}
```

回放函数只有一个布尔参数：

```ts
function variables(history: RealmHistory, output: boolean = true) {
  const variables = structuredClone(history.variables);
  for (const input of history.prompts) patch(variables, input.variables);
  if (output) { /* 再回放选中输出的补丁 */ }
  return variables;
}
```

**一个布尔值切换了时间点**。于是「切换到任意历史输出，变量回到那一刻」
这个交互**不需要任何状态管理代码** —— 数据模型层面就已经成立。

**代价**：每次读取都要回放，读多写少才划算；补丁语义要自己定义。

### 9. 多维数组承载两个正交需求

```ts
// src/models/client/processer.ts
history.outputs.push(outputs);   // 每次生成追加一组
```

`outputs` 是二维数组：外层是「第几次生成」（版本），
内层是「一轮因工具调用拆成的多段」。

一个结构同时解决了**版本管理**与**工具循环**。
用户能来回翻看历史版本，「切换输出改变上下文」也自然成立。

**可迁移**：一个数据结构能同时承载两个正交需求，通常比两套机制更省。

### 10. 单线程下用简单锁就够

```ts
// src/utils/mutex.ts
export class Mutex {
  queue: Action[] = [];
  lock(action) { /* 入队；空闲则启动驱动循环 */ }
}
```

注释写明「适用于单线程」—— 它保护的是 `await` 之间的**交错**，不是真并发。
对保护内存中的队列/Map 完全够用。

一个值得记的性质：**一个 action 抛错只 reject 它自己，不卡住后面的**。

**可迁移**：不要因为「需要并发安全」就上重型方案。
先问要保护的是真并行还是 `await` 交错 —— 后者几十行就够。

### 11. 同名的工具函数要显式写清约定

```ts
// merge: 左值是累加器，原地修改；右值是外部数据，永不被改
merge(lft, rht) → T
```

「左值是调用方自己的对象」这个前提不写下来，后面的人一定当成 bug。
作者后来把它列进了 `CONTRIBUTING.md` 的「易被误读的契约」。

**可迁移**：函数正确性依赖「调用方怎么用它」时，把前提写进注释与文档。

## 四、交互与协议

### 12. 复用已有通道，别加新概念

世界书和记忆要往上下文塞文本。直觉做法是加一种消息类型
（`role: 'knowledge'`）。实际做法是**伪造一次工具调用**
（`src/lorebooks/client/realm.ts`）：

```ts
caller('', null, [{
  name: models.engines.knowledge.info.name,      // 'get_knowledge'
  arguments: models.engines.knowledge.args({ type: 'lorebook' }),
  result: content,
}]);
```

三层好处：引擎层零改动；天然兼容所有供应商；动机可读
（那句 `description: 'return empty if current knowledge is injected'`
是在用自然语言提示模型别重复调用）。

**可迁移**：找到已有抽象的正确用法，比加一层新抽象难，但收益大得多。

### 13. 用 Promise 表达「等一个未来值」

`ask_user` 让 AI 中途停下来问用户，实现出奇地短
（`src/tools/elicits/client/tool.tsx`）：

```ts
invoke({ args: item }) {
  return new Promise<string>((resolve) => {
    const state = useElicitState.getState();
    state.push({ ...item, reply: async (answer) => resolve(answer) });
  });
}
```

返回一个**永不主动 resolve 的 Promise**，把 `resolve` 交给 UI。
生成流程自然挂起，不需要在管线里加任何「暂停/恢复」概念。

**代价**：这条 Promise 没有取消路径（见 [09 篇](./09-工具与记忆.md) §4）。

### 14. 只实现你需要的那部分协议

`sseUtils`（`src/signal/index.ts`）没引库，两个函数就够：
`pack` 逐条写成 `data: <json>\n\n`，`read` 按 `\n\n` 切事件。

`read` 里两处细节值得学：

* 只在 `done` 时才把最后一段**未闭合**的 buffer 当事件
  （`allEvents.slice(0, -1)`）—— 避免半个 JSON 被提前解析。
* 多个 `data:` 行用 `\n` 拼回一个字符串再解析，兼容规范的多行写法。

**可迁移**：协议实现不必完整，想清楚只需要哪些部分，还省一个依赖。

### 15. 网络边界传实体，不传 id

```ts
// src/stories/server/api.ts
realm: {
  POST: route(async (request) => {
    const story = await request.json();        // 整个 Story
    const realms = await stories.repository.getRealm(story);
  }),
}
```

因为前端可能拿着**尚未落库或刚改过没保存**的 Story 去预览。
用 id 就会读到库里的旧版本。

**可迁移**：客户端状态可能领先于服务端时（预览、试算、草稿），传实体更正确。

### 16. 取消与重试是两个层级

生成管线的重试里，外部取消与本轮请求是不同生命周期的信号
（`src/models/client/processer.ts`）：

```ts
// 外层：用户取消，跨多轮，只绑一次
signals.setAbort(signal, () => { iteration = 0; });

while (iteration > 0) {
  while (retry > 0) {
    const { controller, destroy } = signals.createSub(signal);  // 每轮一个
    try { /* 请求 + 流式读取 */ }
    finally { finished = true; destroy(); }   // 必须手动销毁
  }
}
```

配套两点：

* **卡死检测**：流式超过 `interval` 秒没有新 chunk 就中断，被 catch 识别为「重试」。
* **判据用 `err.message === 'retry'`** 而不是 `AbortSignal.reason` ——
  `reason` 在不同运行时/不同 fetch 实现下抛出的形态不一致，`message` 是稳定的。

**边界**：`createSub` 挂的是手写监听器，不像 `setAbort` 那样自析构，
漏掉 `destroy()` 就是泄漏。

## 五、工程习惯

### 17. 兜底放在代码里，不放在 UI 约束里

重试次数设为 0 时，旧实现会让这次生成**一个请求都不发**，外层循环照跑 20 轮。
修复是两层：代码 `Math.max(maxRetry, 1)` + UI `min={1}`。

**可迁移**：UI 的 `min` 只在「有值」时生效，清空输入框得到 `NaN`，拦不住。
凡「非法值后果严重」的参数，代码里要有兜底。

> ⚠️ 这条修复其实**不完整**：`Math.max(NaN, 1)` 仍是 `NaN`，
> 所以 `NaN` 通道依然存在（见 [08 篇](./08-生成管线.md) §10）。
> 兜底要想清楚兜的是哪个非法值。

### 18. 注释记「为什么」，并允许承认不知道

```ts
/**
 * 复选的规则很复杂，
 * 1，相同的code，不同的key共享一个禁用
 * 2，不同的code，相同的key是正常情况
 * 3，相同的code，相同的key，会追加且共享
 */
```

更难得的是这种：

```tsx
{/* key不要删除。发布后，如果没有这个key，会导致引用有问题，原因不明，开发环境无此问题。 */}
```

作者明确承认「原因不明」。这比编一个听起来合理的解释有用得多：
后来者知道这里不能动，也知道作者没搞懂。

```ts
// 偷懒，deepseek的思考直接放这里了
```

**可迁移**：写下「为什么」和「我也不确定」，成本极低、回报极高。
代码会被反复读，但作者只会解释一次。

### 19. 测试只记录现象，不固化推断

`tests/GUIDELINES.md` 的约定：不确定的行为**不要**写成 `it.fails` 或断言，
先描述现象再问。

`tests/TODO.md` 更进一步，逐条区分证据强度：已实测复现 / 已写断言的现状 /
纯读码推断，并标注「有意保留」。

**可迁移**：测试套件最大的风险不是覆盖不足，
而是**把 bug 固化成预期行为**。
加一句「这条记录的是现状，不是期望」就能避免误导。

### 20. 判断权交给用户，不替用户拍板

> 用户是最终判断者。凡是「预期行为」和「应对方式」需要人来定的地方，
> 先问，不要自己拍板。

并列出必须问的场景：某行为算不算缺陷、硬修还是软处理、要不要改 `src/**`、
任何 git 操作。

**可迁移**：让 AI 或协作者参与开发时，最贵的错误不是写错代码，
而是方向不一致导致白做。把「哪些必须问」写成清单，比事后返工便宜。

## 六、刻意不做的

理解「为什么不」比抄「怎么做」更重要。

### 21. 不给 iframe 加 sandbox

定位是自部署的个人应用，部署者即管理员，不存在多租户边界。
预设执行用户自己的 JS/CSS 是核心能力，不是漏洞。
`CONTRIBUTING.md` 明确写了不要提「移除这项能力」式的加固 PR。

**可迁移**：评价安全设计必须先确定**威胁模型**。
脱离「谁在用、谁能被攻击」谈危不危险没有意义。

### 22. 不做通用滑动窗口

角色扮演的上下文价值密度与顺序强相关，通用滑动窗口会切掉关键设定。
所以不做自动裁剪，而用「总结段落」让用户自己决定截断点：

```ts
if (history.summary) break;   // 遇到总结段停止回溯
```

**可迁移**：搬通用机制前，先确认你的场景符合同一个假设。
「agent 都这么做」不是理由。

### 23. 不为两个取值建注册表

`model.builder` 有 `default` 与 `layered`，后者是试验性分支。
作者的态度是「一般就用 default，如果有必要，后续会改成注册机制」。

**可迁移**：等第三个真实需求出现再抽象（对照第 4 条）。

## 七、如果只带走五条

25 条里如果只记五条，选这些 —— 最通用，也最难自己想到：

1. **顺序靠声明推导**（第 2 条）——
   `requires` + 拓扑排序，比文档里写「注意先后」可靠一个数量级。
2. **复用已有通道，别加新概念**（第 12 条）—— 世界书伪装成工具调用。
3. **让数据结构承载语义**（第 8、9 条）—— JSON Patch 让「翻页改变上下文」自然成立。
4. **等第二个用户出现再抽**（第 4、23 条）——
   `TaskRunner` 被复用时，边界一眼就看清了。
5. **把前提和不确定写下来**（第 11、18、19 条）——
   注释里的「原因不明」、契约里的「左值是累加器」、测试里的「这条记录现状」。
   **前提被写下来的地方，误判就停止了。**

这五条有个共同点：都不是某个具体技术，而是**关于如何选择技术的方法**。
具体技术会过时，方法不会。
