# 09 · 工具与记忆

工具让 LLM 能「做事」，记忆让 LLM 能「记住」。
两者最终都通过**工具调用通道**参与生成流程。

> 📌 本篇已按 `1.3.5.0` 复核，**改动很大**：
> 内建 provider 从 4 个变成 **5 个**（新增 `elicits` 的 `ask_user`，
> 让 AI 能中途反问用户）；工具调用从**串行改为并行**（`tools/client/task.ts`）；
> `ToolItem.invoke` 的签名从 `(args) => string` 变成 `(ctx: CallContext) => string`；
> RAG 重构为**可插拔 embedder + IndexedDB 向量缓存**，旧笔记里
> 「每次生成全量重建、不持久化」的性能警告**已经解决**。

---

## 1. 工具数据模型

```ts
// src/tools/index.ts
export interface Tool<T = any> {
  type: string;      // provider 名，决定由哪个 provider 创建
  macro?: string;    // ⚠️ 是 string（宏的 code），不是 boolean
  config: T;
}

export interface ToolCall {
  index: number;     // 调用索引
  id: string;        // 调用 id
  name: string;      // 工具名
  arguments: string; // 参数（JSON 字符串）
  result?: string;   // 执行结果
}

const defaultValue: Tool = { type: 'variable', config: {} };
```

> ⚠️ **`Tool.macro` 的类型是 `string` 而不是 `boolean`**。
> 注释写的是「绑定同名宏，宏的状态会和工具同步」，
> 但实际用法是**填宏的 `code`**（见下面的 getter/setter 实现）——
> 源码注释里的「同名」是过时说法。旧笔记把它记成 `boolean` 也是错的。

工具**没有独立表** —— 它是预设条目（`entryType = 'tool'`），
持久化走 preset 的 entry 机制，导出走 `storages.create`。

启用状态存在 **realm properties** 而非数据库列：

```ts
export interface ToolProperty {
  items: Record<string, boolean>;
}
```

源码注释说明「因为一开始都是勾选的，直接存 disabled」。

## 2. 双层 Provider（一个域，两个运行时半边）

| 层     | 文件                            | 注册表名        | 职责                                   |
| ------ | ------------------------------- | --------------- | -------------------------------------- |
| 客户端 | `src/tools/client/providers.ts` | `tool-provider` | **界面与交互**：配置 UI + 创建工具实例 |
| 服务端 | `src/tools/server/providers.ts` | `tool-provider` | **执行与数据**：导出/导入时的归档钩子  |

两侧同名是**规律而非陷阱**：一个域（"工具"）在浏览器与 Node 各有一套实现，
所以注册表名必然相同（判据见 [01 篇](./01-架构与模块系统.md) §2）。

> ⚠️ **但这一对是全项目唯一不吻合那条规律的。**
> 客户端半边有 `configComponent` / `configureObject` / `create`，
> 是标准的「配置 + 创建」组合；服务端半边却**只有归档钩子**
> （`loadArchive` / `saveArchive`），没有任何"提供工具"的语义 ——
> 它其实是「工具条目的导出格式」，与 `preset-storage` 是同一件事。
>
> 对比同模块的另外两对（`model-engine`、`comfyui-model-importer`），
> 两侧都是「客户端配置 UI + 服务端执行」的完整对应。
> **只有它合不成一个域**，所以这个名字是有缺口的：
> 更贴切的是 `tool-archive`，或把这两个钩子并进
> `preset-storage` 的归档体系（它本来就注册到 `presets.storage.registry`）。
>
> 我没有改源码，只在笔记里标注 —— 这属于「先开 Issue 讨论」的范畴。

### 服务端 Provider（归档）

`1.3.4.0` 前后它的签名从「多个位置参数」改成了**单一 context 对象**：

```ts

interface ToolArchiveContext<T = any> extends PresetArchiveContext {
  entry: PresetItem<Tool<T>>;
  name: string;
}

export interface ToolProvider<T = any> extends Registerable {
  loadArchive: (context: ToolArchiveContext<T>) => Promise<void>;
  saveArchive: (context: ToolArchiveContext<T>) => Promise<void>;

```

### 客户端 Provider

```ts
// src/tools/client/providers.ts
export interface CallContext<TArgs = any> {
  toolcall?: ToolCall;          // ⭐ 本次调用的原始记录
  args: TArgs;                  // 已 JSON.parse 的参数
  controller: AbortController;  // ⭐ 支持取消
}

export interface ToolItem<TArgs = any> {
  name: string;
  description: string;
  parameters: JsonSchema;       // 暴露给 LLM 的 JSON Schema
  invoke: (ctx: CallContext<TArgs>) => Promise<string>;   // ⭐ 收 ctx，不是裸 args
}

export interface ToolProvider<T = any> extends Registerable {
  configComponent?: React.ComponentType<ToolProps<T>>;
  configureObject?: (data: FormData, tool: Tool<T>) => Promise<void>;
  create: (entry: PresetItem<Tool<T>>, realm: Realm) => Promise<ToolItem[]>;
}
```

两点要注意：

- `invoke` 收的是 **`CallContext`**（`{ args, toolcall, controller }`），
  这是旧笔记里没有的。`controller` 让工具能响应「停止生成」，
  `toolcall` 让工具能读到自己被调用的原始 id/name。
- `configComponent` 的 props 是 **`ToolProps`**（`{ entry, formRef }`），
  不是裸的 `{ tool }` —— `formRef` 供 Monaco 之类的非受控组件回写表单用。
- `create` 返回**数组** —— 一个条目可以产出多个工具。

## 3. 工具的组装与执行

### init：建工具池

```ts
// src/tools/client/realm.ts —— 现在只剩 init
export const processer: Processer = {
  id: main.name,
  async init({ realm }) {
    const cache: ToolCache = { tools: {} };
    const { items } = tools.property(realm);
    const { checkItems } = macros.property(realm);
    await utils.forEachItemsList(realm.presets, tools.plural, async (entry) => {
      const { disabled, type, macro } = entry;
      if (!type) return;
      const provider = tools.providers.registry.record(type);
      if (!provider) {
        // 缺失只警告，不中断（⚠️ 注释与实现不一致，见下）
        console.warn(`[tool]: provider missing(${type})`);
        return;
      }
      try {
        const list = await provider.create(entry, realm);
        for (const tool of list) {
          const { name } = tool;
          cache.tools[name] = {
            ...tool,
            get disabled() {
              // ⭐ macro 是宏的 code
              return (macro ? checkItems[macro] : items[name]) ?? disabled;
            },
            set disabled(b: boolean) {
              if (macro) checkItems[macro] = b;
              else items[name] = b;
            },
          };
        }
      } catch (error) {
        throw new BusinessError(
          'tool create failed',
          'tool.create_failed',
          error,
        ).withValue('entry', entry.name);
      }
    });
    return cache;
  },
};
```

注意 `disabled` 用 getter/setter **直接读写 realm properties**，
所以 UI 勾选立即生效，无需重建缓存。

> ⚠️ **`console.warn` 那段的注释与实现不一致**：
> 注释写的是「工具未注册则报错中断，防止模型反复调用不存在的工具白耗 token」，
> 但代码实际是 `console.warn` + `return`（静默跳过）。
> 我倾向于认为注释是**当时想要的**、实现后来退回了宽松版
> （或者反过来）。这条在 [12 篇](./12-开发手册.md) 的踩坑清单里保留。
>
> 另外：`provider.create` 抛错时会**包成 `BusinessError` 并中断整个 init**，
> 也就是说**一个坏工具条目会让整个 Realm 打不开**。

### calling：并行执行工具调用（已重写）

> ⭐ 这是本篇相对旧笔记**最大的实现变化**。旧版 `calling` 是一个顺序 `for` 循环，
> 现在它是 `src/tools/client/task.ts` 里一个继承 `TaskRunner` 的并发池。

```ts
// src/tools/client/task.ts
class Manager extends TaskRunner<ToolCall> {
  constructor(
    protected cache: ToolCache,
    protected controller: AbortController,
  ) {
    super();
    // ⭐ 外部取消时，清空还没开始的任务
    signals.setAbort(controller.signal, () => { this.pending.length = 0; });
  }

  protected async execute(task: TaskInfo<ToolCall>) {
    const toolcall = task.args;
    const { setRealmInfo } = useRealmState.getState();
    try {
      const tool = this.cache.tools[toolcall.name];
      if (tool) {
        const args = JSON.parse(toolcall.arguments);
        setRealmInfo(toolcall.id, { title: 'tool.calling_tool', content: toolcall.name });
        toolcall.result = await tool.invoke({ args, toolcall, controller: this.controller });
      } else {
        toolcall.result = '';       // ⚠️ 找不到工具 → 空结果，不报错
      }
    } catch (err: any) {
      toolcall.result = `error: ${err?.message ?? 'unknown error'}`;
      console.error(err);
    } finally {
      setRealmInfo(toolcall.id);    // 清掉这条进度
    }
    return 'success';
  }
}

export async function calling(realm, controller, toolCalls?) {
  if (!toolCalls?.length) return;
  const cache: ToolCache = tools.cache(realm);
  const manager = new Manager(cache, controller!);

  setRealmInfo('main', { title: 'tool.calling_tool' });
  for (const toolCall of toolCalls.filter((u) => !u.result)) {
    await manager.create(toolCall.id, toolCall);   // 逐个入队
  }
  await manager.wait();                            // 等全部结束
}
```

关键设计：

- **并发上限来自 `TaskRunner` 的默认 `max = 8`**（`tools/client/task.ts`
  调用 `super()` 不传参，所以是 8，而服务端 `TaskManager` 显式传了 8）。
  也就是说一轮里超过 8 个工具调用会排队。
- **异常不抛出，而是作为 `error: <msg>` 结果返回给模型**。
  这与旧笔记的描述一致，是刻意设计：模型能看到「工具失败了」并自行调整。
- **取消语义是「清空待执行队列」**：已经在跑的工具不会被中断
  （`pending.length = 0` 只处理没开始的）。所以点「停止」后
  正在执行的 `url_fetch` 仍会跑完 —— 它内部有自己的 `createSub` 超时控制。
- **进度显示按 `toolcall.id` 分别上报**（`setRealmInfo(toolcall.id, ...)`），
  这正是 `realmInfos` 从单个对象改成 `Record<string, RealmInfo>` 的原因 ——
  并行执行时同时会有多条进度。
- `filter(u => !u.result)` 保证**已完成的不重复执行**
  （历史重放时会重新走进这里）。

### 暴露给 LLM


前端的 prompt 构造器把它映射成 OpenAI 的 `tools` 数组（`type: 'function'`）。

## 4. 五个内置 Provider

`src/tools/client/index.tsx` 的 default 导出里注册的就是这五个：

```ts
tools.providers.registry.register(
  variables,
  fetchers,
  scripts.tool,
  agents.tool,
  elicits.tool,
);
```

### variables —— 变量读写

| 工具           | 行为                                        |
| -------------- | ------------------------------------------- |
| `get_variable` | 按 `/` 分隔路径读取（含本轮尚未落盘的变更） |
| `set_variable` | 写变量                                      |
| `del_variable` | 删变量                                      |

**关键设计**：`set_variable` / `del_variable` **不直接改数据**，
而是把 JSON Patch 操作 push 到 `currentOutput.variables`，
由 `generateCurrentVariables` 统一应用。

这与 [06-故事与领域](./06-故事与领域.md) 的变量系统一致：
变量变更以**补丁序列**的形式挂在消息上，从而支持按输出翻页回溯。

### fetchers —— 网页抓取

`url_fetch`：

- 最多 `config.maxResults` 个 URL（UI 里限制 1–5，默认 3）；
- 经后端 `/api/proxy` 转发（绕过 CORS）；
- HTML/XML 用 `@mozilla/readability` 抽取正文；
- 截断到 `config.maxLength`（默认 8000）。

```ts
// src/tools/fetchers/client/index.tsx
async invoke({ args: { urls }, controller }) {
  const targetUrls = urls.slice(0, config.maxResults);
  for (const url of targetUrls) {
    results.push(await fetchUrl(url, controller.signal, config.timeout * 1000, config.maxLength));
  }
  // …
}
```

> 📌 这里是**串行**抓取（`await` 在 `for` 循环里）。
> 虽然 `tools.calling` 层面是并发的，但**一个 `url_fetch` 内部的多个 URL 仍然顺序处理**。
> 每个 URL 内部还会 `signals.createSub` 建自己的超时信号，
> **单个 URL 超时不会影响其余 URL**（错误被收敛成 `{ url, success: false, error }`）。

### scripts —— 自定义脚本工具

```ts
const fn = new Function('input', 'context', config.script ?? '');
```

`context` 可按**两个独立开关**注入：

| 开关 | 注入内容 |
| --- | --- |
| `enableDoc` | `context.document` / `context.window`（iframe 的） |
| `enableVariable` | `context.variables`（当前历史变量） |

⚠️ **注意 `context.variables` 取的是 `history.variables` 原始基线**，
**不是回放补丁后的当前值**：

```ts
if (config.enableVariable) {
  const history = await realms.history.get(null, realm);
  context.variables = history.variables;   // ⚠️ 基线快照，非最新
}
```

要拿最新变量应该用 `realms.variables(history)`。这与
[06 篇](./06-故事与领域.md) §6 描述的回放机制是同一件事的两面。

> ⚠️ **这是任意 JS 执行面**。与预设里的前端 Script 条目不同，
> 这里执行在**服务端调用路径**上（由 AI 工具调用触发）。
> 与项目定位一致（自部署个人应用，部署者即管理员），属于刻意提供的能力。

### agents —— 子 Agent

构造一个子 Realm 并跑**嵌套的生成循环**。
`create` 是模块级的异步函数（不只是 `configComponent` 的工厂），
它做了四件事：

```ts
async function create({ config, output }, { id, presets: parents, model, properties, entries, histories }) {
  // ① 嵌套防护：主 Realm 带了 properties.agent 就直接不产出工具
  if (properties?.agent) return [];

  const disableTags = new Set(config.disableTags);
  const story: Story = {
    id: main.name, name: main.name,
    presets: [
      ...(config.presets ?? []),
      ...(config.disablePreset ? [] : parents.map(presets.toNameValue)),
    ],
    model: config.model ?? models.toNameValue(model),
    properties,
  };
  // ② 借 stories.proxy.realm.get 重新投影一个 Realm
  const result = await stories.proxy.realm.get(story);
  const realm: Realm = {
    ...result,
    id,
    get histories() { return histories; },     // ⭐ 复用主 Realm 的 histories 引用
    entries,
    presets: result.presets.filter((u) => u.tags.every((v) => !disableTags.has(v))),
    properties: { agent: 1 },                  // ⭐ 给自己打上标记
  };
  // ③ 子 Realm 也要初始化自己的 processer 缓存
  await models.processers.initialize({ realm });
  // ④ 4. 没有外部进度回调时，退化成直接写 realmInfo
  if (!output) { /* … */ }
  return [agent(config, realm, output)];
}
```

子 Agent 的实际调用：

```ts
async invoke({ args, toolcall, controller }) {
  let result: string = 'error: empty content';
  // ⭐ 深拷贝 + 只取最后 maxLength 条，防止污染主 Realm
  const histories = structuredClone(realm.histories.slice(-config.maxLength));
  if (!histories.length) histories.push({ /* 空历史垫底 */ });
  const history = histories.at(-1)!;
  history.outputs = [];        // ⭐ 清掉输出，子 agent 从零开始生成
  history.output = -1;

  for await (const { output } of models.processers.generate({
    controller, args, realm: { ...realm, histories },
  })) {
    result = output.content;
    if (!toolcall) continue;
    // 按 thought / toolArg / content 的长度变化推送进度
    await info(toolcall.id, { content: `${...}`, title: 'agent.thinking', text: output.content });
  }
  return result;
}
```

四个要点：

- **嵌套防护靠 `properties.agent`**（与旧笔记一致），但它在 `create` 阶段就返回 `[]`
  —— 也就是**子 Realm 里根本不会出现 agent 工具**，而不是"出现了但调用被拒"。
  这比运行时拦截更干净。
- **`disableTags` 让子 Agent 可以剔除某一类预设**（如 `theme` / `app` 类），
  源码注释解释了动机：「子agent必须依附于主agent，只可以禁用其中一些预设，
  子agent只考虑上下文构筑」。
- **`structuredClone` 整个 histories 切片**，注释明确写了原因：
  「防止不必要的变化，例如工具冲突。主agent可能已经设置了工具调用」。
- **进度统一走 `info(name, realmInfo)` 回调**，而 `name` 用的是 **`toolcall.id`**
  —— 与主干的并行工具进度用的是同一套 key 空间，
  所以 UI 的 `RealmTips` 能同时显示主 Agent 与子 Agent 的活跃状态
  （这正是 `realmInfos` 改成 `Record` 的意义）。

### ⭐ elicits —— 让 AI 反问用户（`ask_user`）

这是 `1.3.4.0` 新增的 provider，整个实现只有 56 行，但补上了很关键的一环：
**AI 可以在生成过程中停下来问问题**。

```ts
// src/tools/elicits/client/tool.tsx
function elicit(realm: Realm): ToolItem<ElicitItem> {
  return {
    name: 'ask_user',
    description: 'ask the user for input',
    parameters: {
      type: 'object',
      additionalProperties: false,
      required: ['question', 'examples', 'custom'],
      properties: {
        question: { type: 'string', description: 'question to ask user' },
        examples: {
          type: 'array', items: { type: 'string' },
          description: 'examples to show user, user can select one of them',
        },
        custom: {
          type: 'boolean',
          description: 'whether to allow user to input custom answer, true for default',
        },
      },
    },
    invoke({ args: item }) {
      return new Promise<string>((resolve, reject) => {
        try {
          const state = useElicitState.getState();
          const reply = async (answer: string) => { resolve(answer); };
          state.push({ ...item, reply });    // ⭐ 把 resolve 挂进 UI 状态
        } catch (e) { reject(e); }
      });
    },
  };
}
```

**实现方式非常巧**：`invoke` 返回一个**永不主动 resolve 的 Promise**，
把 `resolve` 函数本身塞进 zustand store（`useElicitState`），
由 UI 弹窗在用户提交时调用它。于是：

```
工具调用 await 住 → 生成流程自然挂起 → 弹窗出现 → 用户选择 → resolve(answer)
                                                            → 工具结果 = 用户的回答
                                                            → 模型继续生成
```

这不需要在生成管线里加任何「暂停/恢复」概念 —— **用 Promise 表达等待**。

UI 侧（`src/tools/elicits/client/feature.tsx`，`Feature { id: 'elicit' }`）
是一个 `Dialog`：

- `examples` 渲染成 `RadioGroup`；
- `custom` 为真时多一个 `custom` 单选项 + 自由输入框；
- 提交时区分两种选择：选 `custom` 取输入框内容，否则取 `item.examples[Number(select)]`；
- 然后 `void item?.reply(value); pop();` —— **先 resolve 再出队**。

`useElicitState` 用一个 `render` 计数器强制 `RadioGroup` 重挂载
（`key={render}`），避免连续两次提问时沿用上一次的选中项：

```ts
push: (item) => {
  const { items, render, item: currentItem } = get();
  if (currentItem) items.push(item);        // 已有弹窗 → 排队
  else set({ item, render: render + 1 });   // 空闲 → 立即展示
},
```

> ⚠️ **两个真实的边界问题**：
> 1. **这个 Promise 没有取消路径**。如果用户在弹窗出现时点「停止生成」，
>    工具任务会被 abort，但 `invoke` 返回的 Promise **既不会 resolve 也不会 reject**
>    —— `useElicitState` 里那条 `reply` 除了 UI 提交之外没人调用。
>    它的后果被 `TaskRunner` 吸收了（`abort` 后任务仍在 `running` 里挂着，
>    直到 `manager.wait()` 永远等不到），但弹窗会一直留着。
> 2. **`elicit` 没有 `configComponent` / `configureObject`**，
>    所以工具条目在 UI 上**只有一个开关、没有配置项**（这是对的，它确实没配置）。

## 5. 记忆（Memories）

### 数据模型

```ts
// src/memories/index.ts
export interface Memory {
  text: string;
  sequence: number;   // 默认 100
  importance: number; // 默认 5
  type: string;       // 'event' | 'relation' | 'knowledge' | 'other'
  tags: string[];
}

const defaultValue: Memory = {
  text: '', sequence: 100, importance: 5, type: 'event', tags: [],
};
```

**记忆没有独立的 SQLite 表** —— 它是**故事条目**（plural `memories`），
通过 `storages.create` 注册到 `stories.storage.registry`。

排序键：

```ts
`${sequence.padStart(6, '0')}${importance.padStart(2, '0')}${name}`;
```

即「序列号升序 → 重要度升序 → 名称」。

### 内存缓存 `MemoryCache`


`init` 在 `cache.rag` 存在时把每条记忆都塞进 Orama，

> ⚠️ `cache.memories` **只在 `cache.rag` 非 null 时才会被填充**：
>
> ```ts

>   await utils.forEachItems<StoryItem<Memory>, Realm>(realm, memories.plural, async (entry) => {
>     cache.memories[entry.entryId] = entry;
>     // …embed + insert
>   });

> ```
>
> 也就是说 **RAG 关掉后，`memories` 注入链路整体失效**
> （注入时 `cache.memories[id]` 恒为 `undefined` → `continue`）。
> 这与 `get_memory` 工具会返回 `'warn: RAG is not enabled'` 是一致的取舍：
> 没有 RAG 就没有记忆功能，但会明确告知而不是静默。

### ⭐ 向量现在是持久化缓存的

这正是旧笔记里作者提出的那个问题（「不重建，换模型就瞎了，重建条目多又很慢」），
现在的解法是 **IndexedDB + 内容哈希缓存**：

```ts
// src/memories/client/rag.ts
interface VectorItem { vector: Float32Array; model: string; time: number; }

async cache(input: string, model: string, factory: () => Promise<Float32Array>) {
  const buffer = strUtils.fnv1a64Bytes(input);      // ⭐ 内容哈希做 key
  const key = new Uint8Array(buffer).buffer;
  const db = await getVectorDb();                   // IndexedDB: 'VectorCache'
  const item: VectorItem = (await db.get('vectors', key)) ?? {};

  if (model !== item.model) {                       // ⭐ 换模型才重算
    const vector = await factory();
    item.vector = vector;
    item.model = model;
  }
  item.time = Date.now();                           // ⭐ 命中也要刷新时间（LRU）
  await db.put('vectors', item, key);

  // 超限清理：按 i_time 索引升序（最旧在前）淘汰 100 条
  const count = await db.count('vectors');
  if (count > useRagState.getState().cacheLimit) {
    let remain = 100;
    const tx = db.transaction('vectors', 'readwrite');
    let cursor = await tx.store.index('i_time').openCursor();
    while (cursor && remain > 0) { cursor.delete(); remain--; cursor = await cursor.continue(); }
    await tx.done;
  }
  return item;
}
```

四点值得记：

- **缓存键是 FNV-1a 64 位哈希**（`strUtils.fnv1a64Bytes`，纯 JS 实现），
  不是原文字符串 —— 所以键长固定 8 字节，不随文本长度膨胀。
  这也回答了作者当时的设想（「hash后字符串就是256，只需要向量即可」）。
- **命中条件同时看内容哈希与模型名**：哈希相同但 `model` 不同就重算。
- **淘汰是「一次清 100 条」而非逐条**：超过 `cacheLimit` 才触发，
  每次批量删最旧的 100 条。也就是容量会在阈值附近**锯齿波动**，不是精确 LRU。
- `blocking()` 里会把 `vectorDb` 置空并关闭旧连接，
  处理「另一个标签页升级了数据库」的情况。

> ⚠️ 一个**尚未完全兑现**的点：缓存的收益依赖 `embed.generate` 走 `rags.cache`
> —— `transformer.embed()` 确实走了（`return [...result.vector]`）。
> 但**世界书索引与记忆索引仍然是每次 `init` 重建 Orama 内存库**
> （`rags.create(schema)` 内部 `createSchema(...)`）。
> 缓存省掉的是**重复的模型推理**，不是「重建库」这一步。
> 条目极多时，`init` 期间的 `await insert(...)` 依然是一大开销。

### 检索与写入：两个工具

记忆不是自动注入的，而是通过**工具**由模型主动使用：

#### `get_memory`

参数：`content`、`types`、`tags`、`limit`（默认 3，最大 5）、`min_relevance`（默认 0.3）。

```ts
const embedding = await embed.generate({ content });

// 过滤器：types / tags 都是「数组包在 [字段名, 值] 里」再 Object.fromEntries
const filter: any[][] = [];
if (types?.length) filter.push(['type', types]);
if (tags && tags.length > 0) filter.push(['tags', tags]);

const results = await search(database, {
  mode: 'vector',
  vector: { value: embedding, property: 'embedding' },
  similarity: min_relevance,
  limit: limit * 3, // ⭐ 先多取，再重排
  where: filter.length ? Object.fromEntries(filter) : undefined,
});

// 二次重排
const data = results.hits
  .map((hit) => {
    const { entryId, title, importance, sequence } = hit.document;
    const score =
      hit.score + ((importance / 10) * sequence) / (realm.histories.length + 1);
    return { entryId, title, score };
  })
  .sort((a, b) => b.score - a.score)
  .slice(0, limit);

const codes = memories.codes(output)!;
codes.push(data.map((u) => u.entryId));   // ⭐ 写回命中 id
return JSON.stringify(data.map((u) => u.title));   // 只把标题回给模型
```

**重排公式的含义**：在向量相似度基础上，叠加「重要度 × 序列号 / 历史长度」。
即越重要、越靠后的记忆在长对话中越容易被召回（分母是历史长度，
所以对话越长这个加成的绝对量越小 —— 一种归一化）。

两个细节：

- **`where` 的构造是 `Object.fromEntries([['type', types], ['tags', tags]])`**，
  即 `{ type: ['event'], tags: ['a'] }` —— 数组值在 Orama 里是「任一匹配」。
- `get_memory` 与 `get_lorebook` 一样，**返回给模型的只是标题**，
  正文通过伪 `get_knowledge` 调用注入（见下）。
  这是刻意的两步设计：模型先「知道有哪些」，再由注入通道拿到内容。

#### `set_memory`

生成嵌入 → `stories.proxy.entry.add(...)` → 写缓存 → `insert(database, ...)`。

## 6. 工具循环（回顾）

工具的执行横跨 `prompt` 与 `output` 两个阶段：

```
第 N 轮：
  prompt()  ──▶ engine.prompt() 把 actives 工具映射成 tools 参数
     │
  engine.generate() ──▶ 模型可能返回 tool_calls
     │                     └─ engine.result() 写进 output.callings（arguments 逐步拼接）
     │
  generateOutputs() ──▶ tools.calling(realm, controller, output.callings)
     │                     └─ 并行执行（TaskRunner，上限 8）并写回 result
     │
  下一轮：带着已填充 result 的 callings 重新请求
     │
  直到 stopped 或 iteration 耗尽
```

> 📌 **`tools.calling` 现在只从 `engines.prompt` 里的 `generateOutputs` 调用**
> （历史轮次的工具补执行），**不再挂在 `tools` 的 `output` 钩子上**。
> 旧笔记说的「output 阶段会再被调一次」已过时 ——
> `src/tools/client/realm.ts` 现在只有 `init`，没有 `output`。
> 防重复执行的守卫从「`output` 阶段再跑一遍」变成了
> `callings.filter(u => !u.result)`。

## 7. 已知问题（`1.3.5.0` 复核）

1. ~~记忆 RAG 每次生成重建~~ → ✅ **已大幅缓解**：嵌入走 IndexedDB 缓存
   （内容哈希 + 模型名双键），只有 Orama 内存库仍需重建。
   详见本篇 §5「向量现在是持久化缓存的」。
2. **`set_variable` 走 JSON Patch**：读取时要经过 `patch()` 回放才能看到最新值，
   直接读 `history.variables` 会拿到旧值。
   ⚠️ **`scripts` 工具的 `context.variables` 正好踩了这个坑**
   （`context.variables = history.variables`，是基线快照而非最新值）。
3. **scripts 工具的任意代码执行**：属刻意设计，但审计时值得注意。
4. **工具 provider 缺失的行为与注释不一致**：注释说「报错中断」，
   实现是 `console.warn` + `return`。而 `provider.create` **抛错**时会
   `throw new BusinessError('tool create failed', ...)` 中断整个 init
   —— 也就是说 **`type` 写错 → 静默消失；provider 内部出错 → 整个 Realm 打不开**。
   两者的反差挺大，建议统一（详见本篇 §3）。
5. **`agents` 的嵌套防护**：靠 `properties.agent` 标记。
   它在 `create` 阶段就 `return []`，所以子 Realm 里根本没有 agent 工具
   —— 比「运行时拦截」更干净，但**不是硬性安全边界**
   （`properties` 是普通对象，任何能构造 Realm 的代码都能绕过）。
6. **⭐ `ask_user` 的 Promise 没有取消路径**：弹窗出现时点「停止生成」，
   工具任务被 abort 但 Promise 悬挂，弹窗不消失（详见本篇 §4 的 elicits 小节）。
7. **⭐ 工具并发上限是隐式的 8**：`tools/client/task.ts` 用 `super()` 不传参，
   依赖 `TaskRunner` 的默认值 `max = 8`。改这个上限需要知道它藏在基类默认值里。
8. **`tools.calling` 对 `controller` 用了非空断言**（`controller!`），
   如果将来有调用方不传 controller，会在运行时炸而不是编译期。

## 8. 本章速查

- 想加一个工具？写一个客户端 `ToolProvider`（含 `create`），注册到 `tool-provider`。
- 想让工具能被导出？再写一个服务端 `ToolProvider`（含 `loadArchive`/`saveArchive`）。
  注意它的签名是**单一 context 对象**，不是位置参数。
- 想控制工具的开关？它存 `realm.properties.tool.items`；
  `macro` 填**宏的 code** 时改为与宏的 `checkItems` 同步。
- 工具报错会怎样？作为 `error: <msg>` 文本回灌给模型，不会中断生成。
- 想让工具能响应「停止生成」？用 `invoke({ controller })` 里的信号。
- 记忆怎么进上下文？模型调用 `get_memory`，回忆结果伪装成 `get_knowledge` 工具结果注入。
- 想让 AI 反问用户？用 `ask_user`（`elicits` provider），
  UI 是 `src/tools/elicits/client/feature.tsx` 的弹窗。
