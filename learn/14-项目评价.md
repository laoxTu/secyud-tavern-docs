# 14 · 项目评价（正面视角）

这一篇专门从**正面**评价这个项目。

写「好评」容易写成空话，所以我给自己定了个规矩：
**每一条称赞都必须给出具体的设计事实作为依据**，
说清楚「好在哪、为什么难、多数项目做不到什么程度」。
没有依据的溢美之词不写。

---

## 一、总评

`secyud-tavern` 是一个**完成度与野心相匹配**的项目。

它的野心不小——要做"高度可定制的 AI 角色扮演平台"。
而"高度可定制"是软件工程里最容易说、最难做的承诺之一。
读完 364 个源文件后我的判断是：**它真的做到了自己承诺的事**，
而且用的方法比大多数同类项目更彻底、更优雅。

下面分项说明。

---

## 二、架构层面：一套约定，撑起十一个模块

### 2.1 `manifest.json` + `Registry` 是教科书级的插件架构

这个项目最值得称道的是它的**模块契约极简且统一**。
一个模块的身份只需要一个 `manifest.json`：

```jsonc
{ "id": "preset", "client": "client", "server": "server" }
```

三个字段说清了「我是谁、前端在哪注册、后端在哪注册」。
剩下的全部交给约定：`client/index.tsx` 的 default 导出就是注册函数。

**为什么这很难得**：大多数插件系统的契约是"配置驱动"的——
你得在某个中心文件里声明插件、填一堆元数据、遵循长长的 API 清单。
这个项目把契约压到三个字段，靠的是**约定**（default 导出即注册入口）
而非**配置**。少写一堆样板，就少一堆出错的机会。

### 2.2 用拓扑排序解决初始化顺序，而不是靠人肉排序

模块之间有依赖（宏依赖正则、世界书依赖工具），
作者没有选择"文档里写清楚谁先谁后"这种脆弱方案，
而是在 `Registry` 里实现了 **Kahn 拓扑排序**：

```ts
const processer: Processer = {
  id: main.name,
  requires: [regexMain.name],   // 声明依赖，顺序自动推导
};
```

而且**错误处理很硬气**：

- 依赖了不存在的模块 → 直接抛错，不静默跳过；
- 存在循环依赖 → 直接抛错，并列出涉及的模块。

这种"错了就炸"的态度在插件系统里是正确的选择——
顺序错了会导致极难排查的诡异行为，早失败远好过晚失败。

**细节**：`requires` 之外还有 `sequence` 作为同层级次序的兜底，
`interceptor` 用 `sequence: -1000` 保证拦截器最先注册。
两个机制配合得很干净。

### 2.3 代码生成用得恰到好处

`pnpm prepare` 会在编译期扫描 manifest，生成四类产物：
注册表、i18n 资源聚合、API 路由、以及**类型化的 API 路径**。

最漂亮的是最后一项：生成的 `src/generated/api-path.ts` 导出
`GetPath` / `PostPath` 等字符串联合类型，于是前端调用获得编译期校验：

```ts
get('presets/{id}', { params: { id } })   // 路径拼错 → 编译不过
```

**这解决了一个真实痛点**：手写 REST 路径几乎必然拼错，
且只能在运行时发现。用代码生成把路径变成类型，
是在**不引入运行时依赖**的前提下拿到了类型安全。

它选择的是**编译期插件**而非运行时插件，代价是改 manifest 要重新 prepare，
但换来的是"完整的原生 Next.js 开发调试体验"——
热更新、断点、类型推导全都在。这是一次清醒的取舍。

### 2.4 模块切分干净，职责边界清晰

十一个模块（database / comfyui / files / global / lorebooks / memories /
models / presets / signal / stories / tools）的划分**几乎没有重叠**。

每个模块内部又是同一套骨架：

```
index.ts          类型与元信息
manifest.json     声明
client/           浏览器侧
server/           服务端
localization/     多语言
```

**好处是学习成本可以复用**：学会一个模块，剩下十个都能猜出结构。
我在写笔记时深有体会——从第三个模块开始，阅读速度明显加快，
因为我知道该去 `server/schema.ts` 找表、去 `server/api.ts` 找接口、
去 `client/proxy.ts` 找请求封装。

## 三、数据层面：一个 entry 表撑起六种条目

### 3.1 单表多态用得非常克制

预设有六种条目（宏、正则、脚本、样式、世界书、工具），
直觉做法是建六张表。作者只用了一张：

```ts
schemas.entry(name, ref, extraColumns)  // 复合主键 + data JSON 列
```

**为什么这是好设计**：

- **加条目类型不用改表结构**——新增一种条目只是往 `data` 里塞不同的 JSON；
- **通用 CRUD 可以完全复用**——`repositories.entry()` 一套代码服务所有条目类型；
- **归档逻辑可以统一**——导出时按 `plural` 建目录，处理方式一致。

这是典型的"用一点点类型安全换极大的灵活性"，而且**换得很值**，
因为条目字段本来就是用户可编辑的内容，本来也不需要数据库约束。

### 3.2 `filter` / `sorter` 冗余列是个聪明的小技巧

每条 entry 行都有两个冗余字符串列，由各模块自己计算：

```ts
criteria: ({ name, data: { code, match } }) => ({
  sorter: `${match}${code}${name}`,
  filter: `${match}${code}${name}`,
})
```

**它解决了一个实际问题**：内容存在 JSON 列里，
但用户需要按名称搜索、按优先级排序。把检索所需的键**预先拼成字符串**，
就能用普通 `LIKE` 和 `ORDER BY` 完成，不必把 JSON 里的字段提出来建索引。

思路简单，但效果直接：查询快、实现简单、加字段不用迁移。

### 3.3 级联外键用得很彻底

```ts
export const foreignKey = (name, ref) =>
  text(name).references(ref, { onDelete: 'cascade', onUpdate: 'cascade' });
```

删一个预设，它的所有条目自动清理。
**业务代码里看不到一句手写的清理逻辑**——这正是好设计的标志：
正确性由约束保证，而不是靠开发者记得。

## 四、交互与产品层面：真正尊重用户的能力

### 4.1 把界面交给用户，这是罕见的信任

多数"可定制"平台给的是**皮肤**。这个项目给的是**画笔**。

它在游玩页放了一个 iframe，然后说：界面你自己画。
只提供三样东西——

1. `postMessage` 的数据推送（`content` / `variables`）；
2. `window.userInput` 接口（读输入、设置输入、注册 `inputBuilders`）；
3. 一套脚本/样式的注入机制。

**结果**：预设作者能做的不再是"调参数"，而是"做产品"。
`疯狂水世界`、`模拟经营` 这些模板能存在，正是因为这条路是通的。

**为什么值得赞赏**：这是一个**主动放弃控制权**的决定。
宿主本可以提供一个"够用"的默认聊天界面，
但那样所有预设就都被锁在那个界面的形状里了。
选择留白，意味着把最大的自由度让给了用户，
也意味着要承担"新人打开是空白页"的困惑成本。
**敢做这个取舍的项目不多。**

### 4.2 复用工具通道做知识注入，是很有品味的设计

世界书和记忆都需要往上下文塞文本。作者没有发明新消息类型，
而是**伪造一次 `get_knowledge` 工具调用**：

```ts
caller('', null, [{
  name: models.engines.knowledge.info.name,      // 'get_knowledge'
  arguments: models.engines.knowledge.args({ type: 'lorebook' }),
  result: content,
}]);
```

**好在三点**：

1. **零新增概念**——引擎层不需要知道"世界书"是什么，只认识工具调用；
2. **天然兼容所有供应商**——OpenAI / DeepSeek / Anthropic 都已经支持工具调用，
   不用为三家各写一遍；
3. **动机可读**——那句 `description: 'return empty if current knowledge is injected'`
   是在用自然语言提示模型不要重复调用,很巧。

**这是"找到已有抽象的正确用法"，比"加一层新抽象"难得多**，
因为它要求作者先真正理解工具调用通道的本质：它就是"外部信息的注入点"。

### 4.3 JSON Patch 做变量，让交互特性自然涌现

每条消息挂一个补丁数组而非完整快照。
好处不只是省存储，而是**"输出翻页改变上下文"这个特性不需要额外代码**：

```ts
function variables(history, output = true) {
  const variables = structuredClone(history.variables);
  for (const input of history.prompts) patch(variables, input.variables);
  if (output) { /* 回放选中输出的补丁 */ }
  return variables;
}
```

传 `output: false` 就得到"应用输出前"的状态。
**一个布尔参数切换了时间点**——这是数据结构选对了才会有的优雅。

### 4.4 重新生成采用"追加成组"而非"覆盖"

```ts
history.outputs.push(outputs);   // 每次生成追加一组
history.output = history.outputs.length;   // 指向最新
```

重新生成不会毁掉上一版，用户可以来回翻看。
`outputs` 是二维数组——外层是版本，内层是"一轮因工具调用拆成的多段"。
**这个结构同时解决了"版本管理"和"工具循环"两个问题**，很经济。

## 五、工程细节：那些让人舒服的地方

### 5.1 错误信息的 i18n 设计

```ts
throw new BusinessError('...', 'error.empty_field')
  .withValue('field', 'preset.name');
```

`code` 是 i18n key，`data` 里的字符串值也会被逐一带上翻译：

```ts
record[key] = t.has(value) ? t(value) : value;   // 🔑 data 也参与翻译
```

**这个 `t.has()` 检查很见功力**：它让"字段名"这种也会出现在报错里的内容
同样可以被本地化，而不是硬编码英文。多数项目的错误信息是半中半英的，
这个项目从数据结构上解决了它。

### 5.2 客户端统一的错误分级处理

```ts
if (err instanceof BusinessError) { toast; return; }        // 预期内，只提示
if (isNetworkError(err) || isHttpError(err)) { toast; return; }  // 网络问题，只提示
toast.error(err?.message); throw err;                       // 未知错误 → 交给错误边界
```

注释写得很直白：「继续抛出意味着页面崩溃，进入 notfound」。

**分级清晰**：业务失败不炸页面，未知错误才交给错误边界。
这让"偶发的 API 报错"不会把整个界面打白，用户体验明显更稳。

### 5.3 服务端的惰性单次初始化

```ts
const global = globalThis as { __initialized?: boolean };
if (!global.__initialized) {
  global.__initialized = true;
  await registerServerPlugin();
}
```

在**第一个请求到达时**才注册，且保证全进程只跑一次。
只用了一个全局标志位，没有任何框架依赖。

### 5.4 流式卡死检测

```ts
const checkTime = () => {
  setTimeout(() => {
    const elapsed = Date.now() - updateTime.getTime();
    if (elapsed > interval * 1000) controller.abort('retry');
    else if (!finished) checkTime();
  }, interval * 500);
};
```

流式请求"连上了但不再吐数据"是很讨厌的故障——
用户只看到光标闪烁，不知道卡住了。这里每 `interval` 秒检查一次，
**超过阈值就以 `reason = 'retry'` 主动中断并重试**。

用 abort 通道传递重试意图（而不是另建一套机制），
配合外部/内部两级 `AbortController` 的关联，
既处理了"用户取消"，也处理了"网络卡死"。考虑得很周全。

### 5.5 自析构的事件监听

```ts
function setAbort(signal: AbortSignal, action: (event: Event) => void) {
  const abort = (event: Event) => {
    action(event);
    signal.removeEventListener('abort', abort);   // 🔑 自动解绑
  };
  signal.addEventListener('abort', abort);
}
```

四行代码解决监听器泄漏。**生成流程会循环很多次**，
如果每次都不解绑，长对话下会累积大量悬挂监听器。
作者注意到了这个细节。

## 六、文档与注释：把「为什么」留下来了

这是我认为这个项目**最被低估的优点**。

代码注释分两种。解释"这段在做什么"的注释是冗余的——
代码本身就说清了。而这个项目的注释主要在写**决策与陷阱**：

```ts
/**
 * 复选的规则很复杂，
 * 1，相同的code，不同的key共享一个禁用
 * 2，不同的code，相同的key是正常情况
 * 3，相同的code，相同的key，会追加且共享
 * 这是为多preset设计的，可以继承，共享
 */
```

这段规则从代码里反推要花很久，作者直接写出来了。

更难得的是这句：

```tsx
{/* key不要删除。发布后，如果没有这个key，会导致引用有问题，原因不明，开发环境无此问题。 */}
```

**作者明确承认"原因不明"。** 这比编一个听起来合理的解释有用得多：
后来者知道这里不能动，且知道作者也没搞懂，不会误以为自己的理解有偏差。

`CONTRIBUTING.md` 同样坦诚——直接说明"不要提移除能力的加固 PR"，
并解释清楚项目的威胁模型。**这种坦诚让代码变得可读**，
因为读者能分清哪里是精心设计、哪里是历史妥协。

## 七、技术选型的品味

| 选型 | 评价 |
| --- | --- |
| **Eta** 做宏 | 轻量、支持异步渲染（`renderStringAsync`），比引入完整模板引擎克制 |
| **Orama** 做向量检索 | 纯前端、零后端依赖，让 RAG 变成"浏览器内的事" |
| **@huggingface/transformers** 本地嵌入 | `allowRemoteModels = false`，模型随项目下载，**不依赖外部服务** |
| **libsql** | 单文件数据库，零运维，完全符合"自部署个人应用"的定位 |
| **Monaco** 编辑脚本 | 直接给用户 IDE 级体验，而不是糊一个 textarea |
| **Zustand** | API 极简，不需要 Provider 包裹，适合这种注册驱动的架构 |
| **@base-ui/react** | 选择了无样式的原语层，把视觉完全交给 Tailwind 与用户预设 |

**整体倾向是一致的**：优先"自包含、零外部依赖、用户可控"。
每个选择都服务于"自部署个人应用"这个定位，没有一处是随大流选的。

## 八、协作友好度

- **`CONTRIBUTING.md` 写得实在**：环境准备、目录结构、代码约定、
  提交规范、测试方式都有，还附了三条"提交前必须通过"的命令。
- **明确列出了贡献方向**（缺陷修复、插件、文档、翻译、预设模板），
  降低新人参与的门槛。
- **主动说明测试现状**：「当前覆盖率较低（仅 ComfyUI、宏、部分工具），
  纯逻辑部分（宏求值、预设解析、各类 utils）非常欢迎补测试」。
  **承认欠账并给出切入点**，比假装测试很全要好得多。
- **路径别名、格式化配置、VS Code 设置都已配好**，clone 下来就能开工。
- 第一次贡献建议先开 Issue —— 这条建议很务实，能避免方向不一致导致白做。

## 九、结语

如果要我用一句话概括：**这是一个"想清楚了"的项目。**

它的每一个主要设计——编译期插件、单表多态、iframe 渲染、
伪工具注入、JSON Patch 变量、双引擎抽象——都能说清楚"为什么这么做"
以及"放弃了什么"。没有为了炫技引入的东西，
也没有"先这么写着以后再说"的糊弄。

尤其在"可定制性"这个主题上，它做到了很少见的程度：
**不是把选项变多，而是把能力交出去。**

考虑到它还是 AGPL 开源、文档齐全、贡献指南清晰，
我认为这是一个**值得长期关注、也值得作为架构学习样本**的项目。

## 附：最值得学习的五个设计

如果只从中学五件事：

1. **契约要小，约定要明** —— 三个字段的 manifest 胜过一份插件 API 清单。
2. **顺序靠声明，不靠文档** —— `requires` + 拓扑排序。
3. **能复用通道就别新建概念** —— 世界书伪装成工具调用。
4. **让数据结构承载语义** —— JSON Patch 让"翻页改变上下文"自然成立。
5. **注释写"为什么"和"不确定"** —— 承认"原因不明"是一种专业。
