# 12 · 世界书

世界书是「按条件注入知识」的机制：根据当前对话内容与变量，
决定把哪些设定文本塞进模型的上下文，以及塞在**哪个位置**、以**什么角色**。

> 📌 本篇已按 `1.3.5.0` 复核，**改动较大**。最关键的变化：
> `vector` 匹配器**不再自己做检索**，向量检索改由 LLM 主动调用的
> `get_lorebook` 工具触发（这修掉了旧的「索引写 name、比对用 id」bug）；
> RAG 的 `limit` / `similarity` / `disabled` 全部变为可配置；
> `always` 匹配器新增了 `macro` 绑定。

---

## 1. 条目结构

```ts
// src/lorebooks/index.ts
export type LorebookRole = 'assistant' | 'user' | 'system' | 'knowledge';

export interface Lorebook<TExpression = any> {
  code: string; // 编码，用于去重
  type: string; // json | plaintext | markdown | yaml | xml
  match: string; // matcher id
  expression: TExpression; // matcher 的配置对象
  content?: string; // 世界书正文
  priority: number; // 优先级 → 插入顺序
  layer: number; // 层级 → 插入位置
  role: LorebookRole;
}
```

默认值：

```ts
const defaultEntry: Lorebook = {
  code: '',
  content: '',
  layer: 100,
  expression: {},
  match: 'always',
  priority: 0,
  role: 'knowledge',
  type: 'plaintext',
};
```

支持的文本格式及导出扩展名：

```ts
const typeMap = {
  json: 'json',
  plaintext: 'txt',
  markdown: 'md',
  yaml: 'yaml',
  xml: 'xml',
};
```

> 世界书是**预设条目**（`entryType = 'lorebook'`），不是故事条目。
> 它注册在 `presets.storage.registry` 里，通过故事的预设依赖被引入。

## 2. 排序：layer 与 priority

```ts
function sequence(item: Lorebook) {
  return item.layer * 10000 + item.priority; // ← layer 是大层级，priority 是层内细排
}
function compare(lft, rht) {
  return sequence(lft) - sequence(rht);
}
```

所以 `layer` 每 +1 相当于 `priority` +10000。设计上：

- **`layer >= 100`** 是分界线：`layer < 100` 的世界书注入在**用户消息之前**，
  `layer >= 100` 的注入在**用户消息之后**。
- `priority` 只在同 layer 内决定先后。

## 3. 六种匹配器（Matcher）

```ts
// src/lorebooks/client/matcher.ts
export interface Matcher extends Registerable {
```

### 注册表名与匹配器清单

注册表名 `lorebook-matcher`（`832d3e4` 已修正旧的 `macher` 拼写）。
它是**只有客户端半边**的注册表 —— 匹配逻辑完全在浏览器里跑
（要用到 `history`、变量、向量库，都在前端）。
`src/lorebooks/client/index.tsx` 注册了五个匹配器：

| id         | 配置                                                 | 匹配逻辑                                                                              |
| ---------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `always`   | `{ last: boolean, macro?: string }`                  | 恒真，**不参与逐消息匹配**，直接进固定注入列表                                        |
| `normal`   | `{ keywords: string[][], keywordsLength, fitCount }` | 二维关键词组：**组间 AND，组内 OR**                                                   |
| `event`    | `NormalMatchConfig + { maxDate, minDate }`           | 变量里的日期落在区间内 + 关键词匹配                                                   |
| `variable` | `{ path, value }`                                    | 取变量的指定路径做**字符串全等**比较                                                  |
| `vector`   | 无配置 UI                                            | 读 LLM 通过 `get_lorebook` 工具写入的命中码（**不是自己检索**）                       |
| （date）   | —                                                    | **不是独立匹配器**：日期逻辑内嵌在 `event` 里，`date-editor.tsx` 只是 event 的配置 UI |

### normal 的语义

```ts
// src/lorebooks/client/matchers/normal.tsx
export function normalMatch(context, expression?) {
  if (!expression?.keywordsLength) return false;      // ⚠️ 没这个字段就直接 false
  const content = lorebooks.matchers.content(context);
  let fitCount = 0;
  for (const keywords of expression.keywords) {
    if (keywords.some((keyword) => content.includes(keyword))) fitCount++;
    if (fitCount >= expression.fitCount) return true;  // 达标即提前返回
  }
  return false;
}
```

即：`keywords: [['龙','dragon'], ['魔法']]` + `fitCount: 2`
表示「必须同时命中『龙/龙族』和『魔法』相关词」。
纯 `String.includes`，**无分词、无大小写归一**。

默认值 `{ fitCount: 1, keywords: [[]], keywordsLength: 1 }`，
且 UI 里关键词组数上限是 **4 组**（`maxLength = 4`）。

> ⚠️ **两个容易踩的坑**：
> 1. `keywordsLength` 是**必填** —— 它是 `normalMatch` 的第一道门。
>    导入的预设若缺这个字段，匹配会**恒为 false**。
> 2. `configureObject` 是**从表单重建** `expression` 的：
>    ```ts
>    export function normalConfig(data: FormData): NormalMatchConfig {
>      const keywordsLength = forms.int(data, 'keywordsLength');
>      const keywords: string[][] = [];
>      for (let i = 0; i < keywordsLength; i++) {
>        keywords.push(forms.strs(data, `keywords-${i}`));
>      }
>      return { keywords, keywordsLength, fitCount: Math.min(...) };
>    }
>    ```
>    也就是说**只要你在 UI 里保存过这条世界书，`expression` 就会被表单内容完全覆盖**
>    —— 手写在 `meta.json` 里、或表单未渲染出来的字段都会被丢掉。

### vector 的语义（已重写）

> ✅ **这里是 `1.3.5.0` 相对旧笔记变化最大的地方，务必重读。**

`1.3.2.8` 时 `vectorMatcher.match` 自己跑 Orama 检索、比对 `lorebook.id`，
而索引里写的是 `entry.name`（显示名），两处对不上 —— 笔记当时标为「疑似 bug」，
作者也确认了。**现在的架构换了一层**：检索不再由匹配器发起，
而是**由 LLM 主动调用 `get_lorebook` 工具**发起。

```ts
// src/lorebooks/client/matchers/vector.ts —— 现在只有 25 行
export const vectorMatcher: Matcher = {
  id: 'vector',
  match: async (context, lorebook) => {
    if (!context.cache.rag || !context.output) return false;
    const { properties } = context;
    let ids: Set<string | undefined> = properties[vectorMatcher.id];
    if (!ids) {
      ids = new Set();
      const list = lorebooks.codes(context.message);   // 读消息上的缓存
      if (list) for (const vectors of list) for (const vector of vectors) ids.add(vector);
      properties[vectorMatcher.id] = ids;              // 同一条消息只算一次
    }
    return ids.has(lorebook.id);                       // ⭐ 用 id，与索引一致
  },
};
```

命中的码存在 `message.properties.lorebook_vector`（`string[][]`），
写入者是工具 `get_lorebook`：

```ts
// src/lorebooks/client/tool.ts
const results = await search(database, {
  mode: 'vector',
  vector: { value: embedding, property: 'embedding' },
  similarity: min_relevance,   // ⭐ 可配置，默认取 useRagState().similarity
  limit: limit * 3,            // 先多取，再按 score 排序截断
});
const codes = lorebooks.codes(output)!;
codes.push(data.map((u) => u.document.name));   // name 存的是 entry.id
return JSON.stringify(data.map((u) => u.document.title));  // 只把标题回给模型
```

三个由此产生的性质：

1. **`output: false` 时 vector 恒不匹配**（第一行就 `return false`）。
   即向量世界书只在**输出方向**（AI 刚说的话 / 工具结果）参与匹配。
2. **`lorebook_vector` 是「查一次、用多次」**：一次 `get_lorebook`
   返回的码集合会被**同一条消息上的所有 vector 型条目**共享。
3. **`name` 字段存的是 `entry.id`（`预设id-code`），`title` 才是显示名**
   —— 索引与比对两侧终于对齐了。

### `always` 的 macro 绑定（新增）

`always` 匹配器的配置从 `{ last }` 扩成了 `{ last, macro? }`：

```ts
// src/lorebooks/client/renderer... 实际在 realm.ts 的 fixed()
async function fixed(items: PresetItem<Lorebook<AlwaysMatchConfig>>[]) {
  const { checkItems } = macros.property(realm);
  for (const lorebook of items) {
    if (visited.has(lorebook.id)) continue;
    visited.add(lorebook.id);
    // ⭐ 绑定了宏、且该宏未勾选 → 这条常驻世界书不注入
    if (!lorebook.expression.macro || !checkItems[lorebook.expression.macro]) {
      list.push(lorebook);
    }
  }
}
```

语义是「**用宏的勾选状态当作这条常驻世界书的开关**」：
`expression.macro` 填一个宏的 `code`，那个宏被勾上时这条世界书就**不**注入。
（注意判断是反的：`checkItems[macro]` 为真 → 不 push。）

## 4. 匹配结果的缓存

```ts
async function analyze(items, context) {
  const activeLorebooks: string[] = [];
  for (const [key, lorebook] of Object.entries(items)) {
    const matcher = matchers[lorebook.match];
    if (matcher && (await matcher.match(context, lorebook)))
      activeLorebooks.push(key);
  }
  utils.setProperty(message, lorebooks.plural, activeLorebooks); // ← 写回消息
  return activeLorebooks;
}
```

命中结果写进 **`message.properties.lorebooks`**。这样做的收益：

- 同一条消息不会重复计算匹配；
- 生成结束后 `processer.output` 会对输出消息再跑一遍并落库缓存，
  **历史重放时可复现**，不必重算（世界书依赖的向量/变量可能已变化）。

读取时优先用缓存：

```ts
const ids =
  message.properties?.[lorebooks.plural] ??
  (await matchers.analyze(cache.entries, {
    history,
    message,
    properties: {},
    output,
    cache,
  }));
```

两个复用辅助（都做 `properties` 级缓存）：

```ts
content(ctx); // output=true 时 = message.content + 所有 callings 的 result 拼接
variables(ctx); // = realms.variables(history, output)
```

## 5. 注入算法（核心）

`processer.prompt` 只是把一个注入器工厂推入 `ctx.injects`：

```ts
export const processer: Processer = {
  id: main.name,
  requires: [tools.name], // ⭐ knowledge 角色走工具通道，故依赖 tools
  init, // 建缓存与向量索引
  async prompt(ctx, cache) {
    ctx.injects.push((inject) => create(ctx, inject, cache));
  },
  async output({ history }, cache) {
    /* 生成后重算并缓存匹配结果 */
  },
};
```

### 初始化缓存

```ts
init: async ({ realm }) => {
  const cache: LorebookCache = {
    before: [],
    after: [],
    entries: {},
    rag: await rags.create(lorebookSchema),   // ⭐ RAG 实例（可被配置禁用）
  };
  await utils.forEachItemsList(
    realm.presets,
    lorebooks.plural,
    async (entry, item) => {
      entry.id = `${item.id}-${entry.code}`; // ⭐ 预设 id + code 组成唯一键
      const { disabled, match, type, expression } = entry;
      if (disabled) return;
      if (type === 'json') entry.content = jsonUtils.minify(entry.content);
      if (match === alwaysMatcher.id) {
        if (expression?.last) cache.after.push(entry);
        else cache.before.push(entry);
      } else {
        cache.entries[entry.id ?? ''] = entry; // 参与匹配
      }
      // ⭐ 只为 vector 型条目建索引；name 用 id、title 用显示名（已对齐）
      if (cache.rag && entry.match === vectorMatcher.id) {
        const { embed, database } = cache.rag;
        const embedding = await embed.generate({
          content: entry.content ?? '',
        });
        await insert(database, { name: entry.id, title: entry.name, embedding });
      }
    },
  );
  return cache;
};
```

> **设计意图（作者确认）**：`jsonUtils.minify` 在这里是**边界消毒**，不是通用解析器。
> 上游 `src/lorebooks/client/content.tsx` 在写入前已经用
> `checker.validJsonOrEmpty(content, 'preset.lorebook')` 校验过作者手写的内容，
> 所以「能走到这里的合法 JSON」是由上游保证的。
>
> 剩下能走到这里的非法内容**只可能来自导入的预设包** —— 把这种内容清空是刻意的：
> 既不浪费 token，也避免把一个格式错误的 JSON 喂给模型造成误导。
> 因此 `type: 'json'` 的条目在导入后变成空内容是**设计行为，不是数据丢失**。
> 导出/导入两侧对空内容与非法内容都保持宽容、不做拦截报错，**责任在预设包的制作者**。

三类归属：

- `always` + `last: false` → `cache.before`（固定前置）
- `always` + `last: true` → `cache.after`（固定后置）
- 其他 → `cache.entries`（按消息内容动态匹配）

### 默认 builder 模式

```ts
default:
  let index = 0;
  await fixed(cache.before);            // 前置固定条目先无条件入 list
  return {
    async before(i) {                 // 每条历史的用户输入之前
      const history = histories[i];
      await moved(history, history.prompts, false);      // 用户输入触发的世界书
      if (i === histories.length - 1) await fixed(cache.after);
      list.sort(lorebooks.compare);
      const c = list.findIndex(u => u.layer >= 100);
      index = c < 0 ? list.length : c;
      await inject(list.slice(0, index));                // layer < 100 → user 之前
    },
    async middle() {                  // 用户输入之后
      await inject(list.slice(index, list.length));      // layer >= 100 → user 之后
      list.length = 0;                // ⭐ 清空，下一条历史重新累积
    },
    async behind(i) {                 // AI 输出之后
      if (i === histories.length - 1) return;
      await moved(history, realms.outputs(history), true);  // AI 输出触发的世界书
    },
  };
```

三个钩子恰好对应 `ModelInjectContext` 的时序（见 [07-生成管线](./08-生成管线.md)）：

```
before(i)  → 注入 user 消息 → middle(i) → 注入 assistant 输出 → behind(i)
```

`middle()` 结尾的 `list.length = 0` 很关键：它保证**每条历史的世界书集合是独立的**，
不会把上一轮的内容带到下一轮。`visited` 集合则跨全部历史生效，负责全局去重。

### layered builder 模式

当 `model.builder === 'layered'` 时启用，语义是「滑窗」。
注意它与 default 的**结构差异**：`fixed(cache.after)` 提前到最前面执行，
且**没有 `before` / `behind` 钩子**，只返回 `middle`：

```ts
case 'layered': {
  await fixed(cache.before);
  await fixed(cache.after);
  for (const history of histories) {
    await moved(history, history.prompts, false);
    if (history === histories.at(-1)) break;    // 最后一条历史不取输出
    await moved(history, realms.outputs(history), true);
  }
  list.sort(lorebooks.compare);
  let index = 0;
  return {
    async middle(i) {
      const items = [];
      for (; index < list.length; index++) {
        const u = list[index];
        if (i === histories.length - 1 || u.layer + histories.length >= i + 100) break;
        items.push(u);
      }
      await inject(items);
    },
  };
}
```

用 `u.layer + histories.length >= i + 100` 决定某条世界书落在哪一层历史，
即**越靠后的历史承载 layer 越高的条目**，实现「越近的上下文越细节」的效果。

> **必须先 `list.sort(lorebooks.compare)` 才能用这个滑窗**：
> `middle` 里是**顺序消费** `list`（`index` 只增不减），
> 依赖列表已按 `layer*10000 + priority` 升序排好。

> 说明：`default` 模式**没有真正的 token 预算裁剪**，
> 「预算」实际由 layer 阈值 100 与 `visited` 去重间接约束；只有 `layered` 有滑窗语义。

## 6. 按 role 分发注入

```ts
async function inject(items: PresetItem<Lorebook>[]) {
  const groups = arrUtils.groupSerial(items, u => u.role);   // 按 role 连续分组
  for (const group of groups) {
    const contents: string[] = [];
    for (const item of group.items) {
      const content = await models.convert(converts, item.content ?? '', {
        role: group.key, type: 'output', history: null,
      });
      contents.push(content);
    }
    const content = arrUtils.join(contents, '\n\n');
    switch (group.key) {
      case 'knowledge': ...caller(...);  break;
      case 'system':    system(content); break;
      case 'assistant': assist(content, null); break;
      case 'user':      prompt(content); break;
    }
  }
}
```

两个重要细节：

1. **世界书内容也会过 converts 链**（即宏与正则同样作用于世界书）。
   源码注释明确写了「世界书也会经过转化」。
2. `arrUtils.groupSerial` 是**按连续相同键分组**，不是全局 groupBy。
   所以同 role 的条目需要相邻才会合并成一条消息。

### knowledge 角色：伪装成工具调用

这是全项目最巧妙的设计之一。`role: 'knowledge'` 的世界书**不直接进消息列表**，
而是伪装成一次 `get_knowledge` 工具调用的返回值：

```ts
case 'knowledge':
  simulation += 1;
  caller('', null, [{
    index: 0,
    id: `${name(simulation)}l`,
    name: models.engines.knowledge.info.name,          // 'get_knowledge'
    arguments: models.engines.knowledge.args({ type: 'lorebook' }),
    result: content,
  }]);
  break;
```

`models.engines.knowledge` 是一个**虚拟工具签名**，不属于任何 provider：

```ts
// src/models/client/engine.ts
knowledge: {
  info: { name: 'get_knowledge', description: 'get knowledge. return empty if current knowledge is injected. ' },
  schema: { type: 'object', properties: { type: { type: 'string', description: 'the type of knowledge. ' } } },
  args: (args: { type: string }) => JSON.stringify(args),
},
```

好处是：

- 复用工具调用通道，**无需为「知识注入」单独设计消息格式**；
- 世界书与记忆（memories）走同一套表示，模型看到的是统一形态；
- `description` 里那句 "return empty if current knowledge is injected"
  是在提示模型不要重复调用。

> laotu：这只是个小巧思，工具调用天然带知识背景的语义，作为主动知识注入很合适。好处其实是不需要依赖ai对上下文的理解，进行强行注入

## 7. 与记忆（Memories）的对照

记忆的注入用的是**同一套技巧**，只是 `type: 'memory'`：

```ts
// src/memories/client/processer.ts（注入时）
callings.push({
  index,
  id: `${name(simulation++)}m`,
  name: models.engines.knowledge.info.name, // 同样是 get_knowledge
  arguments: models.engines.knowledge.args({ type: 'memory' }),
  result: arrUtils.join(items, '\n', (u) => `- ${u.name}: ${u.text}`),
});
```

区别在于：

|      | 世界书                     | 记忆                           |
| ---- | -------------------------- | ------------------------------ |
| 归属 | 预设条目                   | 故事条目                       |
| 触发 | 内容/变量/向量匹配         | LLM 主动调用 `get_memory` 工具 |
| 时机 | 每次 prompt 组装时         | 生成后按记录回填到历史         |
| 缓存 | `properties.lorebooks`（存 id 数组） | `properties.memory`（存 entryId 数组） |

> 两者都走 `get_knowledge` 伪调用，**`role: 'knowledge'` 的世界书与记忆在模型眼里长得一样**，
> 区别只在那句 `arguments` 里的 `type` 是 `'lorebook'` 还是 `'memory'`。

## 9. 已知问题与注意点（`1.3.5.0` 复核）

1. ~~**vector matcher 的疑似 bug**~~ → ✅ **已修复，且机制已重构**。
   索引写 `entry.id`、比对 `lorebook.id`，两侧一致；同时检索从「匹配器自己跑」
   改为「LLM 调 `get_lorebook` 工具跑」。详见本篇 §3「vector 的语义」。
   > laotu：确实是bug，已改。AI查的比我细致得多。
2. **RAG 未配置时的行为现在是明确的**：`rags.create()` 返回 `null`，
   vector 型世界书不建索引、不匹配；而需要用到向量的**工具**会自己给出提示：

   ```ts
   // src/lorebooks/client/tool.ts —— get_lorebook
   const cache = lorebooks.cache(realm);
   if (!cache.rag) return 'warn: RAG is not enabled';   // 明确回给模型
   ```

   所以「静默失效」现在只发生在**世界书注入**这一侧，工具调用侧是有反馈的。
   > laotu：其实不是，我允许rags不配置，但是各处用到rags时应该有自己的行为。比如我会在工具调用返回时给上rag is not enabled。毕竟不是所有人都有rag环境。
3. **`matchers.content` 只匹配当前消息**：历史消息的世界书激活依赖
   先前 `output` 阶段写入的 `properties.lorebooks` 缓存；
   若历史被外部导入或手工编辑过，属性可能缺失，此时会现场重算。
   > laotu：这确实是个问题，历史编辑后应该把编辑的缓存清空。后面看看怎么优化。
4. **`always` 型不参与匹配**，因此它不受 `expression` 中关键词的影响，
   只看 `last` 决定前置还是后置（外加 `macro` 绑定这一层开关，见本篇 §3）。
5. **默认模式无 token 预算**：条目很多时会无限膨胀上下文，
   需要靠预设作者自己用 layer/priority 与匹配条件控制。
   > laotu：依靠总结，但是这个项目确实没有滑动窗口，后面看看是否需要。作为角色扮演应用确实不适合普通agent那一套滑动窗口。
6. **⭐ vector 检索现在是「模型决定何时检索」**。这带来一个新的使用约束：
   如果预设没有给模型 `get_lorebook` 工具（或它被禁用），
   **所有 vector 型世界书永远不会被激活** —— 因为没有任何地方会去查向量库了。
   这是与旧版最大的行为差异，迁移旧预设时要注意。
7. **`get_lorebook` 的 `limit` / `min_relevance` 默认值来自全局 RAG 设置**
   （`useRagState`），但 **JSON Schema 里的 `default` 只用作文档说明**，
   真正生效的是 `invoke` 解构时的兜底值 `limit = 3` / `min_relevance = 0.3`
   —— 两者如果不一致，模型看到的是前者、实际用的是后者。

## 10. 本章速查

- 想让某段设定常驻？用 `always` 匹配器，`last` 决定放前面还是后面；
  还可以用 `expression.macro` 绑一个宏当总开关。
- 想按关键词触发？用 `normal`，记住「组间 AND、组内 OR」。
- 想按变量/日期触发？用 `variable` / `event`。
- 想按语义相似触发？用 `vector`，**同时必须让模型能用 `get_lorebook` 工具**。
- 想控制插入位置？调 `layer`（<100 在用户消息前，>=100 在后）。
- 想控制同层顺序？调 `priority`。
- 想让内容对 AI 呈现为「系统指令」？把 `role` 设为 `system`。
- 默认 `role: knowledge` 会以 `get_knowledge` 工具结果的形式注入。
- 调 RAG 的命中数/相似度阈值？在**设置页的 RAG 分区**（`useRagState`），
  不在世界书条目里。
