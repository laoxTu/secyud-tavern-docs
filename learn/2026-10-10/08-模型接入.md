# 08 · 模型接入

项目支持三种模型供应商：**OpenAI、DeepSeek、Anthropic**。
接入方式是「双层引擎」抽象，前后端各有一个同名注册表 `model-engine`。

> 📌 本篇已按 `1.3.5.0` 复核。主要变化：
> 新增 **token 预算（`config.token` + usage 累计 + 超限告警）**、
> DeepSeek 的 **thinking / reasoning_effort** 配置、
> `ModelInput.summaries` 现在会被 Context Viewer 真正消费、
> 以及确认了「密钥只在服务端解密」这条链路。

---

## 1. 数据模型

```ts
// src/models/index.ts
export interface Model extends Entity, Properties {
  name: string;         // 展示名
  stream: boolean;      // 是否流式
  engine?: string;      // 引擎 id：openai / deepseek / anthropic
  builder: string;      // 提示词构造器：default / layered
  iterations: number;   // 单轮最大工具循环次数
  key?: string;         // 加密后的 API Key
  iv?: Buffer;          // AES 初始向量
  properties?: Record<string, any> & ModelProperty;
}

export interface ModelProperty {
  retry: { interval: number; max: number };   // ⭐ 现在唯一的内置属性
}
export interface ModelSetting { model: NameValue | null; }

export interface TokenUsage {
  prompt: number;
  output: number;
}
```

> ⚠️ 与旧笔记的两处差异：
> - **`Model` 不再 `extends DisableDto`** —— 表里也没有 `disabled` 列。
>   模型没有「条目级禁用」这一层，只有故事/设置里选中的那个才生效。
> - `iterations` 是**必填** `number`（schema 有 `default(20)`），不是 `number?`。

数据库表 `model`（`src/models/server/schema.ts`）：

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `id` | text PK | UUID |
| `name` | text | 有 `model_name_idx` 索引 |
| `engine` | text | 引擎 id |
| `builder` | text NOT NULL default `'default'` | `default` / `layered` |
| `stream` | boolean default `true` | |
| `key` | text | 加密的 API Key |
| `iterations` | integer default `20` | 工具循环上限 |
| `iv` | blob | AES 向量 |
| `properties` | json default `{}` | 动态属性容器 |

供应商专属配置全部塞进 `properties` 的两个键：

```ts
models.names.config  = 'config';   // 连接配置（url、format、token 预算等）
models.names.options = 'option';   // ⚠️ 注意是单数 'option'
```

> ⚠️ `models.names.options` 的值是 **`'option'`（单数）**，
> 而 getter 叫 `options`、类型叫 `Model` 的字段是 `properties`。
> 三个词长度不同很容易写错，抄代码时注意。

## 2. 双层引擎抽象

这是理解模型接入的关键：**同名注册表，前后端各一个，职责不同**。

| 层 | 文件 | 职责 |
| --- | --- | --- |
| 前端引擎 | `src/models/client/engine.ts` | **格式**：把回调组装成供应商格式；解析流式事件 |
| 后端引擎 | `src/models/server/engine.ts` | **传输**：调用 SDK，返回流或完整响应 |

### 前端引擎

```ts
// src/models/client/engine.ts
export interface ModelEngine extends Registerable {
  configComponent: React.ComponentType;                                  // 配置 UI
  configureObject: (data: FormData, model: Partial<Model>) => Partial<Model>; // 表单 → 配置
  result: (ctx: ModelResultContext) => Promise<void>;                     // 解析输出
  prompt: (ctx: ModelPromptContext) => Promise<ModelInput>;               // 组装输入
}
```

`prompt` 收到的是「回调集合」（`ModelInjectContext`），
它负责把这些回调翻译成具体供应商的消息数组：

```ts
prompt: (content: string) => void;                              // user 消息
assist: (content, output) => void;                              // assistant 消息
system: (content) => void;                                      // system 消息
caller: (content, output, callings) => void;                    // 工具调用
```

`result` 把流式 delta 写进 `RealmOutput`（`content` / `thought` / `callings`），
并在结束时置 `ctx.stopped`。

### 后端引擎

```ts
// src/models/server/engine.ts
export interface ModelEngine extends Registerable {
  generate(context: ModelGenerateContext): Promise<AsyncIterable<any> | Record<string, any>>;
}

async function generate(model: Model, input: any, signal: AbortSignal) {
  const name = checker.notNullOrWhitespace('engine', model.engine, 'model');
  const engine = registry.records[name];
  checker.notNullEntity(name, engine, 'model.engine');

  const apiKey = model.key && model.iv ? hasher.decrypt(model.key, model.iv) : '';
  return await engine.generate({ model, apiKey, signal, input });
}
```

注意 **API Key 在此处解密**，仅在内存中明文存在。

## 3. 三个供应商实现

### OpenAI

```ts
// src/models/openai/server/engine.ts
const client = new OpenAI({ baseURL: config.url, apiKey });

if (config.format === 'responses') {
  return await client.responses.create({
    ...options, ...input, stream: model.stream,
    ...jsonUtils.parse(config.extras, {}),
  }, { signal });
} else {
  return await client.chat.completions.create({
    ...options, ...input, stream: model.stream,
  }, { signal });
}
```

**支持两种 API 格式**：

- `chat` —— 传统 `chat.completions`，消息数组 + `tools` / `tool_calls`。
- `responses` —— 新版 `responses` API，`instructions` + `function_call` / `function_call_output`。

前端引擎相应地有两套组装逻辑（`promptChatCompletion` / `promptResponses`）。

**流式事件解析**（前端 `result`）识别：

- `response.output_text.delta` → 正文
- `response.reasoning_summary_text.delta` → 思考内容
- `delta.tool_calls` → 按 `index` 归并并拼接 `arguments`
- `finish_reason === 'stop'` 或 `response.completed` → `ctx.stopped = true`

### DeepSeek

复用 `openai` 包，只换 `baseURL: 'https://api.deepseek.com'`。

**前端引擎不再直接复用 OpenAI 的**（旧笔记说「直接复用 `openais.engine.prompt`」已过时）：
它有自己的 `prompt`（为了注入 `reasoning_content`）和 `Content` 配置组件，
只有 `result` 仍然是 `openais.engine.result`：

```ts
export const engine: ModelEngine = {
  id: deepseeks.name,
  configComponent: Content,
  configureObject(data, model) { /* … */ },
  async prompt(ctx) {
    // …
    messages.push({
      role: 'assistant', content, tool_calls: [...],
      // ⭐ 把上一轮的思考回传给 DeepSeek（thinking 开启时）
      ...(options.thinking.type === 'enabled'
        ? { reasoning_content: output ? (output?.thought ?? '') : 'user generated calling' }
        : {}),
    });
  },
  result: openais.engine.result,   // 只有这里复用
};
```

**DeepSeek 的选项模型**（`src/models/deepseek/index.ts`）：

```ts
export interface DeepseekOptions {
  model: string;                              // 'deepseek-flash' | 'deepseek-pro'
  thinking: { type: 'enabled' | 'disabled' }; // ⭐ 思考模式开关
  reasoning_effort: string;                   // 'high' | 'max'
  temperature: number;
  top_p: number;
  max_tokens: number;
  logprobs: boolean;
  top_logprobs: number;
}
export interface DeepseekConfig {
  token: number;                              // ⭐ token 预算
}
```

后端做了一些字段清理（`src/models/deepseek/server/engine.ts`）：

```ts
if (!options.logprobs) parameter.top_logprobs = undefined;
if (!options.max_tokens) parameter.max_tokens = undefined;
if (options.thinking.type === 'disabled') parameter.reasoning_effort = undefined;
```

> ⚠️ 这三行是「按值清理」，不是「按白名单构造」：
> `options` 是**整个对象**被展开进请求体的（`...options`），
> 所以 `thinking` / `logprobs` 这两个**非 OpenAI 标准字段也会被发出去**。
> DeepSeek 服务端目前容忍它们，但换到别的 OpenAI 兼容网关时可能被拒。
>
> UI 上还有一处细节：`logprobs` 与 `top_logprobs` 两个输入是
> **`disabled` 且 `logprobs: false` 硬编码**，也就是这两个功能当前**没有真正开放**。

### Anthropic

用 `@anthropic-ai/sdk` 的 `anthropic.messages.create`，支持 `config.extras` 合并。

它的 `prompt` 是三者里最特别的，处理 **thinking 签名（signature）**：

```ts
assist: (content, output) => {
  const message: Anthropic.MessageParam = output?.properties?.['signature']
    ? {
        role: 'assistant',
        content: [
          { type: 'text', text: content },
          { type: 'thinking', thinking: output.thought, signature: output.properties['signature'] },
        ],
      }
    : { role: 'assistant', content };
  messages.push(message);
},
```

`signature` 是 Anthropic 扩展思考的**完整性凭据**：多轮对话里要原样回传，
否则 API 会拒绝。它在流式解析中被**逐片累加**（`signature_delta`），
存在 `output.properties['signature']`，非流式则直接取自 `delta.signature`。

`caller` 里有一句值得注意的注释与实现：

```ts
caller: (content, output, callings) => {
  const aiParams: Anthropic.ContentBlockParam[] = [];
  // 即便没有工具调用，思考和ai回复也要注入
  messages.push({ role: 'assistant', content: aiParams });
  if (content) aiParams.push({ type: 'text', text: content });
  if (output?.properties?.['signature']) aiParams.push({ type: 'thinking', ... });
  if (!callings.length) return;      // ⚠️ 已经 push 过一条 assistant 消息了
  // …工具调用与 tool_result 装进一条 user 消息
},
```

> ⚠️ **Anthropic 分支会无条件 push 一条 assistant 消息**（哪怕 `content` 为空、`callings` 为空），
> 而 OpenAI / DeepSeek 分支在 `if (content)` 为假时不会 push。
> 也就是说同一次生成在三家供应商下产出的消息序列**长度可能不同**。
> 这是 Anthropic 对「assistant / user 必须交替」的要求所致，但读代码时容易误判成 bug。

## 4. 密钥加密

```ts
// src/utils/server/hasher.ts（概要）
hasher.create(key)      // AES-128-CBC 加解密
hasher.generateKey(text, salt)  // pbkdf2Sync(text, salt, 100000, 16, 'sha256')
hasher.encrypt / decrypt        // 模块级单例，读 process.env.SECRET_KEYS / SECRET_SALT
```

> ⚠️ 两个默认值兜底：`process.env.SECRET_KEYS ?? 'secyud'` / `SECRET_SALT ?? 'secyud'`
> —— 也就是说**没配 `.env` 时并不会崩，而是用 `'secyud'` 这个公开常量当密钥**。
> 排查「换了机器解不开 Key」时要先确认 `.env` 是否真的被加载了。
> `hasher` 是**模块级单例**：`SECRET_KEYS` 在模块首次求值时读取一次，之后改环境变量无效。

Repository 中的处理（`src/models/server/repository.ts`）：

- `update()` 若存在 `model.key`，生成 **16 字节随机 iv**（`crypto.randomBytes`）并加密，
  同时**删除缓存**（`cache.delete('model_<id>')`）。
- `get()` 走进程内缓存 `model_{id}`，**TTL 5 分钟**。
- `list()` 只投影 `{ id, name }`，支持 `fuzzy` 的 `LIKE`。

> 📌 「创建时不能带 Key」这句**已经不在 repository 里了**，而是移到了路由层：
>
> ```ts
> // src/models/server/api.ts —— POST /api/models
> const model: Model = await request.json();
> model.key = undefined;
> model.iv = undefined;
> const id = await models.repository.create(model);
> ```
>
> 语义没变（创建时不接受 Key），但位置变了：
> **`repository.create()` 本身不再做这个清理**，直接调 repository 的代码要自己注意。

### 密钥的完整生命周期（复核确认）

```text
用户在设置页输入 api_key
  → POST /api/models 或 PUT /api/models/{id}（明文走 HTTPS）
  → repository.update(): crypto.randomBytes(16) 生成 iv
                        hasher.encrypt(key, iv)
                        ↓
                     仅 key(密文) + iv 落库
                        ↓
生成时（服务端）：
  models/server/engine.ts
    const apiKey = model.key && model.iv ? hasher.decrypt(model.key, model.iv) : '';
    return await engine.generate({ model, apiKey, signal, input });
                        ↓
                    SDK 调用，明文只在服务端进程内存中存在
```

> **客户端不参与加解密**：`src/models/client/proxy.ts` 只是转发请求，
> 全项目 `crypto` 的引用只在 `src/utils/server/hasher.ts` 与
> `src/models/server/repository.ts`（生成 iv）两处。
> 所以「密钥只在服务端解密」这条结论**成立**，可以按它做威胁建模。

> ⚠️ `.env` 里的 `SECRET_SALT` / `SECRET_KEYS` 由 `pnpm prepare` 生成，
> **一旦丢失就无法解密已存的 API Key**。
> 另外它们由 `strUtils.random`（基于 `Math.random()`）生成，非密码学安全随机源。

## 5. API 端点

| 方法 | 路径 |
| --- | --- |
| GET / POST | `/api/models` |
| GET / PUT / DELETE | `/api/models/{id}` |
| POST | `/api/models/{id}/clone` |
| POST | `/api/models/{id}/engine/generate` |

`generate` 是核心端点：`model.stream` 为真时用 `sseUtils.pack(result)`
包装成 `ReadableStream` 并以 `text/event-stream` 返回，否则返回 JSON。

前端 `handleResponse` 因 `Content-Type` 非 JSON 而原样放行 `Response`，
供 `sseUtils.read` 消费 —— 这是流式链路能成立的前提。

## 7. token 预算（新增）

`1.3.4.0` 前后加进来的机制。它是**三级配合**，只看其中一处会看不懂：

### ① 配置：每个引擎的 `config.token`

```ts
export interface OpenAIConfig {
  extras: string;
  url: string;
  format: 'chat' | 'responses';
  token: number;        // ⭐ 预算，默认 100000
}
export interface DeepseekConfig { token: number; }
// Anthropic 目前没有这一项
```

UI 上的字段标签是 `model.token_limit`，`min={0}`（0 表示不检查）。

### ② 记录：引擎在 `result` 里累计 usage

```ts
// src/models/openai/client/engine.tsx
const usage = event.response.usage;            // 流式：response.completed 事件
if (usage) {
  const tu: TokenUsage = {
    prompt: usage.input_tokens,
    output: usage.output_tokens,
  };
  utils.setProperty(output, 'usage', tu);      // ⭐ 挂在 RealmOutput.properties.usage
}
```

三家各自映射字段名（`input_tokens`/`output_tokens` vs `prompt_tokens`/`completion_tokens`），
最终都归一成 `{ prompt, output }`。

### ③ 检查：下一次 `prompt` 时比对并告警

```ts
// src/models/openai/client/engine.tsx
async prompt(ctx) {
  const usage = utils.getProperty<TokenUsage>(
    realms.outputs(ctx.histories.at(-2))?.at(-1),   // ⭐ 上一轮的最后一段输出
    'usage',
  );
  if (config.token && usage && config.token <= usage.prompt + usage.output) {
    toast.warning('token is over limit. use summary to compress', { richColors: true });
  }
  // …
}
```

四个要点：

- 读的是 **`histories.at(-2)`**（倒数第二条历史）的**最后一段**输出。
  `at(-2)` 而不是 `at(-1)`，是因为 `at(-1)` 是本次正在构造的这一轮。
- 判据是 `config.token <= prompt + output`，即**上一轮的用量**（不是预估本轮）。
- **只告警，不阻断**。文案直接建议「用总结来压缩」——
  呼应 [06 篇](./06-故事与领域.md) §5 的「上下文截断靠 `summary` 标记」。
- ⚠️ **这条 toast 的文案是硬编码英文**（`'token is over limit. use summary to compress'`），
  没有走 i18n —— 与项目其他地方的 `t('...')` 风格不一致。

> 📌 这实际上回答了旧笔记里「`ModelInput.summaries` 的消费者是谁」之外的另一半问题：
> 上下文预算**现在有了一个（提示性的）出口**，
> 但它与 `summaries`（给 Context Viewer 看的）是两套互不相干的机制。

## 8. builder 的两种构造器

`model.builder` 有 `default` 与 `layered` 两个选项（UI 在
`src/models/client/setting.tsx` 的 `['default','layered']`）。

- **default**：世界书按 layer 阈值 100 简单划分注入位置。
- **layered**：世界书按「滑窗」分配层级，越靠后的历史承载 layer 越高的条目。

> 注意：`builder` 字段本身在 `src/models/**` 内**只是下发**，
> 真正的消费点在世界书注入器（`src/lorebooks/client/realm.ts` 的
> `create()` 里 `switch (builder)`）。这是模块间通过通用字段解耦的一个例子。
>
> 作者的补充说明：`layered` 原本设计成可注册的构造器，但实际是个试验性分支，
> **一般只用 `default`**。两种模式的世界书时序差别见
> [05 篇](./05-世界书.md) §5（`layered` 没有 `before`/`behind` 钩子）。

## 9. 某个模型的完整调用链

```
用户输入
  └─ models.processers.generate()
       ├─ prompt() → 各 Processer 填 converts/injects
       │    └─ engine.prompt(context)          ← 前端引擎，组装成 messages
       │         ├─ 读上一轮 usage 比对 config.token → 超限则 toast.warning
       │         └─ 返回 { input, summaries }
       │
       ├─ models.proxy.engine.generate(model.id, input, controller.signal)
       │    └─ POST /api/models/{id}/engine/generate   （SSE 或 JSON）
       │         └─ 服务端 engines.generate()
       │              ├─ 校验 engine 存在
       │              ├─ hasher.decrypt(key, iv)       ← 解密 API Key
       │              └─ engine.generate({ model, apiKey, signal, input })
       │                   └─ OpenAI / DeepSeek / Anthropic SDK
       │
       └─ for await chunk of sseUtils.read(response.body)
            └─ engine.result(context)         ← 前端引擎，解析 delta
                 ├─ 写入 output.{content, thought, callings}
                 ├─ 记录 output.properties.usage ← token 用量
                 └─ ctx.stopped? → 终止工具循环
```

> 两条与 token 相关的边值得单独记住：
> **usage 是在 `result` 阶段写进 `output.properties` 的**，
> 而**检查发生在下一次的 `prompt` 阶段** ——
> 也就是说预算判断永远是「滞后一轮」的，且依赖输出被成功落库。

## 10. 已知问题（`1.3.5.0` 复核）

1. ~~非流式分支的 `stream` 实参~~ → ✅ 已修复为 `generate(false, response)`
   （详见 [07 篇](./07-生成管线.md) §10）。
2. **重试语义混淆**：`retry` 同时用于「网络错误重试」与「流式卡死重试」。
   作者认为对用户而言等价，属取舍而非缺陷。
3. **`ModelInput.summaries` 的消费者**：现在确认是 `Context Viewer`
   （`src/stories/client/realms/feature.tsx` 的 `context-viewer`，
   `sequence: 1000`）。构建 `summaries` 时有三条必须同步的调用：
   `prompt` / `assist` / `system` 各 push 一次，工具调用则统一走
   `tools.summary(callings, items)` —— **三家引擎各调一次，漏一个就会出现预览偏差**。
4. **DeepSeek 只有 `result` 复用 OpenAI 前端引擎**（`prompt` 已独立），
   原因是需要注入 `reasoning_content`。若 DeepSeek 的 reasoning 字段语义变化，
   要改的是它自己的 `prompt` 与共用的 `resultChatCompletion`。
5. **⚠️ `token` 预算只对 OpenAI / DeepSeek 生效**，Anthropic 引擎的
   `config` 里没有 `token` 字段，也没有 usage 检查 —— 用 Anthropic 时没有超限提醒。
6. **⚠️ token 超限提示是硬编码英文**，未走 i18n（见本篇 §7）。
7. **⚠️ 请求体是「展开 + 局部清理」而非白名单构造**：
   `{ ...options, ...input, ... }` 会把 `thinking` / `logprobs` 这类
   非标准字段也发给 OpenAI 兼容端点，换网关时可能被拒。

## 11. 本章速查

- 想加一个新供应商？写 `server/engine.ts`（传输）+ `client/engine.tsx`（格式），
  在两侧的 `index.ts` 里 `register`。
- API Key 存哪里？`model.key`（AES 加密）+ `model.iv`，`.env` 提供主密钥。
- 为什么生成会走到 `/api/models/{id}/engine/generate`？因为密钥只在服务端解密。
- 想换默认模型？设置页星标，或直接在故事上指定。
- 想控制上下文成本？`config.token`（告警阈值）+ `history.summary`（真正的截断开关）。
- 想加供应商专属配置？塞进 `properties.config` / `properties.option` 两个键，
  **不要加数据库列**（源码注释明确说了这个取向）。
