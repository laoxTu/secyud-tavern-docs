# 10 · 任务与调度

> ⭐ 本篇是 `1.3.5.0` 复核时**新增**的章节。
> `tasks` 是 `1.3.3.0 → 1.3.4.0` 之间长出来的模块，
> 旧笔记成文时它还不存在，所以 02–19 篇里几乎没提它。

`tasks` 在项目里是一个**双重身份**的存在，这是理解它的关键：

| 身份 | 内容 | 位置 |
| --- | --- | --- |
| **一套通用框架** | `TaskRunner` 抽象类（并发池 + 生命周期 + 取消） | `src/tasks/index.ts` |
| **一个能力模块** | `TaskManager`、`task_provider` 注册表、两张表、菜单页、4 个 API | `src/tasks/server/**`、`src/tasks/client/**` |

所以它既被 `src/tools/client/task.ts` 继承（工具并行执行），
又自己有一条完整的「数据库 → API → 菜单」链路（后台下载等长任务）。

---

## 1. 要解决什么问题

在它出现之前，项目里有几处需求没有被抽象覆盖：

- **「起一个后台活儿，然后告诉用户进度」**：
  ComfyUI 模型下载要跑几分钟，不能挂在 HTTP 请求里。
- **「同一趟里并发做多件事」**：一轮 AI 回复可能同时调 5 个工具，
  串行会让等待时间线性叠加。
- **「重试一次，且保留上一次的记录」**：下载失败想重来时，
  旧结果不该被覆盖掉。
- **「取消一个正在跑的东西」**：`AbortController` 有了，
  但缺一个统一的「谁持有它、谁负责清理」的容器。

`TaskRunner` 就是这四个需求的交集：**一个有上限的并发池，
每个任务有状态机、可取消、可重试、且每次尝试都被记录**。

## 2. 数据模型

```ts
// src/tasks/index.ts
export type TaskStatus =
  'pending' | 'running' | 'completed' | 'failed' | 'cancelled';

export interface TaskProgress {
  progress: number;          // ⚠️ 见 §8 第 1 条：目前没有任何人写入它
}

interface TaskBase {
  attempt: number;           // 尝试次数（重试会 +1）
  queue?: number | null;     // 入队时间戳
  start?: number | null;     // 本次开始时间戳
  finish?: number | null;    // 本次结束时间戳
  result?: string | null;    // 成功信息或失败原因（序列化后的错误）
  status: TaskStatus;
}

/** 当前任务状态 */
export interface Task<T = any> extends Entity, Properties, TaskBase {
  name: string;              // 展示名，如 `download <model.code>`
  args: T;                   // 任意参数（含 provider）
}

/** 状态归档：每次重试前把旧状态存一份 */
export interface TaskHistory extends TaskBase {
  masterId: string;          // → task.id
}

/** 运行中状态：多持有一个 AbortController */
export interface TaskInfo<T = any> extends Task<T> {
  controller: AbortController;
}
```

**`task` / `task_history` 是 `realm_history` 的同一种套路**：
主表存「当前」，历史表存「每次变更的快照」，主键都是 `masterId + 序号`。
区别是这里的序号是 `attempt`（尝试次数），而 realm 那边是 `sequence`。

```ts
// src/tasks/server/schema.ts
export const taskSchema = sqliteTable('task', {
  id: text('id').primaryKey(),
  name: text('name').notNull(),
  args: json<Record<string, any>>('args').notNull(),
  progress: real('progress'),        // ⚠️ 列在，但没人写
  attempt: integer('attempt').notNull(),
  queue: integer('queue'),
  start: integer('start'),
  finish: integer('finish'),
  result: text('result'),
  status: text('status').notNull(),
  properties: json('properties').default({}),
}, (t) => [index(`task_name_idx`).on(t.name)]);

export const taskHistorySchema = sqliteTable('task_history', {
  masterId: foreignKey('master_id', () => taskSchema.id).notNull(),
  attempt: integer('attempt').notNull(),
  // …与 TaskBase 同构
}, (table) => [primaryKey({ columns: [table.masterId, table.attempt] })]);
```

> 📌 `task_history` 没有 `name` / `args` / `properties` —— 它只记「状态变迁」，
> 任务的身份在主表上。所以 `history.list(id)` 读出来的是**时间线**，不是完整快照。

## 3. `TaskRunner`：并发池与状态机

```ts
export abstract class TaskRunner<TArgs = any> {
  protected pending: Task[] = [];                    // 等待队列（FIFO）
  protected running: Map<string, TaskInfo> = new Map();
  protected mutex = new Mutex();                     // 保护上面两者的简单锁

  constructor(protected max: number = 8) {}          // ⭐ 默认并发上限 8

  /** 子类实现真正的活儿 */
  protected abstract execute(task: TaskInfo<TArgs>): Promise<string | undefined>;

  async create<T extends TArgs = TArgs>(name: string, args: T) { /* 入队 + 尝试开工 */ }
  async start(): Promise<TaskInfo | undefined> { /* 从队首取一个开始跑 */ }
  async restart(id: string) { /* 取消当前 + attempt+1 + 重跑 */ }
  async delete(id: string) { /* 取消/移除 */ }
}
```

### 生命周期

```text
create(name, args)
  └─ queue(task)          : pending.push, queue = now, status = 'pending'
       └─ start()         : 取队首 → running.set(id, {...task, controller}) → run(task)

run(task)
  ├─ status = 'running', start = now
  ├─ execute(task)                       ← 子类实现，拿到 controller
  │    ├─ then  → success(): status = 'completed', result = 返回值
  │    └─ catch → failed() : status = 'failed',    result = errors.serialize(err)
  └─ finally → finish(): running.delete, finish = now, → start()   ← ⭐ 递归启动下一个
```

四个设计细节：

1. **`execute` 的返回值就是 `result`**。`TaskManager` 让它永远返回 `'success'`，
   而工具那个池子也返回 `'success'` —— 真正的信息在别处（工具写 `toolcall.result`）。
2. **`finish()` 末尾再次 `start()`**：这就是「池子会自动填满」的原因。
   一次 `create` 可能引发一串连锁启动（每完成一个就补一个）。
3. **`abort` 用 `BusinessError` 当 reason**，不是字符串：

   ```ts
   task.controller.abort(new BusinessError('canceled', `error.canceled`));
   origin.controller.abort(new BusinessError('restart', `error.restart`));
   ```

   这样「取消」与「重试」在 `signal.reason` 上可区分，
   而错误本身也带 `code` 可供 i18n（虽然这里没人消费它）。
4. **`delete` 的语义分三种情况**：

   ```ts
   async delete(id: string) {
     await this.mutex.lock(async () => {
       const index = this.pending.findIndex((u) => u.id === id);
       if (index >= 0) {
         this.pending[index].status = 'cancelled';
         this.pending.splice(index, 1);
         return;                                     // ① 还没开始：直接移除
       }
       const task = this.running.get(id);
       if (task) {
         task.status = 'cancelled';
         task.controller.abort(new BusinessError('canceled', `error.canceled`));
         this.running.delete(id);                    // ② 正在跑：abort + 移出
       }
     });
     await this.start();                             // ③ 顺手补一个
   }
   ```

   ⚠️ 注意 `running.delete(id)` 之后 `execute` 的 `finally` 仍会调 `finish(task)`，
   于是 `finish` 会**再 delete 一次**（幂等）并再次 `start()`。
   不会出错，但一次取消会触发两次 `start()`。

### `Mutex`：单线程下的简单锁

```ts
// src/utils/mutex.ts
export class Mutex {
  queue: Action[] = [];
  current: Action | undefined;

  private async run() {
    this.current = this.queue.shift();
    while (this.current) {
      try { await this.current.execute(); this.current.resolve('success'); }
      catch (err) { this.current.reject(err); }
      this.current = this.queue.shift();            // ⭐ 串行消费
    }
  }

  lock(action: () => Promise<void>) {
    return new Promise((resolve, reject) => {
      this.queue.push({ execute: action, resolve, reject });
      if (!this.current) this.run();                // ⭐ 空闲才启动驱动循环
    });
  }
}
```

`1.3.5.0` 新增的工具（`tests/utils/mutex.test.ts` 覆盖了它）。
它注释里写得很清楚：「一个简单的锁，适用于单线程」——
**它保护的是 `await` 之间的交错，不是真并发**。
对 `pending` / `running` 这两个内存结构来说足够了。

> ⚠️ 一个值得注意的性质：`lock()` 返回的 Promise 在**前一个 action 抛错时**
> 只 reject 自己那一个，`run()` 的 `while` 继续往下走。
> 也就是说**一个 action 失败不会卡住后面的**。这正是 `TaskRunner` 需要的语义。

## 4. `TaskManager`：落库与 provider 分发

```ts
// src/tasks/server/manager.ts
export interface TaskArgs {
  provider: string;                                    // ⭐ 约定字段
}

export interface TaskProvider<T = any> extends Registerable {
  execute(args: T, controller: AbortController): Promise<void>;
}

export const registry = getRegistry<TaskProvider>('task_provider');

export class TaskManager extends TaskRunner<TaskArgs> {
  constructor() { super(8); }

  /** 按 args.provider 找到执行者 */
  protected async execute(task: TaskInfo<TaskArgs>) {
    const provider = registry.record(task.args.provider);
    await provider?.execute(task.args, task.controller);   // ⚠️ 找不到就静默成功
    return 'success';
  }

  /** 每次启动都写库 */
  protected async run(task: TaskInfo<TaskArgs>) {
    await super.run(task);
    await repository.update(task.id, {
      start: task.start, status: task.status, attempt: task.attempt,
    });
  }

  /** 每次结束都写库 */
  protected async finish(task: TaskInfo<TaskArgs>) {
    await super.finish(task);
    await repository.update(task.id, {
      finish: task.finish, status: task.status, result: task.result,
    });
  }

  /** 重试前先归档旧状态 */
  async restart(id: string) {
    const task = this.running.get(id);
    if (task) await repository.history.add(task.id, task);   // ⭐ 归档
    await super.restart(id);
  }

  async delete(id: string) {
    await super.delete(id);
    await repository.delete(id);                              // ⭐ 连库一起删
  }

  async create<T extends TaskArgs = TaskArgs>(name: string, args: T) {
    const task = await super.create(name, args);
    await repository.create(task);                            // ⭐ 入队即落库
    return task;
  }

  get(id: string) {
    return this.running.get(id);                              // ⚠️ 只查内存
  }
}

export const manager = getSingleton('task_manager', () => new TaskManager());
```

### 三个值得记住的点

1. **`manager` 是 `getSingleton` 而不是 `getRegistry`** ——
   这是全项目唯一一处用到 `getSingleton` 的地方（见 [03 篇](./03-模块系统.md) §2）。
   原因很实际：`TaskManager` 不是 `Registerable`，它是**有状态的容器**。
2. **「入队即落库」**：`create` 先 `super.create`（进内存队列）再 `repository.create`。
   所以即使进程马上挂掉，数据库里也已经有这条 `pending` 记录了。
3. **⚠️ `provider` 找不到时静默成功**：
   `await provider?.execute(...)` 后面无条件 `return 'success'`。
   也就是说 `args.provider` 拼错时，任务会**立刻标记为完成**，
   而没有做任何事。这与 `tools` 那边「provider 缺失只 warn」是同一种宽松取向。

### 注册一个 provider

```ts
// src/comfyui/server/importers.ts
const tasks: TaskProvider<ModelDownloadArgs> = {
  id: 'comfyui-model-download',
  async execute(args) { /* 干活，成功抛错都自己处理 */ },
};

// src/comfyui/server/index.ts —— default 导出里注册
tasks.registry.register(importers.tasks);
```

注意 `TaskProvider.execute` 的签名是 **`(args, controller)`**（两个位置参数），
而 `TaskRunner.execute` 是 **`(task)`**（一个 `TaskInfo`）——
`TaskManager` 在中间做了桥接。这是**同名不同签名**的又一处。

> 📌 `tasks` 模块的 `sequence` 是 **`99999`**，所以它在所有模块之后注册。
> 这是有意的：`task_provider` 注册表要先被 `comfyui` 填充完，
> `tasks/server` 自己反而没什么要注册的（`default` 导出是**空函数**）。

### 菜单页

PagedItemList<Task>

  ├─ ItemDescription:
  │    progress === undefined || status !== 'running'  →  t(`task.${status}`)
  │    否则                                             →  <Progress value={progress} />

## 6. 第二个子类：工具并发池

这是 `TaskRunner` 被复用得最巧的地方 —— **它不在 `tasks` 模块里**：

```ts
// src/tools/client/task.ts
class Manager extends TaskRunner<ToolCall> {
  constructor(
    protected cache: ToolCache,
    protected controller: AbortController,
  ) {
    super();                                    // ⚠️ 不传参 → max = 8
    signals.setAbort(controller.signal, () => {
      this.pending.length = 0;                  // 外部取消 → 丢弃待执行的
    });
  }

  protected async execute(task: TaskInfo<ToolCall>) { /* 见 09 篇 */ }

  protected async finish(task: TaskInfo<ToolCall>) {
    await super.finish(task);
    this.check();                               // ⭐ 供 wait() 用的收尾检查
  }

  private resolve?: (value: void | PromiseLike<void>) => void;
  private promise?: Promise<void>;

  check() {
    if (this.running.size || this.pending.length) return;
    this.resolve?.();
  }
  wait(): Promise<void> {
    return (this.promise ??= new Promise((resolve) => {
      this.resolve = resolve;
      this.check();
    }));
  }
}
```

**`wait()` 是这里最有意思的部分**：`TaskRunner` 本身**没有「等全部完成」的 API**
（它的 `start()` 是 fire-and-forget 的）。子类用「`running` 与 `pending` 同时为空」
作为完成条件，并把 `check()` 挂进 `finish()` 里。

⚠️ 但这个实现有个隐患：`wait()` 的 `check()` **只在第一次调用时执行一次**
（`this.promise ??= ...` 里的 `check()` 在 Promise 构造器内）。
之后依赖 `finish()` → `check()` 来 resolve。
如果**所有任务在 `wait()` 被调用之前就已经结束**，
那么 `new Promise(...)` 里的 `check()` 会立刻 resolve —— 这条路径是覆盖到的。

但 `resolve` 只被赋一次值，且 `promise` 被缓存 ——
**`wait()` 不能被用于「等下一批」**，只能等当前这一趟。对 `calling()` 的用法而言够了。

### 两个池子的对照

| | `TaskManager`（服务端） | `tools` 的 `Manager`（客户端） |
| --- | --- | --- |
| 继承 | `TaskRunner<TaskArgs>` | `TaskRunner<ToolCall>` |
| 上限 | `super(8)` 显式 | `super()` → 默认 `8` |
| 落库 | ⭐ 有（`task` / `task_history` 表） | 无（结果写回 `toolcall.result`） |
| provider 分发 | `args.provider` → `task_provider` | `task.args.name` → `cache.tools` |
| 取消语义 | abort controller | 清空 `pending` |
| 等待 | 无（各自独立） | `wait()` |
| 生命周期 | 进程级单例 | 每次 `calling()` 新建一个 |

> 这个对照很能说明 `TaskRunner` 抽象得是否合适：
> **两个子类的差异集中在「结果去哪」与「谁来等」，而队列、锁、状态机、
> 重试、并发上限全部复用** —— 抽象边界画得准。

## 7. 进度广播（设计完整、生产端缺失）

订阅链路是通的，但我没找到**发送方**：

```ts
// 客户端：已实现
useSse<TaskProgress>('task_progress', (target, data) => { /* 更新进度条 */ });
await signals.proxy.subscription({ type: 'task_progress', targets, action: 'set', status: 'part' });
```

```ts
// 服务端：❌ 搜遍 src/ 没有这样的调用
signals.send({ type: 'task_progress', target: task.id, data: { progress } });
```

全项目 `task_progress` 只出现在 `src/tasks/client/state.ts` 与
`src/tasks/client/content.tsx` 两处（都是消费端）。
再加上 `TaskRunner` 从不写 `task.progress`（§8 第 1 条），
结论是：**进度条目前永远不会显示，任务列表恒显示状态文案。**

这不是「坏了」，而是**功能只建好了管道**。
把生产端补上大概需要三件事：

1. `TaskRunner` 提供一个 `progress(task, n)` 方法写 `task.progress`（并持久化）；
2. `TaskManager` 里 `signals.send({ type: 'task_progress', target, data })`；
3. `TaskProvider.execute` 的签名要让 provider 能拿到上报回调
   （现在只有 `(args, controller)`）。

## 8. 已知问题（复核发现）

> ⭐ **本节有两份独立证据**：一份是我按源码静态阅读得出的，
> 另一份来自仓库自带的 [tests/TODO.md](../../tests/TODO.md) §「可疑但未确认 / tasks」
> —— 那是一份**逐条标了文件名与行号**的清单，还区分了
> 「已写断言的现状」与「纯读码推断」。
> 两边交叉比对后，我把自己独立确认过的补充进来。凡标 🔬 的是**读码可确证**的。

1. **🔬 `create()` 返回的对象永远停在 `pending`。**
   `TaskRunner` 在 `start()` 里用 `{ ...top, controller }` **造了一个副本**放进
   `running`，之后所有状态变更（`status` / `start` / `finish` / `result`）
   都写在副本上：

   ```ts
   // src/tasks/index.ts
   const top = this.pending.shift();
   task = { ...top, controller: new AbortController() };   // ⭐ 副本
   this.running.set(task.id, task);
   await this.run(task);                                    // 改的是副本
   ```

   于是 `await tasks.manager.create(...)` 拿回来的那个对象**永远是 `pending`**。
   当前调用方（`api-models.ts`）只用它的 `model.code` 做日志，
   所以没暴露出来 —— 但这是个容易误导人的返回值。

2. **🔬 达到并发上限时，`create` 会「先入队再抛错」。**

   ```ts
   async start() {
     await this.mutex.lock(async () => {
       if (this.max <= this.running.size)
         throw new BusinessError('running task over limit!');   // ⭐ 先抛
       const top = this.pending.shift();                        // 再取
       // …
     });
   }
   async create(name, args) {
     await this.queue(task);     // ⭐ 已经 push 进 pending 了
     await this.start();         // 这里抛
     return task;                // 永远执行不到
   }
   ```

   后果链：调用方收不到 id，`TaskManager.create` 里的
   `await repository.create(task)` **不会执行**（数据库里没有这行），
   但任务**仍然留在 `pending` 里**，等有位置了会被自动拉起 ——
   然后 `manager.run` 去 `repository.update` 一个不存在的 id
   （drizzle 更新 0 行不报错）。
   真实影响点：`src/comfyui/server/api-models.ts` 的下载接口会返回 500，
   而下载其实已排队。

   > 这条**行为被测试固化了**：`tests/tasks/index.test.ts` 有一条
   > 「达到上限时新任务应当留在队列，等前一个结束再自动启动」。
   > 也就是说「留在队列」是刻意的，**「先抛错导致不落库」是它的副作用**。

3. **🔬 `restart` 不把新任务写回 `running`，导致新一轮执行收不到取消。**
   我逐行追了这一条：

   ```ts
   async restart(id: string) {
     await this.mutex.lock(async () => {
       if (!this.running.has(id)) throw new BusinessError('only running task canbe restart!');
       const origin = this.running.get(id)!;
       origin.controller.abort(new BusinessError('restart', `error.restart`));
       // ⭐ 建立了新实例……
       const task = { ...origin, controller: new AbortController(), attempt: origin.attempt + 1 };
       // ⚠️ …但直接调 run，既没有 this.running.set(id, task)，
       //    也没有走 start()（start 才会写 running）
       await this.run(task);
     });
   }
   ```

   于是 `running` Map 里**仍然挂着那个已被 abort 的旧对象**。
   后果：之后任何 `manager.delete(id)` 拿到的都是旧对象，
   `task.controller.abort(...)` 作用在**已经 abort 过的信号**上 ——
   **新一轮的执行永远收不到取消**（只能等它自己跑完）。
   这条与 TODO.md 的结论一致，且我认为它是本节里**实际危害最大的一条**。

4. **🔬 `success` / `failed` 无条件覆盖 `status`。**
   `delete` 把运行中的任务标成 `cancelled`，但 `execute` 的 Promise
   稍后 settle 时：

   ```ts
   protected async success(task, result) { task.status = 'completed'; }   // ⭐ 覆盖
   protected async failed(task, err)      { task.status = 'failed'; }      // ⭐ 覆盖
   ```

   —— 状态又变回 `completed` / `failed`。
   而 `delete` 已经把数据库行删了，于是 `manager.finish` 变成一次空写。
   源码注释写的是「取消是否回档取决于内部实现，**但是已完成的任务一定不会回档**」，
   实现恰好把前半句的意思反过来了。

5. **⚠️ `progress` 字段是死的**。
   `task` 表有 `progress real` 列、`TaskProgress` 类型有 `progress: number`、
   UI 有 `<Progress value={progress} />` —— 但
   **`TaskRunner` 与 `TaskProvider` 都没有任何写入 `progress` 的入口**。
   所以那个 `progress === undefined` 分支恒为真，进度条永远不出现。
6. **⚠️ `task_progress` 没有发送方**（见 §7）。
   与第 5 条是同一个缺口的两个表现。
7. **🔴 `restart` 只对 `running` 状态有效，但 UI 对所有任务都显示按钮**：

   ```ts
   // src/tasks/server/manager.ts → TaskRunner.restart
   if (!this.running.has(id))
     throw new BusinessError('only running task canbe restart!');
   ```

   已完成/失败的任务不在 `running` 里，点「重试」会收到
   一个**硬编码英文、没有 i18n code 的**错误 toast。
   用户视角是「重试按钮坏了」。
   从产品语义看，**「失败的任务」恰恰是最需要重试的对象** ——
   而现在只有「还在跑的任务」能重试（这更像"重启"而不是"重试"）。

   > 📌 作者知道这个限制：`tests/tasks/index.test.ts` 与
   > `tests/tasks/server/manager.test.ts` 里各有一条
   > 「restart 非运行中的任务应当报错」。所以这是**被测试固化下来的现状**，
   > 不是漏掉的边界。要不要改是产品决策，不是 bug 修复。

8. **`get(id)` 查不到已结束的任务**：`manager.get` 只看 `running` Map。
   （旧笔记第 39 条写的是「任务完成后移出 Map，完成的任务查不到」，
   这条**仍然成立** —— 只是影响面小，因为列表走的是数据库。）
9. **`provider` 找不到时任务静默「成功」**（§4 第 3 条）。
10. **一次取消会触发两次 `start()`**（§3 第 4 条），属无害但不整洁。
11. **`TaskProvider.execute` 与 `TaskRunner.execute` 同名不同签名**，
    读代码时容易混（§4 末尾）。
12. **`tasks` 模块的 `default` 导出是空函数**：

    ```ts
    // src/tasks/server/index.ts
    /** TODO 是否延迟开启任务？ */
    export default async function () {}
    ```

    作者自己留了个 TODO —— 也就是说「进程重启后，数据库里那些
    停在 `running` 的任务怎么办」这个问题**当前没有答案**
    （它们会永远显示为「进行中」，因为内存池已经空了）。
13. **`repository.create` 不校验 id 的 uuid 格式**（对照 `comfyui` 的
    `validate()`），只判 `!task.id` 才补一个。
14. **`repository.history.get` 签名是 `Promise<TaskHistory>`，
    但查不到时返回 `undefined`** —— 类型与实现不符（当前无调用点）。

### 与工具的并发池共享的问题

`tools/client/task.ts` 的 `Manager` 是同一个基类的子类，
所以第 1、2、4、10 条**同样作用于工具调用**：

- 工具池**没有 `repository`**，所以第 2 条的「不落库」在那里自然无害；
- 但**第 4 条（状态被覆盖）与第 10 条（两次 `start`）同样存在**；
- 工具池额外自己处理了取消：`constructor` 里
  `signals.setAbort(controller.signal, () => { this.pending.length = 0; })`
  —— **只清待执行的，已经在跑的工具不会被中断**。

## 9. 本章速查

- 想加一个后台任务？写一个 `TaskProvider`（`id` + `execute(args, controller)`），
  `tasks.registry.register(...)`，然后
  `tasks.manager.create(name, { provider: <那个 id>, ...args })`。
- 想加一个**支持并发**的前台批量操作？继承 `TaskRunner`，
  参考 `src/tools/client/task.ts`（含 `wait()` 的写法）。
- 并发上限在哪调？`TaskRunner` 构造函数的 `max`，默认 **8**。
  注意 `tools` 那个池子用的是默认值，改默认值会同时影响它。
- 任务状态从哪看？`/api/tasks`（分页）与「任务」菜单。
- 任务失败原因在哪？`task.result`（由 `errors.serialize` 写入的 JSON 字符串）。
- 重试为什么报错？因为只有 `running` 的任务能重试（§8 第 7 条）。
- 进度条为什么不显示？因为没人写 `progress`（§8 第 5 条）。
- 想看更细的缺陷清单？读 [tests/TODO.md](../../tests/TODO.md)，
  它的记录比我这里更细（含行号与「已实测/纯推断」的区分）。
