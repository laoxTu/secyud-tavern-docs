# 13 · 心得体会

前 13 篇是「这个项目是什么」。这一篇是「我读完之后的所思所想」——
包括我认为它做得好的地方、让我困惑的地方、以及我自己在整理笔记时犯的错。

这一篇带主观判断，与前 13 篇的客观陈述性质不同，请分开看待。

---

## 一、这个项目最打动我的地方

### 1. 它把「可定制」做到了骨子里，而不是嘴上

大多数标榜「高度可定制」的项目，定制点是**枚举出来的**：
给你一堆开关、一堆模板槽位，你能改的都在文档里列着。

这个项目的做法不一样。它把**界面本身**也交给了用户：

> 没有任何预设时，是一片空白，无法直接互动。
> 你需要至少一个展示脚本才能看到交互页面。

第一次读到 `realm.md` 这句话时我愣了一下。这不是"功能缺失"的委婉说法，
而是一个**刻意的架构决定**——宿主连"聊天界面长什么样"都不预设，
只提供一个 iframe、一套 `postMessage` 协议、一个 `userInput` 接口。

结果是预设作者的能力边界不再是"配置"，而是"编程"。
`疯狂水世界`、`模拟经营` 这类模板能存在，正是因为这条路是通的。

**代价也真实存在**：新人第一次运行会面对空白页面不知所措。
这是个勇敢的取舍，我不确定换成我会不会敢做。

### 2. 「复用已有的通道」比「新建一套机制」更聪明

有两处设计让我停下来想了很久：

**第一处是知识注入。** 世界书和记忆都需要往上下文里塞文本。
最直觉的做法是设计一种新的消息类型，比如 `role: 'knowledge'` 直接插进 messages。
但作者的做法是——**伪造一次 `get_knowledge` 工具调用**：

```ts
caller('', null, [
  {
    name: models.engines.knowledge.info.name, // 'get_knowledge'
    arguments: models.engines.knowledge.args({ type: 'lorebook' }),
    result: content,
  },
]);
```

于是世界书、记忆、未来的任何"知识"都复用同一条工具通道，
不需要在引擎层为"知识"这个概念写任何代码。
那句 `description: 'return empty if current knowledge is injected'`
甚至是在用自然语言引导模型不要重复调用——很巧。

**第二处是变量系统。** 每条消息挂一个 JSON Patch 数组而非完整快照。
省存储只是顺带的好处，真正的收益是：**切换到任意历史输出，
回放补丁就能得到那一刻的变量状态**。"输出翻页会改变上下文"这个交互，
在数据模型层面就已经成立了，不需要额外写状态管理代码。

这种"让数据结构自己承载语义"的思路，我觉得是这个项目里最值得学的东西。

### 3. 代码注释保留了「为什么」

很多项目的注释在解释"这段代码在做什么"——而这从代码本身就能看出来。
这个项目的注释更多在记录**决策与陷阱**：

```ts
/**
 * 复选的规则很复杂，
 * 1，相同的code，不同的key共享一个禁用
 * 2，不同的code，相同的key是正常情况
 * 3，相同的code，相同的key，会追加且共享
 * 这是为多preset设计的，可以继承，共享
 */
```

```tsx
{
  /* key不要删除。发布后，如果没有这个key，会导致引用有问题，原因不明，开发环境无此问题。 */
}
```

第二句尤其珍贵——**作者明确承认"原因不明"**。
比编一个听起来合理的解释要诚实得多，也更有用：
后来者知道这里不能乱动，且知道作者也没搞懂。

## 二、让我困惑或存疑的地方

下面这些不是"bug 清单"（那在 [12-开发手册](./12-开发手册.md) 里），
而是我在阅读时**停下来想过"为什么"但没能完全说服自己**的地方。

### 1. `Promise<{ id: string }>` 形式的 params

`src/app/[id]/page.tsx` 的 props 是 `params: Promise<{ id: string }>`，
所有 API handler 都要写 `const { id } = await params`。

这是 Next.js 15+ 的破坏性变更（params 改为异步）。
项目用了 Next 16，所以必须跟进——但整个代码库里这个 `await` 无处不在，
读起来有种"到处在等同一个东西"的噪音感。这不是项目的问题，
但我确实花了几分钟才确认这不是某种自定义约定。

### 2. 为什么模块注册要写成 `default export async function`

```ts
export default async function () {
  globals.menus.register(menu);
}
```

匿名 default 导出的函数，在调用栈里显示不出名字，调试时不够友好。
代码生成器生成的 `console.debug('@/presets/client')` 一定程度上补偿了这点，
但如果写成具名函数（`export default async function registerPresets()`），
profiler 里的可读性会好很多。这可能只是个小疏忽。

### 3. `disabled` 字段的两套语义

预设里的条目禁用状态存在**两处**：

- 数据库 `preset_entry.disabled` 列（条目自身）
- `realm.properties` 里的 `checkItems` / `selections` / `items`（运行时开关）

宏和工具用 getter/setter 把两者缝在一起：

```ts
get disabled() {
  return (macro ? checkItems[tool.name] : items[tool.name]) ?? disabled;
}
```

这个设计是合理的（条目默认值 + 本次游玩覆盖），
但 `??` 的语义意味着**运行时一旦显式设过就永远覆盖条目配置**，
且没法"恢复默认"。我在笔记里如实描述了，但没找到"重置为默认"的入口。

### 4. `builder: 'layered'` 的归属

`model.builder` 字段定义在**模型**上，但消费点在**世界书注入器**里。
我一开始在 `src/models/**` 里找了很久都没找到用法，差点当成死字段。

跨模块通过一个字符串字段解耦，好处是模型侧无需知道世界书的存在；
代价是这个字段的语义漂在两个模块之间，只看一边完全看不懂。
我在 [08-模型接入](./08-模型接入.md) 和 [05-世界书](./05-世界书.md) 里
各写了一半，读者需要跨篇拼起来。

## 三、我自己犯的错（值得记下来）

### 我把 Zod 写进了技术栈

这个错误值得单独拿出来说，因为它的成因很典型。

我在最初浏览项目时用 glob 扫了一遍文件树，`node_modules/.pnpm/` 里出现了
`zod-to-json-schema@3.25.2_zod@3.25.76`。后来整理技术栈表时，
我把 Zod 写了进去——**尽管我早就读过 `package.json`**。

问题出在哪？我把"这个目录存在于 node_modules" 当成了
"这是项目的依赖"。而它其实只是某个包（可能是 `shadcn` CLI 或 drizzle-kit）
的传递依赖，跟你删没删毫无关系。

**教训**：`node_modules` 只能说明"某个东西被安装过"，
判断直接依赖的唯一依据是 `package.json`。我跳过了这一步，
而且是在**已经读过正确信息的情况下**跳过的——这比"没查"更糟，
因为它说明我当时是在凭印象填表，而不是在核对。

顺手复查又发现同表的第二处错误：我写了 "Radix / Base UI"，
实际是 32 处 `@base-ui/react`、0 处 `@radix-ui`，底层是 Base UI。
更尴尬的是我在 `11-前端架构.md` 里写对了（"底层不是 Radix"），
两篇自相矛盾——说明我写总览时是在**总结印象**，而不是**回查事实**。

### 我依赖了四个 subagent 的报告

这一轮我派了 4 个 subagent 并行调研，它们返回了很详实的报告。
这提高了效率，但引入了一个风险：**我把它们的部分结论直接写进了笔记，
而没有逐条回到源码验证**。

比如 ComfyUI 的 `execSync` 命令注入、`checker.validateCode` 的正则只匹配单字符
——这两条我后来抽查确认是真的。但"抽查确认了两条"不等于"其余都确认了"。

我现在的判断是：subagent 报告适合用来**发现问题**，
不适合直接作为**结论**。我在笔记开头写了"结论均来自源码阅读"，
更准确的说法应该是"主干逻辑来自我亲自阅读，部分细节来自辅助调研"。

### 关于「疑似 bug」的分寸

我标注了大约 10 处疑似 bug。回头看，我的分寸大致是：

- **高置信**（读了完整调用链，能说清为什么错）：
  如正则 `target` 过滤与挂载点不一致、`remaining.join(', ')` 对对象数组调用。
- **中置信**（两处代码对不上，但可能是我漏看了中间环节）：
  如 vector 匹配器索引写 `name`、检索比对 `id`。
- **低置信**（只是"看起来不对"）：
  如非流式分支传 `stream: true`——也可能是我误解了参数语义。

我尽量都标了"疑似"并写了不确定的原因。但现在想，
**更好的做法是把置信度写得更显式**，而不是让读者从我措辞的软硬去猜。

## 四、读完之后的几个判断

### 这个项目的复杂度是"必要复杂度"

`src/` 下 364 个文件、10 个模块、一套代码生成流水线——
乍看很重。但读完之后我认为大部分复杂度是被**产品目标逼出来的**：

要让"预设能自己画界面"，就必须有 iframe + 消息协议；
要让"多个预设能叠加继承"，就必须有条目合并与去重规则；
要让"用户能翻看历史并回滚变量"，就必须有 Patch 回放。

真正的"额外复杂度"其实不多。唯一让我觉得可以更简单的是注册表系统——
但换成别的方案，大概也省不下多少，还未必有 `requires` 拓扑排序这么清晰。

### 测试是最大的欠账

4 个测试文件，覆盖 ComfyUI 的两个点、宏的 Eta 调用、hasher 往返。
而数据库、插件系统、拦截器、生成管线、故事、世界书——**全是零覆盖**。

我读代码时多次遇到"这行为对不对？"却无法通过测试确认
（比如 vector 匹配器那个疑似 bug，一个测试就能定性）。
`CONTRIBUTING.md` 说"纯逻辑部分非常欢迎补测试"，这个邀请是真诚的，
因为`Registry.sortByRequires`、`jsonUtils.merge`、`json-patch`
这些东西**测试成本极低、价值极高**。

### 「自部署个人应用」这个定位解释了几乎所有取舍

一开始我对"允许预设执行任意 JS"感到不安。读完 `CONTRIBUTING.md`
的那一节后才理解：**部署者即管理员，不存在多租户边界**。
在这个前提下，允许执行用户自己写的脚本不是漏洞，是功能——
就像本地 IDE 允许你运行自己的代码一样。

这让我意识到：**评价一个安全设计，必须先确定威胁模型**。
脱离"谁在用、谁能被攻击"谈"这段代码危不危险"，是没有意义的。
（当然，`execSync` 拼 curl 那条仍然值得修——
它的输入虽然来自本地库，但库内容来自外部 API，链条更长。）

## 五、如果我要继续参与

按我心里的优先级：

1. **补测试**——尤其是 `Registry` 的拓扑排序、
   `json-patch` 的 `patch`/`extract`、`buildUrl`/`handleResponse`。
   这是唯一能"低风险高收益"改变项目质量的事。
2. **给疑似 bug 写复现用例**——把"疑似"变成"确定是/不是"。
   vector 匹配器那条尤其值得，因为它影响功能正确性而非仅代码整洁。
3. **修明确的低级错误**——`checker.validateCode` 的正则、
   `response.download` 的 Content-Type、循环依赖报错里的 `[object Object]`。
   这些改动小、风险低、不会有争议。
4. **谨慎碰的东西**：正则 `target` 的语义、
   `Registry` 的报错行为——这些可能有人依赖了当前行为，
   按 `CONTRIBUTING.md` 的建议，**先开 Issue 讨论再动手**。

## 六、最后

这个项目给我最深的印象不是某个具体技术点，而是一种**态度**：
作者在注释里承认"原因不明"，在文档里承认"目前不能复刻脚本，需要自行调整"，
在贡献指南里明确说"不要提移除能力的加固 PR"。

这种坦诚让代码变得可读——**因为我知道哪里是精心设计的，哪里是妥协的产物**。
读一个把取舍摊开来讲的代码库，比读一个假装一切都很完美的代码库，
收获要大得多。

也正因为如此，我把自己犯的错（Zod、Radix）也写进了这一篇。
如果只留下"我读懂了"的部分而藏起"我搞错了"的部分，
那这份笔记本身就成了另一种"假装完美"。

## 附：几条通用的阅读心得

- **先找注册点，再看实现**。这个项目里"什么东西从哪来"永远比"它怎么工作"更难找。
- **`manifest.json` 是理解模块边界的钥匙**，比任何文档都准。
- **注意名字相同但接口不同的东西**：两套 `model-engine`、
  两套 `tool-provider`、两处 "script"（预设脚本 vs 工具脚本）。
  这是最容易读串的地方。
- **`requires` 就是调用顺序**。看不懂执行顺序时，先查 `requires`。
- **文档与代码冲突时信代码**。我至少遇到两处
  （`Script.defaultEntry.type`、正则 target 的行为）。
- **警惕"看起来有据"的推断**。我的 Zod 错误就是这么来的。
