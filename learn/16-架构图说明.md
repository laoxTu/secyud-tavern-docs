# 16 · 架构图说明

配套文件：[`architecture.drawio`](./architecture.drawio)

**格式**：draw.io 原生 XML（`<mxfile>` / `<mxGraphModel>`），**未压缩**，可直接文本 diff。

打开方式（任选）：

- [app.diagrams.net](https://app.diagrams.net/) → `File → Open From → Device`
- VS Code 装 **Draw.io Integration** 插件，直接双击文件
- draw.io 桌面版 → `File → Open`

> 为什么不是 JSON：draw.io 的原生文件格式是 XML。
> JSON 形式（`{"pages":[{"cells":[...]}]}`）是它内部的剪贴板 / 自动保存结构，
> 文件打开对话框不认。而且那个结构**没有坐标字段**，
> 即使导入也会所有元素堆在原点。本文件用 XML 并写入了完整 `mxGeometry`。

包含三页：

| 页 | 内容 | 适合看什么 |
| --- | --- | --- |
| **总架构** | 六个层次 + 全部模块与流向 | 建立整体认知 |
| **生成时序** | 一次 AI 回复的 15 步 | 理解运行时行为 |
| **模块契约** | 目录骨架 + 注册表清单 + 扩展点 | 准备动手改代码 |

## 一、总架构（第 1 页）

### 六个层次

图自上而下分为六层，**这个分层本身就说明了系统的运行方式**：

```
① 启动与装配层   ← 编译期跑一次，之后固定
② 应用外壳层     ← 浏览器运行时
③ 能力模块层     ← 声明式，被①扫描、被②驱动
④ 生成管线层     ← 决定「发给模型什么」
⑤ 渲染管线层     ← 决定「用户看到什么」
⑥ 持久化层       ← 所有人共用
```

**关键读法**：① 和 ③ 的关系是「扫描与被扫描」——
`pnpm prepare` 扫描所有 `manifest.json`，生成注册表；
而 ④ ⑤ 是**同一批模块的两种投影**：
一个模块可以同时是 Processer（影响输入）和 Renderer（影响输出）。

### 颜色约定

| 颜色 | 含义 |
| --- | --- |
| 蓝底 | 应用外壳、前端流程、数据访问 |
| 绿底 | 能力模块、持久化 |
| 黄底 | 生成管线（Processer 与转换/注入链） |
| 橙底 | 编译期产物（`src/generated/*`、`src/app/api/*`） |
| 紫底 | 服务端引擎与 API |
| 红底 | 生成结果与缺口提示 |

线型：**实线 = 数据/调用流**，**虚线 = 代码生成或弱依赖**。

### 三条最值得看的连线

1. **`manifest.json` → `pnpm prepare` → `Registry` → `src/generated/*`**
   这是整个项目的「装配主干」。注意 `generated` 是虚线指向外壳层——
   它是**编译期产出**，运行时只是被 import。

2. **能力模块 → 生成管线 / 渲染管线的双向扇出**
   左侧 `presets` 同时连出 4 条线到 Processer（regexes/macros），
   又连出 4 条到 Renderer（regexes/macros/scripts/styles）。
   **同一个模块名出现在两层，这是理解本项目的关键**——
   `presets/macros/client/realm.ts` 里就同时导出了 `processer` 和 `renderer`。

3. **`converts` 与 `injects` 两条链**
   图中间的两个橙色框是管线的实际数据结构：
   - `converts`：文本转换器链（正则 → 宏）
   - `injects`：消息注入器链（世界书、记忆）

   所有 Processer 做的事，本质就是**往这两条链上 push 一个函数**。

### 两张便签

- **黄色便签**（工具·变量·世界书的组合）：说明本项目的核心设计思路——
  机制正交，策略由预设定义。不是内置"概率/冷却"，而是工具写变量 + 世界书读变量。
- **红色便签**（⚠ 当前缺口）：标注了两个真实缺失——
  无 token 预算控制、`layer` 为粗粒度位置分段。

## 二、生成时序（第 2 页）

这一页画的是 `realms.generate()` 的完整流程，**从用户点提交到落库**。

### 四个阶段

| 阶段 | 步骤 | 要点 |
| --- | --- | --- |
| **准备** | ①②③④ | 输入改写 → 历史合并判定 → 取上下文窗口 |
| **装配** | ⑤⑥ | init 建缓存 → 五个 Processer 各自 push 到 converts/injects |
| **请求** | ⑦⑧⑨ | 组装消息 → 走 API → 服务端解密 Key 调 SDK |
| **循环** | ⑩⑪⑫⑬⑭⑮ | 流式解析 → 工具调用 → 判断是否继续 → 渲染 → 落库 |

### 三个容易忽略的细节

**① 上下文截断不看 token，看 `summary` 标记**

```
倒序回溯 histories
遇到 summary === true 停止
走到头则补 opening（开场白）
```

即上下文永远是「最后一个总结段 → 现在」。
这是**用户可控的**（界面上的"总结"复选框），而非引擎自动计算。

**② Processer 的执行顺序由 `requires` 决定**

图中的 `requires` 标注：

```
regexes ──requires──▶ macros
tools   ──requires──▶ lorebooks
```

为什么宏依赖正则？因为**正则在宏之前跑**——正则可以产出宏表达式，宏再求值。
为什么世界书依赖工具？因为 `role: 'knowledge'` 的世界书要走工具调用通道注入。

**③ 工具循环与重试是两层不同的循环**

- **外层**：工具循环（`iteration`），最多 `iterations` 轮（默认 20，最小 2）
- **内层**：重试循环（`retry`），网络错误或流式卡死超过 `interval` 秒触发

图中 `s_retry` 用虚线指回 `s_api`，`s_loop` 用红实线指回 `s_assemble`——
**两者作用域不同，这是那段代码最复杂的地方**。

### 两张便签

- **`get_knowledge` 伪工具调用**：世界书的 `knowledge` 角色不直接进消息列表，
  而是伪装成一次工具调用的返回值。零新增概念，天然兼容所有供应商。
- **变量是 JSON Patch**：每条消息带 `variables: Operation[]`，
  工具写值只是 push 一个操作。这是「翻页可回放、重生成不污染状态」的基础。

## 三、模块契约（第 3 页）

这一页是**给要动手改代码的人**看的。

### 目录骨架

左边那个等宽字体框就是每个模块的标准结构。要点：

- `manifest.json` 放在**模块根部**，不是 `client/` 或 `server/` 里
- `client/index.tsx` 和 `server/index.ts` 的 **default 导出就是注册函数**
- `client/realm.ts` 是实现 Processer / Renderer 的地方（命名不强制，但这是惯例）

### 注册表清单（12 个）

按颜色分组：

| 分组 | 注册表 |
| --- | --- |
| 蓝（UI 入口） | `global-menu`、`setting-tabs`、`preset-tabs`、`realm-feature` |
| 黄（管线处理器） | `model-processer`、`realm-processer` |
| 紫（前后端各一，同名不同接口） | `model-engine`、`tool-provider` |
| 绿（数据与匹配） | `lorebook-matcher`、`preset-storage` |
| 红（横切） | `interceptor`、`sse-manager` |

> ⚠️ 注意紫色的两个：**`model-engine` 和 `tool-provider` 在前后端各有一个注册表，同名但接口不同**。
> 这是读代码时最容易读串的地方。另外 `src/plugins/` 是**框架本体**，
> 与 `plugins/`（外部插件目录）不是一回事。

### 六类扩展点

右下角六个橙色框是「想加东西时的落点」：

| 想加什么 | 做什么 |
| --- | --- |
| 模块 | 建目录 + `manifest.json` → `pnpm prepare` |
| 条目类型 | `schemas.entry` + `storages.create` + `createPresetEntryState` |
| 工具 | 实现客户端 `ToolProvider.create`（可选服务端归档 Provider） |
| 匹配器 | 实现 `Matcher.match` + 可选 `configComponent` |
| 模型供应商 | 前后端两个 `ModelEngine` |
| UI 入口 | 写 `GlobalMenuItem` / `Feature` / `SettingTab` 并注册 |

### 便签

点出契约的本质：**manifest 只需三个字段，default 导出即注册入口——靠约定而非配置。**
代价写在最后：改 manifest 必须重新 prepare 并重启。

## 四、几个图中没画但值得知道的点

1. **`realm.context` 是跨模块的缓存总线**
   Processer/Renderer 的 `init` 结果都存在这里，键为 `model.<id>` / `realm.<id>`。
   **同键重复初始化会抛错**——这是防止插件互相覆盖的保护。

2. **世界书匹配结果会落进 `message.properties`**
   图⑦⑭之间有一步没画：`Processer.output` 会把命中结果写回消息属性，
   使历史重放时不必重算（向量/变量可能已变化）。

3. **`realms` 是全局单例**
   图②里的"应用外壳"持有 `realms.realm` / `realms.iframe`，
   意味着**同一页面只能有一个活跃 realm**。

4. **iframe 未设置 `sandbox`**
   图②的 iframe 框没有标注这一点。它是同源 iframe，
   预设脚本拥有完整同源权限——按项目定位这是刻意的能力。

## 五、如何修改这张图

- **改文字 / 位置**：直接在 draw.io 里拖动编辑，保存（Ctrl+S）即可，
  格式保持一致。导出给别人时选 `File → Export as → XML`（**不要**勾压缩）。
- **手工加内容**：在对应 `<diagram>` 的 `<root>` 里加 `<mxCell>`：

```xml
<!-- 节点：必须有 vertex="1"、id 唯一、parent 指向所属图层或容器 -->
<mxCell id="my-node" value="标签文字&#10;第二行"
        style="rounded=1;whiteSpace=wrap;html=1;fillColor=#DAE8FC;strokeColor=#6C8EBF;"
        vertex="1" parent="1">
  <mxGeometry x="100" y="100" width="200" height="80" as="geometry" />
</mxCell>

<!-- 边：edge="1"，用 source/target 引用节点 id -->
<mxCell id="my-edge" value="标签" style="endArrow=classic;html=1;rounded=1;"
        edge="1" parent="1" source="my-node" target="other-node">
  <mxGeometry relative="1" as="geometry" />
</mxCell>
```

要点：

- `value` 里的换行用 `&#10;`（XML 数字实体），不是字面量 `\n`
- 标签内的 `<` `>` 要转义成 `&lt;` `&gt;`（本文件里 `<script>` 就是这么写的）
- style 字符串以 `;` 结尾，键值对之间也用 `;` 分隔
- 容器（swimlane）内的子节点，坐标是**相对于容器左上角**的

- **验证**：改完跑一下这段检查引用完整性。

```powershell
[xml]$x = Get-Content "docs\learn\architecture.drawio" -Raw -Encoding UTF8
foreach ($d in $x.mxfile.diagram) {
  $cells = @($d.mxGraphModel.root.mxCell)
  $ids = @{}; $cells | ForEach-Object { $ids[$_.id] = $true }
  $edges = @($cells | Where-Object { $_.edge -eq '1' })
  $bad = @($edges | Where-Object {
    -not ($ids.ContainsKey($_.source) -and $ids.ContainsKey($_.target))
  })
  Write-Output "$($d.name): 断线 $($bad.Count) 条"
}
```
