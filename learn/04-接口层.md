# 04 · 接口层与横切

本项目**没有手写的 API 路由**。接口在模块里声明，路由在 prepare 时生成，
错误处理与序列化由拦截器统一兜底。

> 📌 本篇已按 `1.3.5.0` 复核。主要变化：`buildUrl` **不再原地改入参**（已改为克隆）、
> `BusinessError` 构造签名与 `checker` 成员已补全、
> SSE 广播新增**订阅**能力（不再只用于 toast）。

---

## 1. 在模块里声明接口：`server/api.ts`

模块的 `server/api.ts` 导出一个嵌套对象，**键名即路径，叶子即 HTTP 方法**：

```ts
// 形态示意（真实结构见 src/presets/server/api.ts）
export default {
  presets: {
    GET:  async (request, { searchParams }) => { ... },
    POST: async (request, { searchParams }) => { ... },
    '[id]': {                                    // ⚠️ 是 [id]，不是 {id}
      GET:    async (request, { params }) => { ... },
      PUT:    async (request, { params }) => { ... },
      DELETE: async (request, { params }) => { ... },
      clone:  { POST: async (request, { params }) => { ... } },
    },
    import: { POST: async (request) => { ... } },
  },
};
```

`scripts/operations/api.ts` 递归遍历这棵树，凡是键名落在
`{POST, PUT, DELETE, GET}` 里的，就登记一条描述符 `{ method, module, path }`，
路径由嵌套层级拼成（如 `presets/[id]/clone`）。

### 生成的路由文件

```
src/app/api/<path>/route.ts
```

内容形如（真实文件 `src/app/api/presets/route.ts`）：

```ts
import api0 from '@/presets/server/api';

export const GET = api0['presets']['GET'];
export const POST = api0['presets']['POST'];
```

> ⚠️ `generateApiRoutes` 每次都会先 `rm -rf src/app/api` 再全量重建。
> **手改这个目录里的任何文件都会在下次 prepare 时丢失。**

### 生成的前端路径类型

同时生成 `src/generated/api-path.ts`：

```ts
const get = [ 'models', 'models/{id}', 'presets', ... ] as const;
export type GetPath = typeof get[number];
```

**这里有一次关键的字符替换**：

```ts
// scripts/operations/api.ts
descriptor.path = descriptor.path.replaceAll('[', '{').replaceAll(']', '}');
```

也就是说：

| 位置 | 写法 | 例 |
| --- | --- | --- |
| `server/api.ts` 的**键名** | `[id]` 方括号 | `'[id]': { GET }` |
| 生成的**物理目录** | `[id]` 方括号（Next.js 要求） | `src/app/api/tasks/[id]/route.ts` |
| 前端的**路径类型** | `{id}` 花括号 | `get('tasks/{id}')` |

**两套括号对应的其实是同一个东西**，只是用途不同：方括号给 Next.js 做动态段，
花括号给 `buildUrl` 做占位符替换。这是最容易写错的一处约定。

这些联合类型让前端 `get('presets/{id}')` 获得**字面量级别的路径补全与校验**。
`src/client.ts` 里的 `get/post/put/del/open` 都以此为参数类型。

## 2. 服务端拦截器

```ts
// src/interceptors/server/index.ts
export interface NextHandler {
  (request: NextRequest, records: NextRecord): Promise<NextResponse>;
}

export function route(route: NextHandler): NextHandlerResult {
  return async (request, context) => {
    const global = globalThis as { __initialized?: boolean };
    if (!global.__initialized) {
      global.__initialized = true;
      if (process.env.NODE_ENV === 'development') { /* 给 console.debug 加时间戳 */ }
      await registerServerPlugin();      // ← 惰性初始化所有模块服务端注册
    }
    const interceptors = manager.sorted();  // 按 requires/sequence 拓扑排序
    const handler = composeInterceptors(interceptors, route);
    return handler(request, context);
  };
}
```

三个要点：

1. **惰性单次初始化**：`globalThis.__initialized` 保证 `registerServerPlugin()`
   在一个进程里只跑一次，且是在**第一个 API 请求到达时**才跑。
2. **洋葱模型**：`composeInterceptors` 递归 `dispatch(index)`，
   每个拦截器拿到 `next` 决定是否继续，与 Koa/Express 中间件同构。
3. **searchParams 反序列化**：`deserializeSearchParams` 会尝试对每个值 `JSON.parse`，
   失败则保留字符串。这与前端 `buildUrl` 里「对象值 `JSON.stringify`」互为逆操作：

```ts
// src/client.ts
} else if (typeof value === 'object') {
  params[key] = JSON.stringify(value);   // ← 序列化
}
```

所以带复杂对象（如分页 `search` 参数）的 GET 请求能正确往返。

### 内置的 errorInterceptor

仓库里**只注册了一个**服务端拦截器 —— `errorInterceptor`：

```ts
// src/interceptors/server/error.ts
try { return await next(); }
catch (error) {
  if (error instanceof BusinessError) {
    if (request.method !== 'GET') console.error(error);   // GET 错误不打日志
    return NextResponse.json(
      { message: error.message, code: error.code, data: error.data },
      { status: error.status ?? 500 },
    );
  }
  if (error instanceof Error) {
    console.error(error);
    return NextResponse.json({ message: error.message, data: {} }, { status: 500 });
  }
  throw error;
}
```

要点：GET 请求出错**静默**（不打 error 日志），因为 GET 常用于轮询；
返回体统一为 `{ message, code, data }`，这正是前端 `ApiError` 的构造参数。

## 3. 错误类型体系

```ts
// src/interceptors/index.ts
export class BusinessError extends Error {
  data: Record<string, any> = {};
  code?: string;
  innerError?: any;
  status: number;

  constructor(
    message: string,
    code?: string,
    innerError?: any,   // ⭐ 可包裹底层错误
    status: number = 500,
  )
  withValue(key: string, value: any)   // 链式附加 data
  withValues(obj: any)                 // 链式合并 data
}
```

```ts
// src/interceptors/client/index.ts
export class ApiError extends BusinessError {
  constructor(message: string, code?: string, data?: any) { ... }
}
```

`status` 是**构造参数**（不是后设的属性），`code` 是**i18n key**：
前端 `error()` 会用它去 `t(code)` 取本地化文案，
并把 `data` 里的字符串值也逐一带上翻译（若 key 存在）：

```ts
// src/components/index.tsx
export const translator = {
  t: undefined! as _Translator,   // 由 Client 引导阶段注入
  translate(message: string, data?: Record<string, any>) {
    const t = translator.t;
    if (!t) return message;       // 未注入时不翻译，不抛错
    if (!data) return t(message);
    const record: Record<string, any> = { ...data };
    for (const key in record) {
      const value = record[key];
      if (typeof value === 'string') {
        record[key] = t.has(value) ? t(value) : value;   // ← data 也参与翻译
      } else record[key] = value;
    }
    return t(message, record);
  },
};
```

这是把 next-intl 的 `t` 抽成**非 hook 的全局单例**，好让
`interceptors/client` 这类非组件代码也能翻译。关键的两点：
`t.has(value)` 的探测让 `data` 里的**字段名**（如 `preset.name`）也能被本地化；
`t` 未注入时**降级为原文返回**而不是抛错。

这就是 `BusinessError(...).withValue('field', 'preset.name')` 这类写法的用意：
错误信息本身可被完全本地化。

### `errors.serialize`：把错误变成可持久化字符串

```ts
// src/interceptors/index.ts
export const errors = {
  serialize(err: unknown): string {
    if (err instanceof BusinessError) {
      const inner = err.innerError
        ? { name, message, stack }   // 只挑三个字段，不递归
        : undefined;
      return JSON.stringify({ name, message, stack, data, code, inner });
    }
    if (err instanceof Error) return JSON.stringify({ name, message, stack });
    return String(err);
  },
};
```

它的消费者是**任务系统**：`TaskRunner.failed()` 把异常序列化成字符串写进
`task.result`，这样「失败原因」能落库并在任务列表里回看。
详见 [17-任务与调度](./10-任务与调度.md)。

### checker：参数校验工具集

`src/interceptors/index.ts` 导出的 `checker` 对象提供一组「校验或抛错」的助手，
服务端代码大量使用（下表为完整成员）：

| 方法 | 行为 |
| --- | --- |
| `code` | 正则字符串常量 `'[A-Za-z0-9_]+'`，给 `<Input pattern={...}>` 用 |
| `validateCode(field, value, ns)` | 校验 code 格式，失败抛 `error.invalid_code` |
| `duplicate(exist, entity, name, value)` | 唯一性冲突，抛 `error.entity.duplicate_value` |
| `notNullOrEmpty(field, value, ns)` | 假值即抛 `error.empty_field` |
| `notNullOrWhitespace(field, value, ns)` | 空/纯空白即抛 |
| `notEmpty(field, value, ns)` | 只挡 `''`（`null` / `undefined` 放行） |
| `notWhitespace(field, value, ns)` | `value?.trim() !== ''` 即通过 |
| `validJson(value, name)` | JSON 解析校验，失败抛 `error.json_invalid` |
| `validJsonOrEmpty(value, name)` | 空值放行，否则同 `validJson` |
| `notNullEntity(id, entity, target)` | 实体不存在则抛 `default.entity_not_found` |

典型用法：

```ts
// src/models/server/engine.ts
const name = checker.notNullOrWhitespace('engine', model.engine, 'model');
const engine = registry.records[name];
checker.notNullEntity(name, engine, 'model.engine');
```

> `validateCode` 的正则 **已修复**：`1.3.2.8` 时是只匹配单字符的
> `/^[A-Za-z0-9_]$/`，现在是 `/^[A-Za-z0-9_]+$/`，与 `checker.code` 一致。
>
> `notEmpty` 与 `notWhitespace` 的差别值得记住：
> 前者 `value !== ''`（`undefined` 会**通过**），后者用 `?.trim() !== ''`
> （`undefined?.trim()` 是 `undefined`，`undefined !== ''` 也**通过**）。
> 真正的「必填」语义只有 `notNullOrEmpty` / `notNullOrWhitespace` 有。

## 4. 前端请求器：`src/client.ts`

文件开头有一句重要的定位说明：

> 此文件只用于 client 请求 server。调用第三方接口请使用 fetch 或 proxy。

### 基础用法

```ts
const model = await get('models/{id}', { params: { id } });
const created = await post('presets', body);
await put('presets/{id}', body, { params: { id } });
await del('presets/{id}', { params: { id } });
open('comfyuis/workflows/{id}/export', { params: { id } });   // window.open 下载
```

### buildUrl：路径参数与查询参数的混合处理

```ts
const buildUrl = (url: string, params?: Record<string, any>) => {
  if (!params) return url;
  params = structuredClone(params);       // ⭐ 先克隆，不动入参
  let result = url;
  for (const key of Object.keys(params)) {
    const value = params[key];
    if (value === undefined) {
      delete params[key];                         // undefined 直接剔除
    } else if (result.includes(`{${key}}`)) {
      result = result.replace(`{${key}}`, String(value));   // 填路径占位符
      delete params[key];
    } else if (typeof value === 'object') {
      params[key] = JSON.stringify(value);        // 对象序列化进 query
    }
  }
  const queryString = new URLSearchParams(params).toString();
  return queryString && queryString.length > 0 ? `${result}?${queryString}` : result;
};
```

所以 `params` 承担了**双重职责**：既填充 `{id}` 这类路径占位符，
又作为查询字符串。一个参数只会走其中一条分支。

> ✅ **「不要复用 params 对象」的旧警告已作废。**
> `1.3.2.8` 时 `buildUrl` 会直接 `delete params[key]`，所以同一个对象
> 传给第二次调用就丢字段了（旧笔记在 03/11/12 三处都提醒过）。
> 当前实现**开头就 `structuredClone`**，对入参完全无副作用，可以放心复用。

### 对象/数组参数怎么过 HTTP

查询串里没有「对象」这个概念，靠的是一对互逆的约定：

| 方向 | 位置 | 做法 |
| --- | --- | --- |
| 前端 → URL | `buildUrl` | `typeof value === 'object'` → `JSON.stringify` |
| URL → 服务端 | `deserializeSearchParams` | 每个值都试着 `JSON.parse`，失败就留原字符串 |

```ts
// src/interceptors/server/index.ts
function deserializeSearchParams(searchParams: URLSearchParams) {
  const raw = Object.fromEntries(searchParams);
  const result: Record<string, any> = {};
  for (const [key, value] of Object.entries(raw)) {
    if (!value || typeof value !== 'string') continue;
    const trim = value.trim();
    if (!trim) continue;
    try { result[key] = JSON.parse(trim); } catch { result[key] = trim; }
  }
  return result;
}
```

⚠️ 注意它**会吃掉空字符串**（`if (!trim) continue`）：
`?fuzzy=` 这种「显式传空」在服务端会变成**键不存在**，而不是 `''`。
所以「清空搜索框」的业务不能靠传空串表达，要靠**不传这个键**
（前端 `undefined` 会被 `buildUrl` 删掉，两者刚好闭环）。

### handleResponse 与 Content-Type 判断

```ts
export async function handleResponse(response: Response) {
  const contentType = response.headers.get('Content-Type');
  if (!contentType?.includes('application/json')) {
    return response;          // 非 JSON 直接返回 Response（用于流、文件）
  }
  const json = await response.json();
  if (!response.ok) {
    throw new ApiError(json.message ?? 'Internal Server Error', json.code, json.data);
  }
  return json;
}
```

**这个分支是 SSE 流式生成能工作的前提**：模型生成接口返回 `text/event-stream`，
不是 JSON，因此原样把 `Response` 交给调用方去 `response.body` 上读流。

> ⚠️ 它**不检查 `response.ok` 的非 JSON 分支**：如果服务端以 500 返回
> 一段 HTML 错误页（如 Next 的默认错误页），这里会把它当「流」放行，
> 调用方拿到一个非流的 Response 去 `getReader()`。这是刻意保留的简单性，
> 但排查线上问题时值得先怀疑这里。

### 错误分类工具

```ts
isNetworkError(err)  // TypeError 且 message 含 network/fetch/load failed
isAbortError(err)    // DOMException 且 name === 'AbortError'
isHttpError(err)     // status >= 400
```

生成流程的重试逻辑正是基于 `isNetworkError` 与 `isAbortError` 判断的。

## 5. 客户端统一异常处理：`handler` + `error`

`src/interceptors/client/index.ts` 只导出两个入口（注意**没有** `useHandler` /
`handleError` 这样的命名）：

```ts
export function error(err: any) { ... }        // 分类处理一个错误
export function handler<A, T>(action, finish?): AsyncFunc<A, T> { ... }  // 包一层
```

用法：

```ts
const submit = handler(async () => { await proxy.save(...); });

// 或包表单 action
<form action={handler(async (data: FormData) => { ... })} />
```

`error` 的分支策略值得注意：

| 分支 | 行为 |
| --- | --- |
| `BusinessError` 且有 `code` | 按 `code` 翻译 → `toast.error`，**不再抛出** |
| 字符串 | 直接 `toast.error`，**不再抛出** |
| 网络错误 / HTTP 错误 / **Abort 错误** | `toast.error(err.message)`，**不再抛出** |
| 其他未知错误 | `toast.error` 后 **`throw err`** |

最后那条注释说明了设计意图：

```ts
/**
 * 继续抛出意味着页面崩溃，进入notfound
 */
```

即：预期内的业务失败只弹提示，预期外的错误让错误边界接管
（`src/app/error.tsx` 就是那个边界）。

> 📌 与 `1.3.2.8` 的差异：现在 `isAbortError` 也走「只提示」分支了。
> 这是 `3fa3723 fix abort error` 的成果 —— 用户点「停止生成」会 abort 请求，
> 从前那条会落进「未知错误」被重新抛出，导致页面崩掉。

`handler` 的语义很简单：`try { await action() } catch { error(err) } finally { finish?.() }`。
**注意它会吞掉返回值**（出错时 `return undefined`），
所以 `handler` 只适合「副作用 + 提示」，不适合需要拿到结果的调用。

## 6. SSE 的两套机制（容易混淆）

项目里有两件不同的事都叫 SSE，务必区分：

### (a) 广播通道：`/api/sse/{id}` —— 支持细粒度订阅

`src/signal/` 模块提供的**服务端推送事件总线**。`1.3.4.0` 前后它从
「只会广播 toast」升级成了**带订阅/定向的消息总线**：

```ts
// src/signal/index.ts
export interface SseSubscription {
  status: 'all' | 'part';   // 全收 / 只收 targets 里的
  targets: string[];
}
export interface SseSubscriptionAction extends SseSubscription {
  action: 'set' | 'del' | 'add';
  type: string;             // 事件类型，如 'toast' / 'task_progress'
}
export interface SseMessage<T = any> {
  type: string;
  data: T;
  target?: string;
}
```

- 服务端：`signals.registry`（Registry 名 `sse-manager`）管理所有连接。
  每条连接持有一个 `subscriptions: Map<type, SseSubscription>`。
  广播时**逐条比对订阅**：`status: 'all'` 直接发，
  `status: 'part'` 要求 `message.target` 命中 `targets` 才发。
  发送抛错的连接会被**就地 `unregister`**（当作断线清理）。
- 每个连接创建时**默认订阅 `toast`（`status: 'all'`）**。
- 客户端：`src/signal/client/index.ts` 维护一个**单例 EventSource**
  （`useSseConnection`，id 是 `utils.uuid()`），
  通过 `useSse(type, cb)` 订阅某一类事件。
- 订阅关系通过 `POST /api/sse/{id}/subscription` 动态调整，
  `action` 支持 `set` / `del` / `add`（`add` 会去重合并 targets）。

实际使用方的例子（`tasks` 模块）：

```ts
// src/tasks/client/state.ts
await signals.proxy.subscription({
  type: 'task_progress',
  targets: result.items.map((u) => u.id),   // 只订阅本页任务的进度
  action: 'set',
  status: 'part',
});

// src/tasks/client/content.tsx
useSse<TaskProgress>('task_progress', (target, data) => { ... });
```

> ⚠️ **发送端还没有实现**：`task` 模块至今没有调用 `signals.send({ type: 'task_progress' ... })`，
> 所以任务列表里的进度条目前**永远停留在 `task.${status}` 文案**。
> 管道（订阅、定向、客户端回调、UI 渲染）都通了，只缺生产端。
> 详见 [17-任务与调度 §5](./10-任务与调度.md)。

### (b) 流式工具：`sseUtils.pack` / `sseUtils.read`

`src/signal/index.ts` 里的纯函数，实现 **OpenAI 风格的 SSE 分帧**：

```ts
async function pack(items: AsyncIterable<any>): Promise<ReadableStream>
//   把异步迭代器逐条写成 `data: <json>\n\n`，末尾补 `data: [DONE]\n\n`

async function* read(stream: ReadableStream)
//   增量解析，按 \n\n 切事件，累积 buffer 处理跨块断行
//   遇到 [DONE] 返回 null（即结束标记不产出）
```

服务端的模型生成接口用 `pack` 把引擎的流包成 SSE；
前端 `processers.generate` 用 `read` 消费它：

```ts
for await (const chunk of sseUtils.read(response.body)) {
  updateTime = new Date();
  yield generate(true, chunk);
}
```

`read` 的两个实现细节值得记住：

- **只在 `done` 时才把最后一段未闭合的 buffer 也当作事件**（`allEvents.slice(0, -1)`）。
  这保证了「半个 JSON 到达时不会被提前解析」。
- `analyzeEvent` 会把**多个 `data:` 行用 `\n` 拼回一个字符串**再解析，
  即兼容 SSE 规范里的多行 data 写法。

配套的信号工具有两个（都在 `src/signal/index.ts`）：

```ts
signals.setAbort(signal, action)   // 自析构的监听器：触发后自动 removeEventListener
signals.createSub(signal)          // 创建一个级联子控制器，返回 { controller, destroy }
```

`createSub` 是 `1.3.4.0` 前后新增的，用于「一轮 = 一个新 AbortController，
但要跟着外层信号一起死」的场景 —— 生成管线的重试逻辑与 `url_fetch` 的超时都靠它。
注意它比 `setAbort` 多了一层**手写销毁**责任：不调 `destroy()` 就会漏监听器。

## 7. 本章速查

- 加接口：改模块 `server/api.ts` → `pnpm prepare` → 前端 `get('新路径')` 自动有类型。
  **键名用 `[id]`，调用用 `{id}`。**
- 报错怎么给用户看？`throw new BusinessError(msg, 'i18n.key').withValue('field', 'x.y')`。
- 想统一加鉴权/日志？注册一个 `InterceptorHandler` 到 `manager`
  （唯一的内置实现是 `errorInterceptor`）。
- 需要流式？服务端 `sseUtils.pack(...)` 返回 Response，前端 `handleResponse`
  会因非 JSON 而放行，再由 `sseUtils.read` 消费。
- 需要服务端主动推送？客户端 `useSse(type, cb)` + 服务端 `signals.send({ type, data, target })`，
  定向推送要先 `POST /api/sse/{id}/subscription`（⚠️ 见下面的已知问题）。
- 要包异步副作用？用 `handler(fn)`，错误分类交给 `error()`。

## 8. 已知问题（`1.3.5.0` 复核）

1. **🔴 `signals.proxy.subscription` 丢掉了连接 id，导致定向推送整体失效。**
   这是本轮复核**新发现**的问题，且现有测试把它当成了正确行为固化下来。

   ```ts
   // src/signal/client/proxy.ts —— 没有 id
   async subscription(param: SseSubscriptionAction) {
     await post('sse/{id}/subscription', param);
   }
   ```

   `buildUrl` 只用 `params` 里的键去替换 `{key}` 占位符
   （`result.includes('{id}')` 为真但 `params` 里没有 `id`），
   于是最终请求是字面量 `/api/sse/%7Bid%7D/subscription` ——
   **服务端 `record.params` 解出来的 `id` 是 `'{id}'` 这个字符串**。
   （实测输出见本篇 §9。）

   后果链条：

   ```
   EventSource 连的 id = utils.uuid()      → 注册表键 = 真实 uuid
   subscription 发的 id = '{id}'           → 在注册表里新建/复用一个假连接
   signals.send() 遍历 registry.sorted()   → 真实连接上永远没有 task_progress 订阅
   ```

   所以任务的进度推送**一次都不会到达客户端**。
   修法：`post('sse/{id}/subscription', param, { params: { id: useSseConnection.getState().id } })`。

   > 为什么现有测试没抓到：[tests/signal/client/proxy.test.ts](../../tests/signal/client/proxy.test.ts)
   > 只断言「`post` 收到的是 `'sse/{id}/subscription'` 这个字面量」，
   > 并且把 `@/client` 整个 mock 掉了 —— **被测的正是缺 id 这个事实**。
   > 这是「测试通过了，但测的是 bug」的典型案例，也说明
   > 替换请求层做 mock 时，必须同时覆盖 url 拼装（或对 `buildUrl` 单独测）。

2. **`/api/sse/{id}` 没有鉴权与连接上限。** 任何人可以创建任意多个 SSE 长连接，
   每个连接都持有 `subscriptions` Map，且只靠 `request.signal` 的 abort 清理。

3. **`useSse` 的 `useEffect` 依赖数组为空**（`[]`），
   回调函数变化**不会**重新订阅 —— 传进 `useSse` 的 `callback` 必须是稳定的引用
   （或接受「一直用第一次那个闭包」的语义）。

4. **`read()` 不把 `[DONE]` 当作终止信号。**
   `analyzeEvent` 对 `data: [DONE]` 返回 `null`，而循环里是
   `if (json) yield json` —— 也就是说 `[DONE]` 只是**被跳过**，
   迭代会继续，直到 `reader` 报 `done` 才结束。
   对「服务端发完 `[DONE]` 就关流」的当前实现没有影响，
   但如果将来有人在 `[DONE]` 之后追加统计帧，前端会照单全收。

## 9. 关于本篇 §8 第 1 条的验证方式（方法说明）

我没有跑测试来验证它（本机的 DSH 沙箱阻止 Vite 启动子进程，
`pnpm test` 会以 `spawn EPERM` 失败，见 [12-开发手册](./15-开发手册.md) §4）。
我用的是**提取纯函数 + 直接执行**的办法：把 `src/client.ts` 的 `buildUrl`
原样复制到一段独立脚本里，喂进四种入参组合，实测输出：

```text
"tasks/{id}" {"id":"abc-123"}                        => tasks/abc-123
"sse/{id}/subscription" undefined                    => sse/{id}/subscription
"sse/{id}/subscription" {"action":"set","type":"task_progress"}
                                     => sse/{id}/subscription?action=set&type=task_progress
"stories/{id}/histories/{sequence}" {"id":"s1","sequence":4}
                                     => stories/s1/histories/4
params after call = {"id":"x1","fuzzy":"a"}    ← 未被修改
```

第 2、3 行确认了：**当 `params` 里没有 `id` 时，`{id}` 占位符原样留在 URL 里**。
第 4 行顺带确认了 `buildUrl` 确实不再改入参（`params after call` 与传入一致）。

> 这类「把一个纯函数抠出来单跑」的验证成本极低，
> 在没法跑完整测试套件的环境里很好用。但它**只能验证纯函数**；
> 涉及 React 生命周期、EventSource、数据库的部分仍然需要真跑测试。
