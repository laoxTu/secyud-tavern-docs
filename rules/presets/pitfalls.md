# 改预设踩过的坑

这篇不讲格式，讲改`docs/templates/root`里的预设时实际会踩到的东西。
格式看各篇正文，这里只记「按格式写对了、但还是不生效」的那类问题。

## 向量条目

* 嵌入模型有 512 token 上限，超了会被静默截断，正文尾部等于没进向量库。
  `public/models/`下两个模型（`bge-small-zh-v1.5`、`all-MiniLM-L6-v2`）都是 512。
  中文大致一字一 token，所以正文控制在 500 字以内就稳。
  实测过的例子：一条 1025 token 的背景条目，截断掉一半，「江南」「帝都」这些词根本没进嵌入，搜不到。
* 向量检索只能被 AI 主动调用工具触发，不会自己冒出来。
  而且命中结果是在**下一轮**才进上下文，当轮看不到。
* 工具返回给模型的是条目的`name`（标题），记到消息上用于注入的是条目 id，两者不要混。
* RAG 设置被禁用时不建向量库，向量条目全部失效，工具只会返回提示。

## event 匹配

* `event`依赖`relatedDates`这个历史变量，而这个变量只由写它的宏和变量工具维护。
  预设里没有那套东西时，`relatedDates`是`undefined`，`event`条目**永远不会触发**，不报错也不提示。
* `event`不是纯日期型：日期区间只是前置条件，后面还要过关键词匹配，所以关键词也得配。
* 想让时间线条目能按剧情时间生效又不依赖变量，可行的做法是把它拆成独立条目、
  在正文里显式写出时间（如`0年7月，……`），让模型自己判断该不该用。这是软约束，不是硬门控。

## role 的取舍

* `system`会并进系统提示词，占用真实消息位，适合每轮都要在的规则与综述。
* `knowledge`伪装成一次知识查询的结果注入，不占消息位，适合设定、人物、势力、事件这类查得到的东西。
* `user`会当作用户输入注入。

## code

* `code`只做去重键，运行时键是`<预设 id>-<code>`，所以不同预设的同名条目不会互相覆盖。
* 同一个`code`在多个预设里出现会共享禁用状态，这是刻意的设计，改的时候注意别撞。
* 条目正文里不要引用`code`。正文是给模型看的，写`code`既占 token 又没有意义，要引用就写名字。

## 宏与工具的绑定

* 工具的`macro`字段填的是宏的`code`。填了一个没有宏提供的`code`，工具仍按`disabled`兜底生效，
  但它在宏选择器里的开关是死的——勾选只是往一个没人读的键里写值。
* 世界书正文、开场白、用户输入、AI 输出会依次过正则和宏。在这些文本里引用宏要带`it.`前缀。
  正文里写`<memory_rules/>`这种记号只会原样输出，不会展开成宏的值。

## 归档与空正文

* 正文为空的条目，导出时文件根本不写进包。
* `type`为`json`的正文在注入前会被压成一行，所以写多行只在编辑时好看，实际不影响注入。
* 世界书、宏、工具的前缀只负责文件配对，真正生效的值全部来自`meta.json`。

## 改预设时的操作提醒

* `docs`是 git 子模块，`git status`要在`docs`目录里看，父仓库只会显示`docs`指针变化。
* 条目文件名带旧下标（如`role_ylx_11`）时，这只影响排序，没有功能作用。
* 批量改`meta.json`后再改同名`content.json`，容易漏掉夹在中间的那一条，
  改完要按清单核对条目总数与键分布。
